Issues and Solutions#

1. Full E2E verification of error_recovery_benchmark is blocked by GPU node dependency (EGL/robosuite runtime constraints) [error_recovery_benchmark] (2026-02-10)#

Solution: Define a layered testing strategy: CPU unit tests and smoke tests first, and defer full E2E verification until the an53 GPU node is available, to avoid test blocking development

2. @praha/byethrow’s Result.try() API is misused: AI uses it directly as a result, but actually it returns a reusable parser function [ccusage] (2026-02-12)#

Solution: Store the return value of Result.try({…}) as a function and explicitly call it to obtain Result<T, E>

3. Metadata keys such as sample_spec are mixed in the LiteLLM pricing JSON; after being parsed by valibot schema, they are treated as empty pricing entries, causing test assertion failures [ccusage] (2026-02-12)#

Solution: After schema parsing, additionally check that input_cost_per_token or output_cost_per_token is not null, and filter metadata entries without pricing data

4. Multiple attempts to SSH to the GPU node are rejected by pam_slurm_adopt (active SLURM job required), resulting in significant time waste [error_recovery_benchmark] (2026-02-14)#

Solution: User suggests first running nvidia-smi -L to check if the current node already has a GPU; if 5 A800 GPUs are present, there is no need to SSH to another node

Learning Insights#

Architecture#

  • Using external summary tools (ccusage) to export historical sessions is an effective engineering approach to address AI context limitations: externalizing session summaries into files allows AI to quickly restore project context in new sessions by reading the files, avoiding repeated background description
  • Testing strategies for large robot RL projects should be clearly layered: CPU unit tests, CPU smoke tests, GPU E2E tests; avoid blocking the entire testing process due to unavailable GPUs

Domain Knowledge#

  • OSC controllers (kp=150, Λ≈5–10kg) have strong resistance to external forces; the impulse of duration_steps=1 (about 20ms) is canceled within the controller response cycle, equivalent to no force being applied; to make the disturbance visible, continuous force application for at least several control cycles or forces far exceeding the controller’s capabilities are required
  • MIHD enhancement plan is implemented according to a strict dependency order: configuration basics (Idea 6 Phase 1) → normalization → UNI2+scGPT experiment → Q-Former/LLaVA → Niche query → batch correction → final configuration closure; this order is designed to avoid cumulative refactoring costs

Tools#

  • @praha/byethrow’s Result.try({try, catch}) returns a factory function (which needs additional calling), rather than directly executing and returning a result; different from common Result monad implementations in Rust/fp-ts, special attention is required
  • In HPC clusters, before executing GPU tasks, use nvidia-smi -L to check if the current node already has a GPU; if SSH to a remote node is needed, explicitly cd to the project directory and activate the conda environment in the remote command (SSH does not inherit the current shell working directory)
  • Offline pricing in ccusage is pre-filtered by the isClaudeModel function in _macro.ts during construction; modifying macro and _pricing-fetcher.ts simultaneously is required to support multiple models
  • The ESLint rules for this project require all Node.js built-in objects to be explicitly imported via node: protocol (e.g., import process from ’node:process’), and cannot use global objects directly

Debugging#

  • When debugging force injection or other physical mechanisms, first verify whether the mechanism works using extreme parameters (such as infinite force, 1000 steps continuously) before gradually adjusting parameters to reasonable ranges, rather than starting from reasonable parameters and increasing step by step
