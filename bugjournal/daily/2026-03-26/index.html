Issues and Solutions#

Key Issues#

1. The automatic execution phase of ccplan (Phases 4–6) progresses too fast due to shallow analysis, driven by “continuous execution requirements”#

Solution: Added clear depth requirements: Phase 4 expanded to 10 dimensions and set a minimum detection threshold; Phase 5 became 4-layer analysis (chain/cross/data flow/contract); Phase 6 required at least one detection and structured risk assessment.

Key insight: The automatic execution phase needs quantitative depth requirements and minimum output thresholds; qualitative instructions like “completely” are insufficient to handle efficiency incentives.

2. When WebSearch/WebFetch tools return tags, ccplan workflow breaks, causing the skill list to reload and lose phase context#

Solution: Added a tool call state preservation protocol with a 3-step recovery mechanism: record the current phase before tool call, re-anchor to ECL state fields after tool return, ignore system-reminder metadata; added inline comments in Phases 0/3/7 where searching is possible.

Key insight: Complex multi-phase workflows require clear state preservation protocols, especially when calling external tools that return a lot of metadata; implicit context continuity cannot be relied on.

3. Functionality regression occurs during error fixing — Claude code forgets some features due to context compression, leading to accidental deletion#

Solution: Implemented feature protection protocols, including persistent ECL documentation and feature protection sections, developed portable guard-check.py CLI tool (with 347 lines of code and security hardening), performed interactive confirmation before command execution, implemented automatic generation for Phase 10, and added pre-modification check protocols.

Key insight: Memory and context are transient, but disk data is persistent. The protection mechanism for writing to ECL files remains unchanged across sessions and compression processes. Portability (moved with the skill directory) is better than solution-specific fixes.

4. Floating window drag fails because startDragging() is called in a setTimeout callback, causing loss of Windows pointer event context#

Solution: Changed to manual pointer capture: capture the pointer when pressed and record the starting position, check a 180-millisecond threshold during movement, and call move_float_ball_to IPC; switch to expand state if below threshold when pointer rises.

Key insight: Windows requires drag operations to start from the original pointer event context; setTimeout/async breaks this rule.

5. Window size adjustment during CSS maximum height transition causes bottom edge misalignment with taskbar, due to multiple rapid ResizeObserver→IPC calls.#

Solution: Changed detail CSS transition to ‘opacity 0.8s ease, max-height 0s linear 0.8s’ — gradually reduce opacity without changing layout, then shrink max-height immediately after delay, enabling a single size adjustment.

Key insight: CSS transitions that affect layout dimensions trigger ResizeObserver every frame; delaying layout changes prevents IPC storm and maintains window position atomicity.

6. Floating window expands panels near edges, overflowing the screen; Windows size adjustment always fixes at the bottom, regardless of actual position.#

Solution: Added EXPAND_MARGIN=8.0 constant to ensure at least 8 pixels from the edge; implemented dynamic anchor detection, using top or bottom anchors depending on contact; added SWP_NOCOPYBITS flag to prevent old client area content from being copied back.

Key insight: Expand/collapse states need different positioning strategies; anchors should be dynamically determined based on current window position, not hardcoded; Windows default size adjustment keeps old content, causing visual drift.

7. Floating window transparent frame and hover delay are caused by the coexistence of the window system and floating window pages.#

Solution: Removed global CSS reuse from floating window pages, added native Windows region cropping (SetWindowRgn), rewritten window geometry state machine, ensuring bottom edge always aligns with the working area.

Key insight: Coexistence with the window system causes style and container stacking conflicts; complete separation is required, not patching.

8. Chart hover detail overlay solution causes visual overlap between elements, violating user experience requirements.#

Solution: Shifted to block layout, using onDetailToggle callback to coordinate window height animations (following existing AccordionToggleDetail pattern), implemented handleChartDetailToggle in App.svelte, and used observer suppression.

Key insight: When involving native window operations, passive observation (ResizeObserver) must be suppressed during animation coordination to avoid double triggers and visual issues.

9. Current cost calculation uses locally hard-coded price tables, which do not match ccusage’s official calculation.#

Solution: Added ccusage CLI adapter (ccusage.rs), implemented silent execution for Windows CREATE_NO_WINDOW, implemented priority-based fallback (first try ccusage, fallback to parser on failure), UsagePayload includes usage_source and usage_warning fields, and displays clear warning messages on the front end.

Key insight: Transparent fallback is crucial: do not mask degradation results as normal; clearly inform users of data source and limitations.

10. Non-MacOS platforms are too transparent because glassEffect is applied to all platforms without native blur support.#

Solution: Added isMacOS() check in applyGlass(), forcing opaque effects on non-MacOS, changed default value to false, updated test snapshots.

Key insight: Platform differences (macOS has native blur, Windows/Linux do not) result in different visual effects for the same configuration; platform detection and compensation at the application level are needed.

General Issues#

11. The replace_all function of the edit tool needs file reading first; batch path updates across multiple files fail with “file not read” error.#

Solution: Used sed for batch replacement across files (crate::parser → crate::usage::parser, for multiple.rs files).

Key insight: For large-scale path updates across multiple files, shell tools (sed, grep) are more efficient than individual edits due to pre-reading limitations.

Lessons Learned#

Key Lessons — Complex multi-stage workflows require clear state preservation protocols when calling external tools that return a large amount of metadata; implicit context continuity cannot be relied on. Tools returning tags may disrupt workflow state.#

  • The automatic execution stage in the workflow needs a certain quantity requirement (at least N discovery points, M layer analysis, at least 1 probe) to prevent “fast but shallow” behavior; qualitative instructions like “thoroughly” are insufficient for efficiency motivation.
  • Persistent protection mechanisms (ECL feature protection) and automated checks (guard-check.py) can prevent feature degradation across sessions. Memory and context are transient, but disk is persistent. Testing is ideal, but the protection mechanisms provide a lighterweight safety net for incremental development.
  • In Windows GUI applications, the best practice is to set CREATE_NO_WINDOW (0x0800_0000) when creating flags using std::os::windows::process::CommandExt to avoid console window pop-up.
  • Controlling the visual anchor of Windows window sizes: the default behavior copies old client content to the upper left corner, causing visual drift; SWP_NOCOPYBITS must be used to disable copying and force a full redraw, while dynamic detection of vertical anchors is needed to fix appropriate edge issues.
  • CSS transitions that affect layout size triggerResizeObserver every frame, delaying layout changes until the visual transition is complete (e.g., “opacity 0.8s ease, max-height 0s linear 0.8s”) can prevent IPC call storms and maintain atomic repositioning of window positions.
  • Based on waves execution, and performing verification checkpoints (cargo check, cargo test, vitest) after each wave can detect issues early, avoiding cascading failures during large-scale refactoring.
  • Using mtime for intelligent cache invalidation is more efficient than unconditional invalidation; existing infrastructure (DirectoryStamp) can be used for low-cost change detection.
  • When dealing with native window operations, passive observation (ResizeObserver) must be suppressed during animation coordination to prevent double triggers and visual artifacts.
  • Transparent degradation mechanisms are very important: do not mask the result of degradation as normal; clearly inform users through data model fields (source/warning) and UI warnings.
  • Prompt engineering skills should decompose multi-intent inputs before intent extraction; in practice, assuming a single intent is a common failure mode. Step 1: decomposing multi-intents allows each trace to be processed independently.
  • Adopting a research-first approach and setting quality constraints (e.g., >1k GitHub stars) can produce better designs than isolated invention; leveraging verified solutions can reduce blind spots.
  • Tauri v2 feature system requires clear permission declarations for all window APIs; missing permissions lead to silent failure (returning null) rather than visible errors. Required: core:window:allow-outer-position, allow-scale-factor, allow_current-monitor for drag functionality.
  • Large file decomposition should maintain the single responsibility principle for each module, while test code should be placed in the same file; using Query.rs (987 lines) is acceptable because most of it is test code.
  • Hybrid tool strategy (parallel agents for complex logic, sed/bash for batch string replacement, direct editing for targeted fixes) can optimize both correctness and speed during refactoring across the codebase.
  • Following existing code base patterns (e.g., AccordionToggleDetail callback mechanism) is easier to maintain than introducing new communication paradigms.
  • Cross-platform UI consistency issues usually stem from platform API differences (fuzzy effects on macOS vs. no fuzzy effects on Windows/Linux); platform detection and compensation must be done at the application layer.
  • Fixed UI behavior should not rely on runtime configuration. If the behavior is constant, the code should reflect this by removing conditional logic, improving clarity and maintainability.
