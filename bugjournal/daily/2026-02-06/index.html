Issues and Solutions#

Key Issues#

1. Public users cannot push data to the repository but need to contribute benchmark results#

Solution: Designed a three-layer architecture: users submit data via a relay endpoint → relay validates and forwards it to repository_dispatch → GitHub Actions handles queuing/ingestion/publishing. The relay holds write tokens, and users have no repository access rights.

Key insight: The crowdsourced data pipeline requires an untrusted ingestion path; GitHubActions with validation workflows can provide audit trails and abuse control without granting contributors write access.

2. Bar charts show reversed lengths (bars with higher scores are shorter), although the values in CSV are correct#

Solution: The root cause is a mismatch between the binary-encoded chart data (bdata) and the CDN version. Solutions include: (1) fixing Plotly JS to match the installed Python version, (2) converting all charts’ x/y/text into regular Python lists instead of Pandas Series, (3) forcing flops_gflops to be numeric types during loading, and (4) setting yaxis rangemode=‘tozero’.

Key insight: The binary serialization format in the client plotting library may cause silent rendering errors when CDN versions change; clear list conversion + version fixation ensures deterministic visualization.

3. Automatic upload of benchmark tests without user consent raises ethical issues#

Solution: Added an interactive prompt after saving runs (default disabled), added clear –upload/–no-upload flags to automated operations, requiring a relay URL configuration before the prompt, allowing non-interactive operation to skip the prompt unless –upload is specified.

Key insight: Telemetry and data collection require explicit voluntary consent and clear disclosure; default disabled prompts and flag-based modes respect user autonomy.

4. HOSTNAME regex is too broad, causing damage to timestamps and version strings in valid data#

Solution: Reduced HOSTNAME_RE range from matching any dotted token to requiring a TLD suffix (.[A-Za-z]{2,}\b) to prevent misjudgment of ‘13.0’ or ‘2026-02-07’ patterns.

Key insight: Privacy disinfection rules need precise boundaries; overly aggressive regex patterns may damage legitimate technical metadata that shares surface syntax with PII.

General Issues#

5. Trend chart deletion is incomplete, leaving outdated method calls that cause AttributeError crashes#

Solution: Added a compatibility fallback function create_trend_chart() returning an empty graph, so old or outdated call paths fail gracefully instead of causing AttributeError.

Key insight: Defensive programming via no-op stubs prevents fragile failures during refactoring; the compatibility layer smooths the migration path.

Learning Outcomes#

Key Takeaways#

  • The crowdsourced data pipeline requires a three-layer architecture (untrusted submission → trusted gateway → protected data storage) with validation/audit mechanisms to prevent abuse while prohibiting write access.
  • Ethical data collection needs explicit voluntary consent, with requests defaulted to being denied; automation scenarios require clear flags rather than relying on interactivity detection.
  • Client visualization bugs usually stem from serialization format mismatches, not data correctness issues; clear list conversion and version locking can prevent silent rendering failures.
  • Privacy cleaning rules need precise boundary conditions; overly aggressive regex patterns may damage legitimate technical metadata that shares surface syntax with PII, leading to PII leakage.

Practical Takeaways#

  • Feature removal refactoring should include compatibility stubs for gradual migration; no-op fallbacks prevent fragile AttributeError errors caused by old call paths.
