Issues and Solutions#

Key Issues#

1. MIHD Benchmark: Redundant embedding computation — The same gene/visual encoder was run hundreds of times for different fusion strategies (for example, PCA was calculated 55 times, UNI2 was calculated 77 times)#

Solution: A two-stage pipeline was designed: in the first stage, all encoder embeddings were extracted and cached (duplication reduction, 110 tasks corresponding to 286 experiments = 62% reduction); in the second stage, the cached embeddings were loaded and only fusion+clustering+evaluation were performed. Now the UNI2 model is loaded only once across all 11 parts, instead of 77 times. Key insight: The current cache uses {gene}_{vision}_{fusion}/{section}_embeddings.npz as a key containing the fusion name, so changing the fusion method causes re-extraction. Encoder-level caching gene_cache/{encoder}/{section}.npz, vision_cache/{encoder}/{section}.npz enables significant reuse. Reuse of model instances across different parts also provides additional performance gains.

2. Error recovery benchmark: Force applied to the wrong body part (using bin2 instead of gripper EEF), no abnormal behavior observed in video#

Solution: Detailed logs revealed that force was applied to bin2. Root cause: _get_eef_body_name() lacked “gripper0_eef” in the possible name list, and the geometric fallback search matched robot0_screen_collision (containing “ee”) → bin2. The problem was solved by adding “gripper0_eef”, “robot0_right_hand”, and “gripper0_gripper_base” to the possible name list.

Key insight: The EEF body names for different robots are different (Sawyer uses gripper0_eef, not the generic gripper_link), which must be explicitly included in the possible name list. Falling back to geometric search may cause strings containing “ee” to match irrelevant geometric models.

3. Error recovery benchmark: PreGrasp detector never triggers — get_task_phase() always returns “unknown”#

Solution: Root cause: get_task_phase() called _check_phase_condition(), which is an empty implementation that always returns False. All dependent on task_phase detectors (PreGrasp, GraspPrecond) are affected. The complete phase detection logic is in get_task_completion_stages(). The problem was solved by rewriting get_task_phase() to use sensor-based detection. Multiple cascading errors were also fixed: forward view used a neutral action instead of a demonstration action, the proximity door prevented pre-contact detector activation, global cooling time made simultaneous detection impossible, and MuJoCo body names did not match.

Key insight: There is a working implementation get_task_completion_stages in the code library and an always-failing empty implementation _check_phase_condition; callers used the wrong method. The symptom is the detector not triggering, but the root cause is dead code in the infrastructure layer. When logical contradictions are observed (no rejection but no output), infrastructure auditing should be prioritized over symptom debugging.

4. Error recovery benchmark: duration_steps configuration parameter invalid — all forces lasted only 1 step (0.05 seconds)#

Solution: MuJoCo automatically clears xfrc_applied after each sim.step. Solution: Modify collect_rollout_stats() to call injector.apply() repeatedly during the first duration_steps of the validation process, and call injector.clear() after the duration ends.

Key insight: MuJoCo’s xfrc_applied is a persistent field but is automatically cleared; the application layer needs to re-applicate each step explicitly to maintain force application. This is a system-level error affecting all error types.

5. Error recovery benchmark: 30N force not observed in visualization video of robot arm movement#

Solution: Add --force_override parameter to test larger forces without regeneration; update the force range in configuration to 15–45N. The problem persists at 30N — further investigation is needed into the force mechanism (possibly too strong OSC control loop, too short force duration at 1 step, or incorrect xfrc_applied application).

Key insight: The force injection mechanism works properly (xfrc_applied is set/clear), but 30N may not be sufficient against the 150 N/m stiffness of the OSC controller, or the duration at 1 step (about 20 ms) is too short for visible effects. The OSC control loop may suppress external forces within one control cycle.

6. CalendarPro: Users cannot delete multiple calendar events that match a pattern (e.g., “Cancel all GB teacher meetings before March 1”) — the robot only says “Please specify the events to delete”#

Solution: The data model was extended to support date ranges and batch operations, the LLM prompt was updated to extract these fields, the search function was modified to accept custom time windows, and an interactive confirmation interface with Discord buttons was added, showing a preview and clear approval options.

Key insight: For productivity tools, single CRUD operations are insufficient — batch operations with safety confirmation (preview + user explicit approval) are crucial for user workflows involving patterns.

7. Gadget/summarize: Headless server cannot install cloud storage application to achieve automatic synchronization#

Solution: Researched and integrated the rclone CLI tool, supporting token-based replication authentication (run rclone authorize on a machine using a browser, copy the token to the headless server).

Key insight: rclone supports over 70 cloud providers; token-based replication headless authentication is the best cross-platform cloud CLI option.

8. Error recovery benchmark: Global cooling time prevents pre-grasp detector activation when proximity detection triggers first#

Solution: Implement tracking of each detector’s cooling time (cooldown_counters dictionary) so each detector has independent cooling time. Filter detection results to exclude detectors still in cooling state.

Key insight: Global cooling time is unsuitable for multiple detector systems because different detectors target different stages/conditions. A multi-detector system requires cooling time tracking for each detector.

9. CalendarPro: When a user message occurs, Google Calendar API returns 403 insufficientPermissions, causing a console warning#

Solution: Switch from calendarList().get() API to settings().get(setting=‘timezone’) API, which only requires the calendar.events scope instead of broader calendar access permissions.

Key insight: Different Google Calendar API endpoints require different OAuth scopes — for timezone retrieval, the settings API has lower permission requirements than calendarList API.

10. CalendarPro: When the LLM times out (nested Claude Code environment), batch deletion fails because intent.data is empty — semantic router correctly classified the intent but did not extract structured data#

Solution: Add a raw_input penetration mechanism in the handler, implement_extract_delete_query() and use regular expression patterns to parse search keywords from Chinese/English phrases, and add date extraction patterns to identify ranges like “before March 1”.

Key insight: The double verification system needs independent extraction capabilities in both paths — relying solely on SR fallback or LLM-generated structured data is insufficient.

11. Gadget/summarize: ccusage –offline mode shows Opus 4.6 price as $0#

Solution: Remove –offline parameter and switch to online mode to get the latest model price.

Key insight: The offline pricing table does not include the latest model (e.g., Opus 4.6); online access is needed for accurate billing information. Although online mode is slightly slower, data accuracy is more important.

12. Error recovery benchmark: Proximity door (max_eef_object_distance=0.05m) prevents Pregrasp operations within 0.05–0.1m#

Key insight: The proximity door is designed for contact-based detectors but is incorrectly applied to all detectors regardless of operating distance. Constraints of specific detectors should not be covered by global door detection.

Lessons Learned#

Key Experience – Two-Stage Pipeline Mode in the Experiment Matrix: When running M encoder × N fusion × K parts, divide it into stage 1 (M × K encoding tasks with cache) and stage 2 (M × N × K evaluation tasks loaded from cache). Reducing redundant computation O(M × N × K) to O(M × K + M × N × K) through shared encoding. Cache key design is important: encoder-level cache allows sharing between different fusion steps.- MuJoCo xfrc_applied behavior: Although the documentation indicates that xfrc_applied is retained between calls, mj_step() automatically clears it. To achieve persistence, the application layer must explicitly reapply each step. It must be explicitly cleared via injector.clear() after duration_steps to achieve a true pulse behavior.#

  • STUB methods and complete implementations coexist with code smells: When a function contains a complete logic but the caller always uses a stub that fails, the call relationships should be reviewed immediately rather than debugging parameters. When logical contradictions (no rejection but no output) are observed, infrastructure auditing should be prioritized over symptom debugging.
  • Force injection visualization balance: An OSC controller with KP=150 N/m requires at least ≥25N of force to see displacement, but the OSC control loop may suppress external forces during a control cycle (about 20ms). A careful balance between force magnitude and duration is needed.
  • Productivity tools need batch operations with security mechanisms: (1) pattern matching to find multiple items, (2) preview of affected items, (3) explicit user confirmation before execution. Single-item CRUD operations are insufficient for actual workflows.
  • rclone is the best cross-platform cloud CLI choice, supporting over 70 providers, and enables headless authentication via token replication (run rclone authorize on a machine in the browser, then copy the token to the headless server).
  • Model reuse between batches: For a visual encoder that processes multiple parts, the model only needs to be loaded once for reuse between parts, without reloading each part. The initialization cost of the model is reduced from O(number_of_parts) to O(1). This is crucial for large Transformers like UNI2.
  • Risk of mismatch in fallback mechanisms: When the main method fails, falling back to a stricter match (such as geometric name search) may produce incorrect results (“ee” matching the screen rather than the end effector). The fallback path requires additional verification. EEF body names vary between robots (Sawyer uses gripper0_eef instead of the general gripper_link), which needs to be explicitly included.
  • Simplified detection logic for step-changing systems: For discrete state systems (such as the step change of the gripper 0→1), detection based on continuity (decreased distance, proximity) is unreliable; the state change itself should be checked directly (whether it is different after N steps).
  • Multi-detector systems require tracking of each detector’s cooling time — global cooling may incorrectly prevent simultaneous detection from different sources. Detector-specific constraints (distance thresholds, phase requirements) should not be covered by global gates — let the detector verify itself.
  • The OAuth permission requirements between Google Calendar API endpoints vary greatly — setting up the API requires lower permissions for the same information (timezone) than the calendarList API.
  • A dual-validation system (semantic router + LLM) needs independent extraction capabilities in both paths — it cannot be assumed that the LLM always generates structured output.
  • The pricing table for ccusage offline mode does not include the latest models (such as Opus 4.6); it needs to be obtained online for accurate billing. Although the online mode is slightly slower, data accuracy is more important.
  • Windows child process calls to .cmd files require shell=True; otherwise, the globally installed npm command cannot be found.
  • Visual encoding bottlenecks: (1) the serial patch extraction loop is limited by CPU (3000–4000 iterations). (2) Calling torch.cuda.empty_cache() approximately 100 times after each batch brings significant overhead. (3) The hard-coded batch_size=32 may not be ideal. Performance analysis is needed before optimization.
  • Environment switching based on child processes: When dependencies require different conda environments, use child processes to call scripts in the target environment instead of trying to switch inside Python.
  • User feedback should be detailed and specific — for calendar operations, always include: what operation was performed, which events were affected, and the time of occurrence.
  • The development environment may interfere with the testing system — nested Claude Code sessions block AI service calls based on child processes. Child processes inherit parent environment variables, and specific variables (such as CLAUDECODE) need to be explicitly removed to avoid nested detection.
  • JSON parsing requires multi-level fallback to handle various formats of LLM output: direct parsing → extracting code blocks → searching for {to} substrings. The LLM output format is unstable, so robustness is required.
  • The priority order of configuration files should be: CLI parameters > environment variables > configuration files > default values, to ensure flexibility and overrideability.
  • The choice of deduplication key should be based on the minimum field combination that uniquely identifies entities. For dialogue: (source, project, timestamp).
