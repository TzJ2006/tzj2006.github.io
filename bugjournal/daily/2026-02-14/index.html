Issues and Solutions#

Critical Issues#

1. MIHD Benchmark: Redundant embedding computation — The same gene/visual encoder runs hundreds of times under different fusion strategies (e.g., PCA was calculated 55 times, UNI2 was calculated 77 times)#

Solution: A two-stage pipeline was designed and implemented: in the first stage, all encoder embeddings are extracted and cached (deduplication, 110 tasks out of 286 experiments, reducing by 62%); in the second stage, the cached embeddings are loaded, and then only fusion + clustering + evaluation are performed. Now the UNI2 model needs to be loaded only once for all 11 parts, instead of 77 times. Key insight: The current cache uses {gene}{vision}{fusion}/{section}_embeddings.npz as the key, including the fusion name, so changing the fusion method causes data re-extraction. Encoder-level caching (gene_cache/{encoder}/{section}.npz, vision_cache/{encoder}/{section}.npz) makes data reuse possible. Reuse of model instances across different parts can further improve efficiency.

2. Error recovery benchmark: Force is applied to bin2 (using bin2 instead of gripper EEF), but no interference with the robot is visible in the video#

Solution: Detailed logging revealed that the force is applied to bin2. The root cause was the absence of ‘gripper0_eef’ in the possible_names list, and the geometric fallback search matched robot0_screen_collision (containing ’ee’), thus bin2 was selected. This issue was resolved by adding ‘gripper0_eef’, ‘robot0_right_hand’, and ‘gripper0_gripper_base’ to possible names.

Key insight: The EEF body names for different robots are different (Sawyer uses gripper0_eef, not the generic gripper_link), and these names need to be explicitly included in the possible names list. Fallback to geometric search may cause strings containing ’ee’ to match irrelevant geometric shapes.

3. Error recovery benchmark: Despite registration, PreGrasp detector never triggers — get_task_phase() always returns ‘unknown’#

Solution: The root cause is that when calling get_task_phase(), it calls a stub _check_phase_condition() that always returns False. All detectors dependent on task_phase (PreGrasp, GraspPrecond) are affected. The complete phase detection logic exists in get_task_completion_stages(). The problem was solved by rewriting get_task_phase() to use sensor-based detection methods. Multiple cascading errors were also fixed: lookahead uses a neutral action instead of a demonstration action, the接近 door prevents the detector from activating before contact, global cooling time prevents simultaneous detection, and MuJoCo body names do not match.

Key insight: There is (get_task_completion_stages) with functional implementation in the code library, and a always-failing stub (_check_phase_condition), indicating the caller used the wrong method. The symptom is that the detector does not trigger, but the root cause is dead code in the infrastructure layer. When logical contradictions are observed (no rejection but no output), infrastructure audits should be prioritized over symptom debugging.

4. Error recovery benchmark: duration_steps configuration parameter does not work — all forces last only 1 step (0.05 seconds)#

Solution: MuJoCo automatically clears xfrc_applied after each sim.step(). The solution is to modify collect_rollout_stats() to loop call injector.apply() during the first segment of verification rollout, and call injector.clear() after the duration ends.

Key insight: xfrc_applied in MuJoCo is a persistent field, but it is cleared automatically, so the application layer must explicitly re-apPLY the force for each step to maintain continuous force. This is a systemic error that affects all types of errors.

5. Error recovery benchmark: 30 Newtons are not visible in the visualization video of the robot’s arm movement#

Solution: A --force_override parameter was added to test larger forces without regeneration; the force range in the configuration was updated to 15–45 Newtons. The problem persists at 30 Newtons — further investigation is needed into the force mechanism (possibly the OSC control loop is too strong, the force duration is too short within 1 step, or xfrc_applied is not applied correctly).

Key insight: The force injection mechanism works (xfrc_applied is set or cleared), but 30 Newtons may not be sufficient to counteract the 150 Newtons/m of stiffness of the OSC controller, or the duration of 1 step (about 20 milliseconds) is too short for visible effects. The OSC control loop may suppress external forces within one control cycle.

6. CalendarPro: Users cannot delete multiple calendar events that match a pattern (e.g., “cancel all GB teacher meetings before March 1”) — the robot only says “Please specify the events to delete”#

Solution: The data model was extended to support date ranges and batch operations, the LLM prompt was updated to extract these fields, the search function was modified to accept custom time windows, and an interactive confirmation interface with Discord buttons was added, showing a preview and explicit approval.

Key insight: For productivity tools, single-item CRUD operations are insufficient — batch operations with safety confirmation (preview and user’s explicit approval) are crucial for user workflows involving patterns.

7. Gadget/summarize: Headless server cannot install cloud driver to achieve automatic synchronization#

Solution: The rclone CLI tool was studied and integrated, supporting token replication authentication (authorize rclone via browser on the machine, then copy the token to the headless server).

Key insight: rclone supports over 70 cloud service providers, and token replication for headless authentication is the best cross-platform cloud CLI option.

8. Error recovery benchmark: Global cooling time prevents pregrasp detector from activating near trigger#

Solution: Tracking of each detector’s cooling time was implemented (cooldown_counters dictionary), giving each detector independent cooling time. Detected results were filtered, and detectors still in the cooling period were removed.

Key insight: Global cooling time is not suitable for multi-detector systems because different detectors target different stages/conditions. A multi-detector system requires cooling time tracking for each detector.

9. CalendarPro: Each user message call to Google Calendar API returns a 403 permission error, causing a warning in the console#

Solution: The calendarList().get() API was switched to settings().get(setting=‘timezone’) API, which only requires the calendar_events scope instead of broader calendar access rights.

10. CalendarPro: When the LLM times out (nested Claude code environment), batch deletion fails because intent.data is empty — the semantic router correctly classifies the intent but does not extract structured data#

Solution: A穿透 of raw_input was added in the processor, enabling extract_delete_query(). Regular expressions were used to extract search keywords from Chinese/English phrases, and a date extraction pattern was added to identify ranges like “before March 1”.

Key insight: The dual verification system needs independent extraction capabilities in both paths — only SR fallback cannot fully rely on structured data generated by the LLM.

11. Gadget/summarize: ccusage — In offline mode, the cost of Opus 4.6 is shown as $0#

Solution: –offline parameter was removed, and online mode was switched to get the latest model pricing.

Key insight: The offline pricing table does not include the latest models (such as Opus 4.6); online access is needed for accurate billing. Although online mode is slightly slower, data accuracy is more important.

12. Error recovery benchmark: The接近 door (max_eef_object_distance=0.05m) prevents pregrasp from operating within 0.05–0.1m#

Solution: A list of detector names was added to bypass the door check — detectors with their own distance verification (pregrasp, grasp_precond) can skip the door check.

Key insight: The接近 door is designed for contact-based detectors, but it is incorrectly applied to all detectors without considering their operating distance. Specific detector limitations should not be covered by global doors.

Lessons Learned#

Key Lesson - Two-stage pipeline mode in the experiment matrix: When running M encoder × N fusion × K parts, divide it into a first stage (M×K encoding tasks using a cache mechanism) and a second stage (loading M×N×K evaluation tasks from the cache). Simplify the redundant calculation of O(M×N×K) to O(M×K + M×N×K), while achieving shared encoding. The design of the cache key is very important: encoder-level caching allows different fusion parts to share resources.- MuJoCo xfrc_applied behavior: Although the documentation indicates that xfrc_applied can maintain persistence between calls, mj_step() automatically clears it. To achieve continuous force application, the operation of each step must be explicitly reapplied at the application layer. For true pulse behavior, it must be explicitly cleared via injector.clear() after duration_steps.#

  • Code odor exists: When a function contains complete logic and the caller always uses a failed stub, the call relationships should be audited immediately rather than debugging parameters. When logical contradictions (no rejection, no output) are observed, infrastructure audits should be prioritized over symptom-based debugging.
  • Visual balance of force injection: The OSC controller requires ≥25N of force to see visible displacement when kp=150 N/m, but the OSC control cycle may suppress external forces (about 20 milliseconds) within one control period. A careful balance between force magnitude and duration is needed.
  • Productivity tools need batch operations with security mechanisms: (1) pattern matching to find multiple items, (2) previewing which items will be affected, (3) explicit user confirmation before execution. For actual workflows, single CRUD operations are insufficient.
  • rclone is the best cross-platform cloud CLI choice, supporting over 70 providers, and headless authentication can be achieved by copying the token (run rclone authorize on a machine with a browser, then copy the token to the headless server).
  • Model reuse between batches: For visual encoders that handle multiple parts, the model only needs to be loaded once for different parts, rather than reloading each part. This reduces the model initialization cost from O(n) to O(1). This is very important for large transformer models like UNI2.
  • Risk of mismatch in fallback mechanisms: When the main method fails, falling back to a looser matching method (such as geometric name search) may produce incorrect results (“ee” matches the screen rather than the end effector). Additional verification is needed in the fallback path. EEF body names vary across robots (Sawyer uses gripper0_eef instead of the general gripper_link), and these names need to be explicitly included.
  • For state change systems, simplifying detection logic is necessary: For discrete state systems (such as the change from 0 to 1 for a clamper), continuity-based detection is unreliable; one should directly check whether the state change is different (whether it changes after N steps).
  • Multi-detector systems need tracking of each detector’s cooling time—global cooling may prevent simultaneous detection from different sources. Detector-specific constraints (distance thresholds, phase requirements) should not be covered by global rules—let the detector verify them itself.
  • OAuth permission requirements vary greatly between Google Calendar API endpoints—the permissions required to set up the API are lower than those for calendarList API, even if the same information (timezone) is needed.
