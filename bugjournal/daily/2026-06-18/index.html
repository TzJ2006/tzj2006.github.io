Problems & Solutions#

Critical Issues#

1. Desktop Video app displayed two windows on startup and had CPU spikes during wallpaper navigation.#

Solution: Resolved double-window issue by removing WindowGroup from SwiftUI Scenes and relying solely on AppDelegate. Fixed performance by limiting thumbnail instantiation to visible tiles and adding cache reuse.

Key Insight: Mixing SwiftUI WindowScene and manual NSWindow management causes race conditions. For large datasets, SwiftUI’s ForEach instantiates all views; lazy loading or explicit limits are required.

2. Zero success rate in RoboCasa Error Recovery Benchmark (coffee task) despite adequate file counts; initial assumption of weak policy was incorrect.#

Solution: Diagnosed root cause as incomplete training (5000/10000 steps) and unverified augmented data. Concluded that file existence does not guarantee simulation validity, requiring regeneration of high-quality augmentation.

Key Insight: Uniform 0% failure rates typically indicate system bugs (loading/normalization) or infrastructure issues rather than model weakness; always verify infrastructure before retraining.

3. Leiden clustering initially appeared inferior to mclust by ~8 ARI points due to default hyperparameters.#

Solution: Conducted joint grid searches over n_neighbors, metric, and resolution. Identified n_neighbors as the dominant lever; optimizing it allowed Leiden to match or exceed mclust performance.

Key Insight: Leiden is highly sensitive to n_neighbors; default values are rarely optimal. Locking k=ground truth provides fair comparison but introduces oracle selection bias that inflates ARI.

4. Ambiguity in RoboCasa checkpoint availability and OpenPI evaluation script compatibility with modern wrappers.#

Solution: Identified changyeon/pi05_robocasa_as50_jax as a viable community checkpoint. Found structural bugs in OpenPI’s client-side evaluation logic that prevent direct deployment, requiring patching before testing.

Key Insight: Official assets are often insufficient for benchmarking; deployment strategies must include paths to third-party or custom-converted weights.

General Issues#

5. Sidebar controls obscured by glass effect; initial safe area fix hid content.#

Solution: Corrected layering by applying .background with .ignoresSafeArea to the container view rather than the content, preserving sub-view visibility.

Key Insight: glassEffect can create separate rendering contexts; standard background extensions are safer for maintaining z-ordering integrity.

6. AWS configuration initially failed with ‘No workspace ID found’ errors during CLI smoke tests.#

Solution: Added specific ANTHROPIC_AWS_WORKSPACE_ID to local config and verified via claude auth status. Provider schema differs from Bedrock, requiring explicit workspace scope.

Key Insight: AWS providers require an explicit workspace scope that differs from standard Bedrock or global Anthropic API calls.

Learnings#

Key Learnings#

  • In spatial transcriptomics clustering, ’n_neighbors’ is often the most critical hyperparameter for Leiden, more so than resolution or seed; optimal values vary by section.
  • MIHD’s staig_fusion model collapse is an implementation-specific bug in the encoder-path pipeline, not a limitation of the underlying STAIG algorithm.
  • SwiftUI WindowGroup and AppDelegate manual window creation conflict silently; best practice is to pick one management style per app.
  • Comparing mclust vs Leiden requires strict control of k. Allowing free k favors Leiden’s flexibility; locking k=7 provides a fair comparison but introduces oracle selection bias if compared to ground truth.
  • When deploying complex models like GR00T and OpenPI, verifying exact version tags (e.g., n1.6.1-release) is vital as upstream refactors often break legacy evaluation scripts.

Practical Learnings#

  • Cross-device context switching requires strict documentation of project states; CLAUDE.md serves as a critical interface for maintaining architectural coherence across AI sessions.
  • mKDTree indexing for spatial refinement before clustering loops can drastically reduce computation time in iterative grid searches by O(N²).
