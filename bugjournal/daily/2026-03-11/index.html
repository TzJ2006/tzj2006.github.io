Issues and Solutions#

Key Issues#

1. MIHD patch query returns incorrect physical location: “Patch during query does not match the current patch”#

Solution: The root cause is inconsistent barcode sorting between cache (sc.read_10x_h5 order) and visualization (sc.read_visium order). This issue is resolved by establishing a clear mapping between barcodes and cache indices: {str(b): i for i, b in enumerate(cache_barcodes)}. Data paths and coordinate conventions were also fixed.

Key Insight: When the order of data sources differs, index-based searches fail. A clear key-based alignment method (barcode in this case) is always used when connecting cache data and reloading at runtime.

2. PID namespace isolation in K8s containers prevents nvidia-smi from displaying process information#

Solution: A custom GPU monitoring tool was built that uses /proc//fd to scan /dev/nvidia* device files and the CUDA_VISIBLE_DEVICES environment variable. Tools that open all GPUs (such as nvitop, gpustat, Claude) are filtered out. A rich TUI interface similar to nvitop is implemented.

Key Insight: Containerized GPU monitoring requires checking the process file system. /proc/fd symbolic links can show opened devices; CUDA_VISIBLE_DEVICES contains the actual information. Tools that open all GPUs are false positives—these tools can be filtered by checking whether CUDA_VISIBLE_DEVICES is empty.

3. Despite identical hardware and configuration, training times for the same command differ by 33% between the two projects (openpi 15 hours vs pi05 20 hours)#

Solution: Parallel exploration agents identified the difference in JAX versions (0.5.0 vs 0.5.3) as the main cause. Versions of 6 dependencies were systematically aligned: JAX 0.5.0→0.5.3, torch>=2.5.1→2.7.1, orbax-checkpoint 0.11.1→0.11.13, numpy, beartype, transformers. override-dependencies were added to resolve torch<2.7 constraints in lerobot.

Key Insight: A slight JAX version upgrade (0.5.0→0.5.3) can bring about 20–30% performance improvement due to XLA compiler optimizations; dependency drift across multiple projects is a hidden performance issue that requires regular alignment audits. uv’s override-dependencies provide an effective way to resolve conflicts without branching upstream code.

4. MIHD file structure became chaotic due to inconsistent naming (benchmark_results, hd_results, rm_ideal are distributed in different directories)#

Solution: A systematic 8-step migration plan was executed: creating a new hierarchy (DLPFC, HD, rm_ideal/{cross_section,single_section}), migrating files, updating 14 code files and documents, and cleaning up old directories. bash mv and Edit tools were used for batch path updates. Key Insight: Large-scale refactoring requires early planning (creating directories first), followed by file migration, code updates, and document updates. For historical documents, sed batch processing can be used for archiving.

5. Pi05 training fails at startup: ‘RuntimeError: torchvision::nms does not exist’#

Solution: Detected a version mismatch between torch 2.7.1 and torchvision 0.21.0 (0.21.0 was compiled for torch 2.6.x). torchvision==0.22.1 was added explicitly to pyproject.toml, and uv sync was used for upgrade. After verification, torch is set to 2.7.1+cu126, torchvision is set to 0.22.1+cu126.

Key Insight: PyTorch and torchvision have strict version pairing requirements (2.7.x requires 0.22.x). Indirect dependencies resolved via uv/pip may select incompatible versions—key binary-dependent dependencies must always be explicitly specified.

Common Issues#

6. Wandb logs in Pi05 show num_workers=16, while the default value in code is 8#

Solution: It was found that –num-workers was set to 16, overriding the default value; it is recommended not to pass this parameter and instead modify the code.

Key Insight: Configuration parameters may come from multiple sources (code default values, CLI parameters, configuration files); before making code changes, it is necessary to fully trace their origin.

7. The initial gpumon.py layout had line-end padding, column truncation, and overly crowded process lists#

Solution: Improved step by step: 1) Fixed column width calculation for GPU information, 2) switched to table layout, 3) adopted the dual-boundary style of nvitop, 4) filtered monitoring tools, 5) grouped processes under corresponding GPUs.

Key Insight: Terminal user interface design requires multiple iterations. Refer to existing tools (such as nvitop) to meet user expectations. Automatic filtering of noise (monitoring processes) can improve the signal-to-noise ratio.

Limitations of AI#

Key limitations#

  • Plan mode death spiral: In the v5 visualization task, the AI tried more than 4 times to enter ExitPlanMode, and each attempt was rejected. It was only at the end that the user was asked “what is preventing our progress?” The rejection loop should have been detected earlier, and the mode should have been switched to clarification mode.

General limitations#

  • When initially editing pyproject.toml, there was no expectation of the conflict between lerobot’s torch < 2.7 constraint; the problem was discovered only after the uv lock failed, and then torch was passively added to override-dependencies. A prior analysis of the transitive dependency graph could have been done.
  • Two parallel exploration agents were used to handle almost the same code base (openpi and pi05 share the same OpenPI framework), leading to duplicate discoveries. If only one agent performed sequential exploration, efficiency would be higher.
  • The initial GPU monitoring design was generic and did not consider domain characteristics. No active check of the user experience patterns of nvitop (the domain leader) was done. Multiple user corrections were needed to achieve the desired layout. When building a CLI tool, existing tools should be studied.
  • In the training speed analysis, two parallel Explore agents were started, but initially no comparison was made between uv.lock files (real data of the installation version). Checking lock files such as train.py and config.py first is the primary task for solving dependency-related issues.

Lessons learned#

Key lesson – K8s’ PID namespace isolation can prevent detection of nvidia-smi processes. Solution: Identify the issue by checking the /proc//fd/ directory for /dev/nvidia* devices and the CUDA_VISIBLE_DEVICES environment variable. If monitoring tools open all GPUs without using CUDA_VISIBLE_DEVICES, these detections are likely false positives.#

  • Version upgrades of JAX/XLA (0.5.0→0.5.3) can increase training speed by 20–30% through compiler optimizations; even small updates at the framework level are worth performance audits in machine learning projects that require large computational resources. Changes in dependencies between multiple projects may be hidden performance issues and need regular adjustment.
  • Strict version pairing in PyTorch/torchvision: torch 2.7.x requires torchvision 0.22.x, and 2.6.x requires 0.21.x, etc. If the versions do not match, C++ operator registration fails. When using torchvision, be sure to explicitly specify the dependencies between the two, as indirect solutions may fail.
  • Barcode sorting issues in spatial transcriptomics: The cache created by sc.read_10x_h5() may have a different barcode order than runtime sc.read_visium(). Index-based searches may incorrectly map to wrong positions. Always use a clear mapping from barcodes to indices: {str(b): i for i, b in enumerate(cache_barcodes)}.
  • When the plan mode is repeatedly rejected, users may face insurmountable obstacles (environment unavailable, priority change, technical limitations). After 2–3 rejections, the focus should shift from “let me fix the plan” to “what is preventing us from moving forward?”
  • Centerpoint calculation in RM-IDEAL: For a given query domain, obtain embedding vectors for all points in the domain, compute the average vector to get the centerpoint, and then compare the centerpoint with the positions of other reference points using cosine similarity. This compresses N pairs of M comparisons into 1 pair of M comparisons, improving efficiency and robustness.
  • The override dependency relationship of uv is a good tool for resolving transitive dependency conflicts without splitting or patching upstream packages; it is especially useful when fixed git revisions are required due to incompatible constraints.

Summary of practical experience#

  • Before assuming a repair solution, track all sources of configuration parameters (code defaults, CLI parameters, configuration files, environment variables). Because the values in actual operation may differ from the results of code checks.
  • Refactoring large code bases requires phased approaches: 1) Create a new structure, 2) Migrate files, 3) Update code references, 4) Update documentation (for archived documents, use batch sed processing), 5) Verify the final structure, 6) Clean up old directories. If code updates are done before file migration, it may lead to program crashes.
