Problems and Solutions#

Key Issues#

1. The “Xs ago” text in the footer moves up/down when the window size is adjusted, despite anchor fixes already applied#

Solution: Set the position to fixed; bottom:0, ensuring it stays fixed within the viewport rather than relying on layout

Key insight: SetWindowPos and CSS re-layout introduce an inherent 1-frame delay in the Win32+WebView2 architecture; only position:fixed can bypass the CSS layout timing

2. SWP_NOCOPYBITS causes WebView2 content to disappear every time SetWindowPos is called#

Solution: The SWP_NOCOPYBITS flag was removed; Windows retains the old pixel content, only making the new area ineffective

Key insight: SWP_NOCOPYBITS optimization works for native windows but causes issues in WebView2 — a blank window appears every frame until re-rendering completes

3. The chart hover detail panel flickers and jumps when the mouse moves between bars#

Solution: DOM destruction{#key displayedIdx} was removed, the fade duration was reduced from 500 ms to 150 ms, and the two-stage hide process was simplified to a single process

Key insight: DOM destruction and reconstruction during transitions cause visual repetition; responsive content updates are smoother than button triggers for reloads

4. The border radius edge of #app’s bottom border shows transparent gaps when size is adjusted#

Solution: Before calling IPC, appEl.style.minHeight was set in JS, allowing the browser to render #app to the target height within the same frame as SetWindowPos

Key insight: IPC delay between JS and Rust causes visual artifacts; syncing CSS changes can eliminate the gap

5. Window anchor detection fails at any position (not just 5px from the edge)#

Solution: detect_vertical_anchor was changed from threshold-based detection to distance comparison (top_gap vs bottom_gap); the bottom anchor uses current_rect.bottom instead of work_bottom

Key insight: Threshold-based detection creates dead zones where window behavior is unpredictable; distance comparison works in any case

Learning Outcomes#

Key Takeaways#

  • There is an inherent 1-frame delay between Win32+WebView2 architecture and SetWindowPos (native) and CSS re-layout; only position:fixed bypasses this temporal dependency
  • Hypothesis-based debugging performs better than parallel investigations; three sub-agent investigations H1/H2/H3 can save time and accumulate evidence
  • Evolutionary constraint planning’s adversarial review (stage 5) can identify critical issues: 10 issues were found before implementation, including sub-agent writing conflicts, lack of success criteria, context exhaustion
  • SWP_NOCOPYBITS optimizes native window repainting but breaks WebView2 rendering — a blank window appears every frame until the browser re-renders everything
  • Observable success criteria (like “Xs ago” text position) are better for debugging UI issues than abstract indicators (window coordinates)
