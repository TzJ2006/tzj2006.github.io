Problems & Solutions#

Critical Issues#

1. Ground truth leakage and system ‘cheating’ via environment state access.#

Solution: Deployed prediction_boundary.py to restrict visibility to camera-only data and intercept ground truth subgoals.

2. Scientific invalidity due to test-set contamination or parameter tuning on test splits.#

Solution: Conducted a retrospective audit, documented tuning instances in a formal ledger, and updated launchers to strictly enforce ‘val’ split usage.

3. AI model hallucination of pending tasks from negative facts (e.g., ’not published’ becoming a task).#

Solution: Updated the canonical system prompt with explicit negative constraints to forbid deriving intent from the absence of an action.

4. Data corruption in .npz/trajectory files resulting in truncated image streams.#

Solution: Extracted intact state data and generated clearly labeled re-rendered image supplements to maintain data provenance without modifying original numerical payloads.

5. Discrepancy in rendering methods (GPU vs. Software) between main systems and historical baselines.#

Solution: Classified historical results as diagnostic-only and mandated a strict new GPU-only comparison protocol.

6. Extreme disk space pressure and redundancy in summarization logic.#

Solution: Categorized data for migration/cleanup and designated a single ‘gadget’ repository as the source of truth for logic.

7. Risk of results invalidation through silent reuse of stale or mismatched planner caches.#

Solution: Implemented a cache provenance mechanism requiring a strict match between the cache and the current input/model/code state.

8. Inconsistencies in academic metadata regarding author order, publication years, and identity.#

Solution: Implemented cross-validation using personal faculty homepages, institutional affiliations, and Google Scholar IDs as primary anchors.

General Issues#

9. API rate limiting (429/403 errors) and access restrictions from academic databases.#

Solution: Transitioned to a multi-source strategy using OpenAlex, official homepages, and search engine snippets as fallbacks.

10. TokenMonitor UI refactor caused budget and price information to be hidden.#

AI Limitations#

Critical Limitations#

  • Logical hallucination where the model misinterpreted negative statuses as pending tasks.
  • Inability to reconstruct original pixels from a broken compression stream; it can only generate derivative images by re-rendering.

General Limitations#

  • Difficulty in acquiring reliable quantitative data for subjective metrics like ’lab pressure’ or ‘admission difficulty’.
  • Encountered data retrieval barriers including rate-limiting (429 errors) and access restrictions (403 Forbidden) from academic databases.
  • Difficulty in distinguishing between ‘official research line’ and ‘current active research’ solely from web scraping.
  • The AI’s UI refactor for the recommendation line caused a regression by hiding existing budget/price data.
  • The AI defaulted to a defensive and self-weakening writing style unsuitable for high-impact academic submissions.
  • The AI initially hesitated to declare audits complete, labeling inherent evidence gaps as ‘unresolved’.
  • Inability to directly edit or merge to remote repositories (GitHub/Hugging Face), necessitating a staged/PR-based workflow.

Learnings#

Key Learnings#

  • A system-level integration narrative (e.g., ‘Visual Memory Harness’) is more robust for top-tier publication than focusing on isolated component improvements.
  • The ‘Press-Release Principle’—focusing on strengths and avoiding process-oriented descriptions—is a powerful methodology for academic writing.
  • Scientific integrity in benchmark comparisons requires strict parity in rendering engines and explicit disclosure of task-specific priors.
  • Validating releases in an unauthenticated and isolated environment is essential to guarantee true reproducibility.
  • To prevent task hallucination, canonical prompts must explicitly state that a negative status is not a request or a pending task.
  • A ’thin’ core with modular, verifiable capabilities is more stable and easier to debug than a massive, monolithic orchestration system.
  • Committing large datasets directly into Git history can cause the .git folder to swell to tens of gigabytes.
  • Rust/Cargo ’target’ directories are rebuildable and safe to clear to alleviate storage pressure.
  • When dealing with corrupted dataset members, it is better to provide an exclusion manifest and a corrected candidate rather than silently removing data.
  • Implementing fingerprint-based caching reduces redundant model calls from several seconds to milliseconds for identical summary requests.
  • Using an ‘audit file’ approach to record discrepancies instead of directly modifying original files preserves data provenance.
  • Maintaining statistical counts by using explicitly labeled companion files for derivative data is superior to modifying original payloads.
  • Integrating diverse data sources like personal homepages and replacement candidates significantly improves automated bibliography verification.
  • Strict cryptographic/logical binding of caches to input digests is essential to guarantee the provenance of cached plans.
  • Institutional computing availability (e.g., shared clusters) serves as a more reliable indicator of group resources than unconfirmed funding.
