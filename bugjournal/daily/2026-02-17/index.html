Issues and Solutions#

Key Issues#

1. The single-modal ARI of MIHD visual encoder is extremely low (approximately 0.065), which does not match historical UNI2 performance; the embedding vectors show abnormal patterns (initially many duplicate rows).#

Solution: An in-depth investigation of tissue_positions_list.csv revealed that col4 corresponds to pxl_row_in_fullres (Y-axis) rather than pixel_x, and col5 corresponds to pxl_col_in_fullres (X-axis) rather than pixel_y, although the code naming is reversed. By analyzing the step changes of array_row/array_col, it was confirmed that col4 changes by 119.8px per step (Y-axis), and col5 changes by 68.9px per step (X-axis). The column name was corrected to (pxl_col, pxl_row) to resolve this.Key Findings: Data errors are more subtle than model errors: the code runs normally, caching is generated successfully, and tests pass, but all results are based on incorrect data. We need to trace anomalies at the macro level (low ARI) back to the original data source (CSV column definitions). The Euclidean invariance of spatial distance means graph construction is unaffected, but the visual patch content is completely misplaced.

2. ccusage returns cost=0 for Claude-opus-4-6, causing severe token cost tracking failure (actual $43 on February 17 shows $0.90, which is 13 times underestimated)#

Solution: A backup pricing mechanism was implemented in the fetch_ccusage() function of daily_summary.py through post-processing logic _fix_zero_cost_models(). A dictionary _FALLBACK_PRICING was added (opus-4-6: input $5/model, output $25/model, caching creation $6.25/model, caching reading $0.50/model) to calculate correct costs. Field name errors were fixed (mb.get(‘model’) → mb.get(‘modelName’) or mb.get(‘model’)) to ensure compatibility. Logs for February 13–17 were re-exported, and the displayed costs were corrected from $3–7 per day to actual $18–48 per day.

Key Findings: Defects in third-party tool pricing cannot be directly fixed—a local backup mechanism is used as a practical solution. LiteLLM uses versioned model names (anthropic.claude-opus-4-6-v1 with -v1 suffix), while Claude Code logs use simplified names (claude-opus-4-6), leading to systematic mismatches. The backup design must trigger only when anomalies occur (cost=0) to maintain backward compatibility when upstream fixes appear. Cost tracking errors can lead to over 90% underestimation (13 times in this case), severely affecting resource planning decisions. Always verify the output format of third-party tools by printing the original data rather than inferring from documents.

3. The Tianhe non-pulse injector (friction/pose perturbation/gripping bias) crashes when trying to parse body/geometry IDs in the MuJoCo model due to “AttributeError: no attribute mj_name2id”#

Solution: The model.body_name2id() and model.geom_name2id() methods are wrapped by robosuite instead of direct mujoco.mj_name2id(). An auxiliary function _resolve_body_id() is added, first trying “name” then trying “name_main” suffix (robosuite naming convention). The try/except mechanism is used to handle missing bodies gracefully.

Key Findings: Robosuite wraps MuJoCo through its own API layer and adds a _main suffix after the object name. Direct calls to MuJoCo C API bypass the framework layer and cause crashes—only the wrapping function provided by the framework must be used for name conversion. The robot simulation framework layer abstracts the original physics engine; direct API calls bypassing the framework cause crashes. Before modification, always check valid reference code in the same codebase (e.g., ImpulseInjector) for the same code library.

4. The Tianhe BC-RNN strategy crashes due to KeyError 'object' because the obs dictionary generated by StateExtractor contains the key ‘object-state’, while robomimic training data uses the key ‘object’ (different robosuite tasks have inconsistent key names: PickPlace uses object-state, Lift uses object)#

Solution: A key mapping was added in _to_robosuite_obs() Strategy 1, converting the object-state alias into object before returning the original obs. The backup solution for Strategy 3 was updated, merging objects from StateExtractor into a object key using pos + quat. Verified by 79 unit tests and GPU integration tests—KeyError has been eliminated.

Key Findings: Robosuite automatically adds a -state suffix after grouping modalities (e.g., object → object-state), but training data uses the original names. The adapter layer must fill this naming convention gap. Different robosuite tasks have inconsistent observation key naming rules. Manual reconstruction of obs cannot guarantee consistency with key names during training. The safest approach is to directly pass the original env.step() return value via a key alias. This indicates that cross-task compatibility requires either (a) a unified obs format or (b) a clear key mapping layer.

5. LLMs often return corrupted JSON in structured reports: unescaped quotes, incomplete objects, extra text, or truncation near token limits, leading to parsing failures and workflow interruptionsSolution: A four-stage backup parser was implemented: (1) directly use json.loads(), (2) extract json blocks, (3) find a complete JSON object based on deep matching of bracket structures, (4) call the LLM to fix the corrupted JSON. For APIs that support this feature, use tool_use (Anthropic) or response_format=json_object (OpenAI) to force valid JSON.#

Key Insight: Structured data generated by LLMs require multiple backup strategies for defensive parsing. The native JSON mode (tool_use/json_object) can significantly reduce errors, but cannot completely avoid failures. Using the LLM fix as the final backup solution can build a robust process. Each backup layer handles a specific type of failure: code blocks handle Markdown formatting, bracket matching handles truncation issues, and the fix handles syntax errors.

6. The BC-RNN model has a 0% success rate after resolving KeyError—the robot hovers over the box but cannot approach the target#

Solution: Three visual videos (400 frames each) were generated to show the robot’s behavior. The root cause was identified as a training insufficient checkpoint (epoch 600, limited demo data), not a framework bug. The video shows the robot hovers but never tries to grab. More training epochs or better checkpoints are needed.

Key Insight: Even if unit tests pass, GPU integration tests are crucial. BC-RNN passed all 79 unit tests, but actual operation on GPU reveals 0% SR issues. Video visualization is important for diagnosing behavioral quality issues in robots. Framework correctness and model quality require different verification strategies: unit tests/integration tests confirm code logic; video visualization reveals behavior quality.

7. SSH connections to the Tianhe HPC cluster often disconnect, causing Claude Code sessions to be lost and work to fail; VS Code Remote SSH is also affected#

Solution: A multi-layer deep defense scheme was implemented: (1) set up SSH keep-alive on both ends (15-second heartbeat, 90-second tolerance), (2) use tmux sessions for persistence so processes continue after disconnection, (3) write Claude-tmux scripts to restore sessions with one-click via automatic proxy, (4) comment out the automatic proxy in .bashrc to isolate the user environment from shared accounts, (5) write local client configuration instructions for ControlMaster multiplexing and automatic SSH reconnection scripts.

Key Insight: Network instability requires multiple layers of redundancy: protocol layer (TCP keep-alive), SSH layer (ControlMaster), application layer (tmux + automatic reconnection). No single layer is sufficient to ensure production environment reliability. tmux separates session state from connection status, achieving true recovery capability. Session-level proxy configuration (not global .bashrc) avoids affecting other shared account users. When working on shared server accounts, each environment modification (PATH, proxy, alias) must consider multi-user impacts.

8. The multi-device daily report workflow requires a synchronization mechanism—device-independent exports but merged reports require access to all device exports, and merged devices may not have access to these files#

Solution: A two-layer rclone synchronization is used: export files are uploaded to <remote>/logs/, merged reports are uploaded to <remote>/reports/. The merge --sync flag is added before LLM aggregation to download logs/files from all devices. A _merged_devices tracking mechanism is implemented to avoid re-summarizing already processed devices.

Key Insight: Distributed workflows require clear synchronization points. Separating original export files (logs/) from aggregated output (reports/) prevents circular dependencies. Idempotent design (skipping processed content) can be safely run again without expensive redundant API calls.

9. The original single-device daily report design assumes a single device; when users need multi-device aggregation, the current architecture cannot handle it#

Solution: The single-stage design (reading dialogue → calling API → generating report) was completely refactored into a two-stage design (Stage 1: export dialogue as JSON per device; Stage 2: merge all exports and call API to generate a summary report). This architectural change was explicitly requested by users.

Key Insight: User requirements change during development. Human users discovered the single-device limitation, while AI did not anticipate it in the initial design. The two-stage architecture is more complex but necessary for real-world use cases. This indicates that human system thinking is superior at anticipating distributed deployment limitations.

10. Scene generation produced zero-friction/gripping bias scenes, despite the injector being enabled (initially only pose_perturb was effective)#

Solution: The detector only generates specific sub-types of friction/gripping bias ErrorSpecs, which do not trigger during operation. A _augment_specs_with_alternatives() method was implemented to programmatically generate friction/gripping and clamping bias/scrambled specifications when the original detector yields no results. 100 additional friction scenes were generated (55 scrambled, 28 tip overshoot, 17 large offsets), expanding the database to 454 scenes.

Key Insight: Error scene generation is a funnel: detector triggers → ErrorSpec generation → injector application → validation → scene acceptance. Enabling the injector does not guarantee generated scenes—it depends on the frequency of detector triggers. Different error types have distinct acceptance rates depending on the task. In pick-and-place tasks, pose perturbation is more generalizable than friction/gripping anomalies. Programmatic specifications can compensate for the coverage gap of the detector.

11. No MimicGen pre-trained BC-RNN checkpoints are available for PickPlace tasks#

Solution: A comprehensive search (official repository, HuggingFace, local filesystem) confirmed that MimicGen only provides datasets and not pre-trained model weights. The demo dataset generated by MimicGen is used to design self-training plans via the robomimic framework.

Key Insight: Official releases may provide data but not trained models. Always verify resource availability before planning dependent workflows. When pre-trained checkpoints are unavailable, training from demonstrations becomes a necessary backup solution.

## Lessons learned  

### Key lessons – Data errors are more hidden and destructive than model errors: MIHD coordinate exchange errors caused all visual experiment results to fail, but the code logic was completely normal and all tests passed. Issues need to be investigated from macro-level metric anomalies (ARI) back to data sources (CSV column definitions). This requires a complete data scientist thought chain; unit tests alone cannot detect such errors.  
- Name convention differences in cross-framework integration are hidden traps: the `_main` suffix in robosuite, differences in observation key names for different tasks (object and object state), and the `-v1` suffix in LiteLLM—these details are not obvious in the documentation but cause runtime errors. The robot simulation framework covers the original physics engine through layer abstraction (robosuite encapsulates MuJoCo). Direct API calls bypassing the framework layers cause problems—framework wrappers must be used to handle naming conventions (such as `_main` suffix) and state management. Robosuite observation key naming rule: the environment automatically adds `-state` suffix after grouping mode (e.g., `object` → `object-state`), but training data usually uses the original names. The adapter layer must handle this mismatch. The safest strategy is: (1) use the framework-wrapped API instead of the underlying API; (2) use the original data structure instead of manual reconstruction; (3) print actual output to verify field names, rather than relying on documentation. Check the available reference code in the same codebase before modification.  
- Framework correctness and model quality require different validation strategies. Unit tests/integration tests can confirm code logic and eliminate KeyError and other errors. Video visualization can reveal behavior quality issues (robot hovering and grasping). Even if unit tests pass, GPU integration tests are crucial—BC-RNN passed 79 unit tests, but 0% SR problems and under-trained checkpoints could only be detected through GPU deployment and visualization checks. Each validation layer has a different role.  
- The multi-device collaborative daily report tool establishes a closed loop: each device exports local logs → the central node merges remote logs → unified deployment to Hugo → publishing to GitHub Pages. This process was used extensively on 2026-02-17 (processing 4 historical dates), proving the feasibility of the two-stage architecture. The next step is automation (proposed by users but not implemented). Meta-tools (used to analyze tool usage) require careful consideration of workflow allocation—conditions on each device, data synchronization methods, and partial information processing methods. The two-stage architecture (local export + centralized aggregation) is more suitable for distributed scenarios than a single monolithic stage design.  
- The expansion from 251 to 454 of the error recovery benchmark scenario library is a successful case of incremental expansion: first implementing the pulse injector (M4) → discovering the need for non-pulse types (M5) → fixing MuJoCo API compatibility → generating multiple type scenarios through the detector candidate extension mechanism. This shows an iterative path from the minimum viable product to fully functional features. Error scenario generation is a funnel: detector triggers → error specification generation → injector application → validation → scenario acceptance. Enabling injectors does not guarantee generated scenarios—it depends on the trigger frequency of detectors. Acceptance rates for different error types vary greatly depending on task dynamics. Pose perturbation is more common in pick-and-place tasks than friction/grasping anomalies. Programmatic spec augmentation (_augment_specs_with_alternatives()) can compensate for insufficient detector coverage.  
- Defensive programming is required for third-party tool integration: zero-cost patches (ccusage), field name compatibility (modelName or model), and self-degradable mechanisms designed for future fixes (when LiteLLM fixes occur, fallback becomes no operation). This “activate only when needed” patch strategy minimizes maintenance costs. Pricing issues of third-party tools should be resolved through local fallback mechanisms rather than waiting for upstream fixes. Design fallback should only trigger in abnormal values (cost = 0) to ensure backward compatibility. LiteLLM uses versioned model names (anthropic.{model}-v1 with an optional:0 suffix), while Claude Code logs use simplified names, leading to systematic mismatches. Cost tracking errors may cause over-underestimation by more than 90% (13 observations), severely affecting financial planning. Regular audits of cost metrics are crucial.  
- When human-machine collaboration is optimal, humans specify the system architecture and strategic decisions, and the AI is responsible for technical implementation and optimization. In this meeting, users’ architectural insights (two-stage design, multi-device synchronization) were important; the AI’s technical execution capabilities (parsing alternative solutions, configuration optimization) filled the gaps. Qualitative judgments from domain experts are crucial for identifying systematic issues. Data-driven analysis by AI and human intuition form an effective complement.  
- Remote development in unstable connection environments requires multiple layers of defense: maintaining active connections (prevention), session persistence (handling interruptions), multiple connections (quick reconnection), and automated scripts (resumption). Single-layer solutions will fail in real network environments. For shared server accounts, user-specific custom settings should be placed in conditional blocks or independent startup scripts, rather than affecting all users’ common .bashrc configuration. tmux simultaneously handles state persistence and environment boundaries. Proxy configurations for session scope (not global bashrc) can avoid affecting other shared account users.  
- Structured data generated by LLMs require multiple alternative parsing strategies for protection. The native JSON pattern (Anthropic uses tool_use, OpenAI uses json_object) helps somewhat, but failures cannot be completely avoided—fixing is always the last resort. Each alternative layer targets specific failure modes: code blocks handle Markdown formatting, bracket matching handles truncation issues, and repair functions handle syntax errors.  
- The daily summary tool can benefit from gradual architecture evolution: starting with a simple task/problem list, adding session summaries to provide context, and adding priority metadata for filtering. Each layer meets the needs of different readers. Batch document workflows benefit from the two-stage architecture: (1) extraction of source files based on local context; (2) integration across sources and global deduplication. This pattern also appears in summary tools (export → merge), MIHD processes (first stage cache embedding → second stage fusion), and error recovery tests (generate scenarios → collect data).  
- MimicGen release policy: only datasets are provided, no pre-trained model checkpoints. The official version may only provide data without the trained model—confirm resource availability before planning. BC-RNN (with RNN behavior cloning) is a simple supervised learning method: collect human demonstration (state, behavior) pairs, train LSTM to predict behavior, and then deploy as a strategy. When enough demonstrations are available, this is a simple and effective foundation for handling manipulation tasks. When pre-trained checkpoints are unavailable, training from demonstrations becomes a necessary backup.  
- Post-work log analysis (summarizing the past week’s work) is a valuable practice; it converts raw conversation logs into structured knowledge outcomes, helping identify patterns and track progress over long periods—powerful design patterns for idempotency (tracking processed content, avoiding duplicate work) are crucial for processes that may be interrupted or restarted. The _merged_devices tracking mechanism avoids expensive duplicate API calls when processing partially completed aggregated data.  
- Large model asset management (47GB+ VLA checkpoints) requires an organizational approach based on symbolic links to avoid duplication while maintaining centralized discoverability. Dispersed checkpoints in the file system hinder reproducibility and configuration management. A centralized checkpoint directory improves discoverability.  
- When fixing historical data quality errors, separating data correction (export) from downstream consumption (report generation) is important. This avoids entire process interruptions due to downstream dependency failures (e.g., LLM API unavailable). The export stage depends on Node.js tools (ccusage), and the merging stage depends on the LLM API—even if merging is blocked, export can continue.  

### Practical experience summary  

- The scope of complex research project documents should not only cover main modules but also include dependencies/submodules (11 in the Motion framework), data transformation pipelines, and integration points across repositories (LeRobot, OpenPI, MimicGen). Thorough exploration can prevent incomplete documents from causing onboarding difficulties.
