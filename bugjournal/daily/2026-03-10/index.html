Issues and Solutions#

Key Issues#

1. Physical force injection of Error Recovery Benchmark v4 cannot generate a time context compatible with VLA — because the initial state of the injection lacks the behavioral history required by the VLA model. Solution: A v5.0 architecture was designed, using an offline two-stage process: Stage 0 collects clean trajectories (human data + 10×VLA strategy success data) → Stage 1离线 scans for opportunity points per frame → Stage 2 quota scheduler (100 points per task × category) → Stage 3 context replay (replay N-1 frames to build a VLA context window, inject an error at frame N, allowing VLA to freely infer from N onward). Switch from force-based injection to a behavioral error skill module (EEF motion/gripper control), with each error type processed independently for detection/insertion/verification.#

Key Insight: The VLA model is dependent on time context — initialization using error states alone is insufficient. Errors must “naturally” emerge from correct trajectories. Offline scanning + quota method effectively balances datasets while maintaining temporal realism.

2. Coordinate misalignment in MIHD spatial transcriptomics patch query visualization — the query patch does not match the expected spatial location.#

Solution: Three root causes were identified: (1) Data loading mismatch between datasets/DLPFC/paths and top-level paths; (2) Position-based allocation lacks barcode mapping (the cache order after scanpy operation does not match data loading order); (3) Using cached coordinates instead of data.obsm[‘spatial’] for marker overlay. These issues are resolved by using consistent paths and a bc_to_cache_idx dictionary for clear barcode alignment, along with coordinate lookup based on barcodes.

Key Insight: The spatial transcriptomics workflow requires clear barcode alignment at each node (cache → load → render) — implicit position matching fails when data is reloaded from different sources or reordered by scanpy. Never assume index preservation between file I/O boundaries.

3. Significant fluctuations in Robobrain Pi training loss — suspected to be a dimension processing issue in action prediction.#

Solution: Deep analysis revealed that the 14-dimensional real actions (right arm 6DOF + gripper + left arm 6DOF + gripper) were padded to 32 dimensions for model architecture compatibility, but MSE loss was calculated across all 32 dimensions. This means 56% of the loss (18/32) comes from zero-padded dimensions, and the model learns trivial noise-to-zero mappings in these dimensions, severely diluting gradient signals. Recommendation: action_loss = mean(square(v_t[…, :14] - u_t[…, :14]))

Key Insight: Zero-padding for architecture compatibility heavily dilutes gradient signals during loss calculation — always map loss to actual dimensions. In this case, 56% of the gradient signal is wasted learning trivial mappings. This is a subtle but critical error affecting training efficiency.

4. The STAIGTrainerE2E.py file was deleted, but still referenced in Fusion.py and pipeline_config.yaml, causing an ImportError when calling staig_fusion_e2e strategy in MIHD pipeline.#

Solution: Users chose the strategy of “cleaning up all references”. staig_fusion_e2e was removed from Fusion.py, pipeline_config.yaml, data_preparer.py, pipeline run program, STAIGutils, MEMORY.md, and 8 other files. Six README errors in dimensions/descriptions found during audit were also fixed.

Key Insight: Isolated references are a major error in production. A systematic grep audit is necessary before deleting files. Automated import testing could detect these errors earlier. A parallel exploration proxy-based code-document consistency audit successfully identified 1 serious error and 6 moderate differences.

5. RoboTwin dataset conversion always uses the first instruction in JSON, reducing training diversity of language-conditioning strategies.#

Solution: Replace instruction_data.get(‘seen’, [’’])[0] with np.random.choice(seen_instructions) so each set randomly selects an instruction, consistent with the reference implementation convert_aloha_data_to_lerobot_robotwin.py.

Key Insight: Dataset conversion should be enhanced at the source level — random selection of instructions per set increases training diversity without multiple dataset versions, directly affecting the model’s generalization to instruction interpretations. This is a simple change but has a major impact on training performance.

6. The Robobrain Pi task completion binary classifier may learn trivial “always predict 0” solutions, even though task_loss_weight is 0.1.#

Solution: Root cause: severe class imbalance (only about 200 frames at the last frame are positive, ratio 9:1) plus task_pos_weight=1.0 (no balancing). Solution requires independently adjusting two hyperparameters: keep task_loss_weight=0.1–0.15 (to prevent auxiliary task overwhelming 50-step action prediction) but increase task_pos_weight to 5.0 (by giving sufficient gradient signals to the positive class per category).

Key Insight: For unbalanced auxiliary classification, class weighting is more effective than overall loss scaling when the task should not dominate the main goal. loss_weight and pos_weight serve different purposes: loss_weight balances task importance, pos_weight balances category contributions within the task. They must be adjusted independently.

7. The Node.js ccusage tool cannot obtain the latest model price information from LiteLLM (1.4MB JSON), instead falling back to 46 cached models rather than 2696 models.#

Solution: Hierarchical testing identified the issue: (1) Downloading 1.4MB data via the campus proxy takes 28 seconds; (2) Node.js’ get function shows “getaddrinfo EBUSY” hostname resolution failure; (3) It was found that Node.js v24’s built-in get function (undici) does not follow HTTPS_PROXY environment variable by default. Solution: NODE_OPTIONS="–use-env-proxy" npx ccusage@latest

Key Insight: Node.js v24’s get function is fundamentally different from traditional HTTP clients (curl/axios/requests) — it ignores environment proxy variables by default. This is a compatibility trap; the –use-env-proxy flag or a global proxy library must be used explicitly. This is crucial for limited network environments.

9. Kubernetes container nvidia-smi shows all GPU processes as [not found], even though GPUs are actively used** Solution: Root cause: PID namespace isolation. nvidia-smi returns host PID (e.g., 3076643) when querying kernel drivers, but containers have different numeric PID namespace numbers (e.g., 990465). Solution: The gpumon.py tool was developed, combining psutil (reading /proc files inside containers for process information: CPU/memory/command line/time elapsed) and nvidia-smi (GPU hardware status: memory/usage/temperature) for rich visualization via a user-friendly interface.#

Key Insight: Container namespace isolation breaks the mapping between process IDs across namespaces. The tool must collect information from each namespace and summarize it. This is why standard monitoring tools fail in containerized environments — they assume PID spaces are unified.

10. Openpi-moe serve_policy.py errors, indicating “MUJOCO_EGL_DEVICE_ID must be between 0 and 0, but actually gets 6”.#

Solution: CUDA_VISIBLE_DEVICES=6 limits the process to using only GPU 0 as device 0, but EGL renderer tries to use the original hardware index 6. Add os.environ.setdefault(‘MUJOCO_EGL_DEVICE_ID’, ‘0’) at script startup to align with CUDA’s remapping.

Key Insight: CUDA_VISIBLE_DEVICES remaps GPU indices to the range 0–N for isolated processes; dependent libraries (e.g., MuJoCo EGL, rendering context) must use the remapped index instead of the original hardware ID. This is a subtle but important interaction between CUDA device isolation and rendering frameworks. When using CUDA_VISIBLE_DEVICES and a single GPU, always set the rendering device ID to 0.

11. Although install.sh completes successfully, the CALVIN calvin_agent module still cannot be found.#

Solution: It was found that pip installation occurred in a different conda environment from the current univla environment. Editable installs create an .egg-info directory, but package availability is limited to the Python environment where the install was executed. Reinstall in the correct environment using pip install -e . –no-deps to avoid overriding PyTorch.

Key Insight: Editable pip installations are environment-dependent — there may be issues, but if installed elsewhere, imports will fail. Before investigating missing modules, verify that ‘which python’ matches the expected environment. The –no-deps flag allows installing package structures without affecting existing dependencies.

Lessons Learned#

Key Experience – VLA model requires redesigning benchmark tests for time context dependence: Cannot simply initialize episodes with error states — VLA needs behavioral history to make appropriate recovery decisions. Solution: replay the first N-1 frames to build a context window, introduce error at frame N, then let VLA infer freely from frame N onward. This transforms the way error is introduced from “initial state perturbation” to “trajectory interruption”, matching how errors occur in real-world scenarios.- Offline scanning and quota scheduling architecture for balancing error datasets: Stage 0 collects clean trajectories (human data and 10 times more running data than VLA strategy success) → Stage 1 performs offline scanning per frame → Stage 2 assigns quotas (100 quotas per task × error category) → Stage 3 performs context replay. This approach is more efficient than online generation, ensures dataset balance, and allows reuse of expensive clean trajectory data in multiple error injection experiments.#

  • Deformed dimension classification for error classification: D0 (only position), D1 (only rotation), D2 (position + rotation) systematically describes the spatial deformation of all error types. This classification method is more systematic than stage-based classification (such as arrival/grasping/raise/transport/placement), and by decomposing the 6 degrees of freedom changes into orthogonal components, the verification logic becomes clearer.
  • Architecture compatibility issues caused by zero padding: Padding (from 14 dimensions to 32 dimensions) for model compatibility may severely dilute gradient signals (wasting 56% of the signal). Therefore, only meaningful dimensions should be retained for loss calculation. In multi-dimensional outputs, this is subtle but crucial—if included in the calculation, although the model can converge, the learning performance will be poor because most gradient signals optimize trivial zero-to-zero mappings.
  • Independent hyperparameter tuning for unbalanced auxiliary tasks: loss_weight is used to balance task importance, while pos_weight balances category contributions within the task, and these two parameters need separate tuning. For severely unbalanced auxiliary classification tasks, keep loss_weight low (0.1–0.15) to avoid excessive impact on the main goal; simultaneously increase pos_weight (e.g., 5.0) to address category imbalance. Overall scalability and class weight allocation are independent control factors.
  • Alignment requirements based on spatial transcriptome barcodes: A clear barcode mapping is required at each process node (cache → load → render). When data is reloaded from different sources or reordered via scanpy operations, position-based matching fails. Never assume that the indices between file I/O boundaries remain unchanged. Solution: maintain a bc_to_cache_idx dictionary throughout the process and use barcodes for coordinate assignment.
  • In-depth understanding of MIHD architecture: Three-stage process (encoder → fusion → clustering/ evaluation), 5 gene encoders (PCA 50d, MLP 128d random initialization, scGPT 512d, GCN 50d, none), 4 visual encoders (ResNet50, HIPT, UNI, UNI2), 10 fusion strategies (series/mean/element sum + attention variants + STAIG/QFormer). Divided into two stages: Stage 1 extraction (cache to embedding cache), Stage 2 evaluation (load + fusion + clustering + metrics).
  • Conversion and enhancement of datasets at the source level: Random sampling instructions per set (selected from available interpretations) increase training diversity without needing multiple dataset versions. This simple change has a significant impact on the generalization ability of language conditional strategies. This indicates that matching patterns with reference implementations in the same code base is very important.
  • Remapping of CUDA_VISIBLE_DEVICES GPU indices: Limit indices to the range 0–N so that processing occurs within the CUDA context. Dependent libraries (such as MuJoCo EGL, rendering frameworks) must use the remapped indices instead of the original hardware ID. When using single-GPU isolation, always set the rendering device ID to 0. This is subtle but critical for multi-GPU setups because different jobs run on different isolated devices.
  • Applicability of injection vs. natural capture: Physically-based injection methods (pulse/friction/pose perturbation) can reliably generate 7 types of errors (falling, collision, positioning, partial stagnation). GRASP_FAILURE/sequence/trajectory/regression errors require temporal behavior of the strategy—only natural capture can produce these errors. Therefore, a hybrid approach is needed to fully cover error types.
