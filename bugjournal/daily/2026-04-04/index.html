Problems & Solutions#

Critical Issues#

1. FloatBall window remains at 400x400 under Linux, Tauri set_size() is completely ineffective#

Solution: GTK bottom-up size negotiation takes max(window_requested, widget_natural_size), andWebKitGTK natural size ≈200x200 causes the window to lock up. Fix: called widget.set_size_request() via with_webview() in the GTK main thread, removed set_resizable toggle (with_webview is asynchronous, set_resizable(false) queued before callback execution and would lock the old size), making Linux permanently resizable.

Key Insight: Tauri’s set_size/set_min_size/set_max_size use GTK window-level hints, and GTK bottom-up negotiation ignores these hints to satisfy widget natural size. The callback from with_webview() is not executed yet, so subsequent Tauri API calls remain FIFO asynchronous queues.

2. Visual jump during Linux collapse: two-stage sequence exposes intermediate state + old WM clamp width causes systematic coordinate offset#

Solution: Two-stage sequence: macOS has a 250ms animation buffer, after disabling transitions on Linux the intermediate state is harsh, so changed the Linux path to first Rust atomic window shrink to 56px, then set CSS expanded=false (now 100% = 56px, no change visible). WM clamp issue: GTK gravity does not apply in this WM (instead introducing systematic offset), probe + corrective reapply causes double-frame flicker; the fundamental solution is a fixed large-size window + internal CSS (pending implementation).

3. Life-Copilot MCP Server three-layer breakdown: There is a Calendar token but the agent still reports unable to connect#

Solution: Three places simultaneously broken: FastMCP is only instantiated without calling run(), .claude/mcp_servers.json is missing, and butler commands (including MCP tools list) never reach the Claude CLI subprocess. Create main.py to start stdio transport, create mcp_servers.json, add –append-system-prompt to ClaudeAdapter, and all 19 MCP tools return normal.

4. Initial solution for Linux Screen Time Tracker uses xdotool, does not support Wayland (user machine runs GNOME 50 Wayland)#

Solution: Feasibility testing confirms a Wayland environment, so use GNOME Introspect D-Bus (org.gnome.Shell.Introspect.GetWindows()) as the main path, xprop as a fallback for XWayland, and PID→cmdline as the final fallback. All subprocess calls add a 5-second timeout + proc.kill().

Key Insight: GNOME 41+ provides a standard Introspect D-Bus interface, which is the correct way to obtain active windows under Wayland; this issue is addressed by the Critic sub-agent for active discovery, and omission would result in complete functionality failure on the user machine.

5. AionUI cannot connect to Claude Code CLI on remote headless server via URL or SSH#

Solution: The AionUI remote Agent architecture assumes the Agent exposes an HTTP port, while the CLI process has no HTTP endpoint, making them fundamentally incompatible. It is recommended to use tmux/screen for multi-session management as a temporary alternative, and submit a feature request to the AionUI team.

Key Insight: The AionUI database already has a remote_agents table (with the allow_insecure field), indicating that the development team is building remote Agent capabilities. SSH direct connection might be a future roadmap direction.

6. X11 WM refuses half-screen window positioning, causing吸附 and collapse position drift#

Solution: X11 WMs such as Mutter/GNOME insert non-decorated windows into the visible area, refusing positioning with x < 0 or x > screen_width - window_width. Linux uses edge_offset=0, while macOS/Windows use edge_offset=ball_size/2.

Key Insight: macOS and Windows allow non-decorated windows to partially exceed the screen border, whereas X11 WMs usually do not; both platforms require different edge offsets.

7. ClaudeCLIAdapter.is_available() lacks async, causing Claude to silently downgrade to Codex and timeout#

Solution: await of a regular method does not cause a compilation error, but the TypeError during runtime is swallowed by except Exception, making Claude considered unavailable. Adding the async keyword restores Claude available: True.

Key Insight: Await of a synchronous method in Python generates TypeError; if silently caught by except Exception, it leads to a false negative result due to logical errors, appearing as a functionality downgrade rather than an error report, making it very difficult to troubleshoot.

8. Bot cannot understand cross-turn references during multiple rounds of conversation (DualVerifier parameter wiring broken)#

Solution: DualVerifier, SemanticRouter, and KeywordScorer all implement the last_assistant_message and last_intent parameters, but _process_input() calls never pass them. Fixing the wiring is sufficient; no classification logic needs to be changed.

Key Insight: “Parameter interface for functionality implemented” does not mean “parameters are passed”; the integration layer is the most common wiring break point. Verification should check the calling side rather than just the implementation side.

9. Bug exists in Codex CLI session resume, with significant differences among three CLI sessions mechanisms#

Solution: Abandon relying on native CLI session, maintain a lightweight history ring buffer (last-20 entries) at the Adapter layer, inject history as a prompt prefix when switching CLI, to achieve transparent cross-CLI conversation history transfer.

Key Insight: Unified abstraction layer (history injection) is more reliable than adapting different CLI session mechanisms; inconsistency in session mechanisms is the main risk of multi-CLI architecture.

10. lark-oapi WebSocket client runs阻塞ly, cannot share the same main loop as FastAPI asyncio#

Solution: Start the Lark bot in a separate daemon thread, and use asyncio.run_coroutine_threadsafe() to bridge message callbacks to the main event loop.

Key Insight: Client.start() of lark-oapi v1.5.3 is essentially synchronous and blocking; thread isolation is required instead of directly await in asyncio tasks; this issue was discovered by the Critic agent for active review.

11. ScrolledWindow scroll bars in WebKitGTK cannot be suppressed with CSS#

Solution: WebKitGTK scroll bars belong to the gtk::ScrolledWindow layer rather than the WebKit rendering tree; CSS pseudo-elements cannot reach them. Traverse the widget ancestry chain in the with_webview callback, and call set_policy(Never, Never) for each ScrolledWindow.

Key Insight: The UI chrome of WebKitGTK belongs to the GTK widget layer; CSS selectors cannot be selected, so it must be handled at the GTK code level.

AI Limitations#

Critical Limitations#

  • When there is no runtime evidence, incorrect assumptions about how underlying APIs (Tauri set_size, GTK gravity, Google Calendar calendarList scope) work as expected cannot be corrected without log evidence or user error reports; multiple fixes of geometric algorithms were applied without questioning whether the underlying OS mechanism actually works.
  • After multiple rounds of fixing failed, it did not actively recognize that “continuing to fix does not resolve architectural issues”; each time new logs appeared, the AI continued trying a new technical solution, and only when the user explicitly requested it to stop did the AI summarize the root cause.
  • No verification was done before introducing new mechanisms to confirm platform support: GTK gravity was not confirmed whether the WM supported it (the introduction actually caused systematic offsets); the transparent safe margin solution immediately caused two issues: dragging and WM clamp, which were not predicted before modification.
  • Incomplete perception of global dependency graphs for large code libraries: the ccplan Critic agent identified 4 hidden dependencies omitted during AI planning (BackgroundCoordinator, slash command, etc.); concurrent/race fixes easily missed boundary cases (scenarios triggered by pointerUp before asynchronous initialization required questioning to discover).
  • Providing outdated or fabricated information in rapidly evolving products: the /model and /effort slashes for AionUI were fabricated (failed after user verification), and the Claude 200k context window was stated in a definitive tone (actually 1M), but not updated technical parameters that change quickly should be stated in this way.
  • Restrictions on external API calls to toolchains (OpenReview 403, lark-oapi thread blocking, Codex session bugs) could not be predicted during planning; they had to be observed in practice or reviewed by Critic to discover; no work alternatives for the OpenReview authentication wall could be provided actively.

General Limitations#

  • Dispersed investigation paths: when dealing with multi-layer breakdowns (calendar connection issues, Discord context anomalies), efforts were made separately for each isolated symptom, failing to quickly locate the root cause at the architecture level; multiple tool calls were required before a conclusion was reached.

Learnings#

Key Learnings#

  • Full picture of GTK window size control mechanism: GTK bottom-up negotiation takes max(window_requested, widget_natural_size); WebKitGTK natural size ≈200x200 logical, so calling widget.set_size_request() is not necessary; Tauri’s set_size/set_min_size/set_max_size do not work on WebKitGTK windows; with_webview() is asynchronous, and subsequent Tauri API calls are queued before the callback execution, which may lock the old size under FIFO; WebKitGTK scroll bars belong to the GTK widget layer, so set_policy(Never, Never) must be used in GTK code to disable them.
  • Architectural constraints of Linux transparent borderless Tauri/WebKitGTK floating windows: the sizes and positions of the WM, GTK, and WebView content areas do not automatically sync; this is a platform constraint, not a bug. The correct architecture should be a fixed large-native window + internal pure CSS expand/collapse, without relying on frequent resize of the outer window; GTK gravity is not supported by all WMs, and moving using the right boundary coordinates causes systematic offsets; probe + corrective reapply cannot eliminate visible transition frames for users; separating visible rect and window rect at the native coordinate level may cause dragging start points and mouse drift.
  • Runtime logs are the fundamental means of debugging underlying systems: when underlying system behaviors such as GTK, WM, and OS occur, assumptions should be confirmed through logs/probes rather than inferred from code; cross-platform animation strategies must be consistent; disabling CSS transitions must synchronize the corresponding JS/Rust timing logic; X11 WM forces decorated windows into the visible area (edge_offset varies by platform), while macOS/Windows allow half-screen visibility.
  • NeurIPS D&B Track submission strategy: “domain correctors” (by quantifying specific defects in existing benchmarks, such as a 57% accuracy rate, triggering a reconfiguration of the evaluation paradigm) are more accepted and have greater lasting impact than “new method proposers”; reviewers value multi-dimensional evaluation, fair baseline comparisons, manual verification mechanisms (κ≥0.68), and counterintuitive negative findings; counterfactual entity substitution can eliminate word overlap bias; symbolic verification closed loops (SPARQL/SQL comparison + N automatic fixes) can increase data accuracy from 57% to 96%+; data cleaning can be重构 into unsupervised anomaly detection (Isolation Forest + Z-score cross-language standardization).
  • Radical simplification (replacing engines) is often more effective than incremental fixes: the Thin Adapter + MCP Server + Skills three-layer model replaces proprietary routing logic, achieving cross-cli universality; large-scale refactoring should be subject to adversarial review (Critic subagent) before coding, which can detect hidden dependencies and architectural risks in advance. In today’s multiple projects, the Critic stage identified high-value issues such as Wayland compatibility, lark-oapi thread blocking, ThoughtStore not being singleton, and 4 hidden code dependencies, with high ROI.
  • “Implemented parameter interfaces” do not mean “parameters have been passed”: the integration layer is the most common connection break point; verification should focus on the calling side rather than just the implementation side; FastMCP’s “create” and “serve” are two steps, and mcp_servers.json must be declared to detect external programs; TypeError in Python await synchronous methods if swallowed by except Exception causes silent degradation of functionality instead of an error report.
  • Modern Linux desktops (Ubuntu 22.04+) already use Wayland by default; cross-platform window tracking should rely on GNOME Introspect D-Bus as the main path, and xdotool/xprop can only serve as a XWayland fallback; background sampling tasks should not rely entirely on CronScheduler (minimum tick 60s), and task applications using independent asyncio.Task loops are needed; ECL documentation structures design decisions persistently, which is a key engineering practice for multi-stage complex feature development.
  • Best practices for multi-cli system design: different CLI tools (Claude Code/Codex/Gemini) have their own convention instruction files (CLAUDE.md/AGENTS.md/GEMINI.md); using convention files is simpler and more reliable than runtime injection; Skills are essentially Markdown prompt templates, and cross-platform migration only requires tool name mapping; App state verification and CLI tool context injection are two independent layers; token verification passing does not mean the CLI tool received the correct context; a unified history ring buffer is more reliable than adapting to each CLI session mechanism.
  • AionUI remote agents only support URL connections (the CLI process has no HTTP endpoint, which is a fundamental architectural limitation), but AionUI’s database already has a remote_agents table; SSH direct connection may be part of the future roadmap; AI should not state technical parameters (commands, model specifications) in a definitive tone in rapidly evolving products; it should declare the knowledge cutoff time and suggest user verification.
  • Correct architecture for lark-oapi WebSocket: Client.start() is blocking, so an independent daemon thread + asyncio.run_coroutine_threadsafe() must be used to bridge it; Google Calendar OAuth scope is finely divided; verification uses token to call events.list(calendarId=‘primary’) instead of calendarList.list(); log level is a zero-cost observability lever; changing provider errors from DEBUG to WARNING immediately improves operational experience.
