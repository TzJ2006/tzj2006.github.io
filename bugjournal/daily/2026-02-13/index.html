Issues and Solutions#

Key Issues#

1. The error recovery robot never approached objects during replay (minimum distance is 0.22 m, requiring contact for the task)#

Solution: Thoroughly analyzed robosuite source code, HDF5 metadata, and MuJoCo body mapping relationships; it was found that the replay using PickPlace_D0+controller_configs recorded in PickPlace actually uses pure PickPlace. The same operation produces a completely different trajectory.

Key Insight: Environmental configuration (kp, damping coefficient, ramp_ratio in controller_configs) fundamentally changes the robot’s dynamics. Replaying using environment metadata fully matching the HDF5 dataset—parameter adjustment can hide the root problem.#### 2. There is a conflict between CalendarPro’s semantic router and the LLM, causing the system to always use SR, resulting in incorrect routing (for example, the “leetcode” keyword → using manage_recurring instead of update).Solution: dual_verify.py was modified to prioritize LLM intent when mismatches occur. The LLM possesses a complete conversation context, while SR only matches keywords. The log shows “→Using LLM intent” for monitoring.

Key Insight: The classifier based on keywords fails when handling ambiguous expressions. When semantic routers and LLM opinions disagree, the model supported by context (LLM) should be trusted instead of the faster model (SR). SR filters obvious cases, while LLM acts as an arbiter.

3. Missing data in the 4 parts of MIHD causes pipeline failure (missing spatial files, empty region in frequency filter, STAIG model crash)#

Solution: Spatial files were extracted from Dataset.zip; boundary checks (min_w/min_h >= 10) were added; a fallback mechanism to mclust for KMeans was introduced, and processing was done using try/except wrappers.

Key Insight: Spatial transcriptomics data requires strong fault tolerance: multi-path candidate search, image processing boundary checks, statistical model fallback strategies to handle distribution anomalies.

4. The original single-step workflow of gadget cannot support multi-device collaboration (log must be manually copied to each device) Solution: Reconstructed into a two-stage process: (1) Export sub-commands to generate local JSON logs containing device information (no API key required); (2) Combine sub-commands, aggregate multiple logs, and call the API to generate the final report; the old mode is retained for backward compatibility.#

Key Insight: Multi-device workflows require a portable intermediate format (versioned JSON logs) and clear stage division (local parsing and remote merging). Key design includes: device information collection, version support designed for future expansion, optional device summaries to prevent information loss during merging.

5. After adding adjacent gating, all error detectors failed—iterative threshold adjustments (0.05→0.15→0.25→0.30 meters) did not produce any trigger signals#

Solution: A diagnostic script was written to measure the distances between actual EEF objects, revealing that the issue was environmental mismatch rather than threshold problems. The root cause was the replay configuration problem, not detector sensitivity issues.

Key Insight: When all detectors fail, real conditions should be measured via diagnostic log records before adjusting thresholds. Symptoms without trigger signals often hide fundamental mismatches (e.g., incorrect controller dynamics).

6. CalendarPro calendar API errors (403 permission insufficient, HttpError) are captured via print() and returned as None, causing users to receive a generic “failed” message and causing confusion#

Solution: A CalendarServiceError exception was created; all calendar_service methods were refactored to provide detailed context information when errors occur; all callers were updated to capture and display user-friendly messages containing technical details.

Key Insight: Silent error handling (print + returning None) violates the contract of error handling. Users cannot fix issues they cannot see. Errors with context should always be passed to the presentation layer and properly formatted.

7. CalendarPro AI provider lacks a timeout mechanism—network pause may cause the entire robot to freeze indefinitely#

Solution: All API calls were wrapped with asyncio.wait_for(timeout=30.0), and httpx.Timeout(30.0) was added to the client constructor. When the timeout occurs, an AIResponse with error fields is returned.

Key Insight: Timeout protection requires dual layers: asyncio coroutine level (wait_for) and HTTP client level (httpx.Timeout) to capture different failure modes.

8. When AI returns prose, multiple blocks, or truncated JSON before JSON, CalendarPro’s JSON parsing fails—leading to intent classification crashes#

Solution: The_extract_json() function was implemented to extract the first complete object by balancing bracket counts; a three-stage fallback mechanism (direct parsing → trailing comma correction → general intent) was added; ValueError exceptions for logging and fallback were removed.

Key Insight: Production-grade AI systems need graceful degradation—they must not crash for malformed output, and safe fallback intents should always be provided.

9. The planning document lacks self-containedness—users repeatedly reject ExitPlanMode, demanding “writing every sentence of the plan into the plan file”#

Solution: The planning document was rewritten to be fully self-contained: user decision records, code snapshots with exact line numbers, QueST reference code details, and complete implementation code were added; each stage had a “inserted after line X” location.

Key Insight: The planning mode document must be fully self-contained so that sessions can be restored later. Users’ rejections indicate insufficient document details—all exploration results (exact positions, line numbers, function signatures, existing code) need to be written into the plan instead of relying on external context.

10. MuJoCo’s speed switching causes false instability triggers (angular velocity is misread as linear)#

Solution: Array slicing was exchanged: linvel = cvel[3:], angvel = cvel[:3] to match MuJoCo’s [angular velocity(3), linear velocity(3)] layout.

Key Insight: Documentation and code do not match: code comments claim [linear, angular velocity], but MuJoCo stores [angular velocity, linear velocity]. Always verify based on the source document rather than inline comments.

11. The CLAUDE.md file has 615 lines, with many repetitions between sections, and some content belongs to the README file#

Solution: The documentation was rewritten, focusing on: (1) inconspicuous information (server limits, common pitfalls); (2) integrating commands into a single block; (3) removing easily identifiable content (file tree, method signatures); (4) retaining only architectures that require multi-file reading.

Key Insight: Documentation for AI agents should focus on content that cannot be discovered via tools, rather than a comprehensive reference. Simplicity improves usability—101 lines vs. 615 lines make it clearer.

12. When CalendarPro updates duplicate events, it modifies the entire series instead of individual instances, even though singleEvents=True is used during search#

Solution: update_event() was modified to detect duplicate instances (with recurringEventId) and remove duplicate/recurringEventId before calling the API. Google Calendar creates a separate exception for such instances.

Key Insight: The implicit behavior of Google Calendar API: singleEvents=True during search provides instance IDs, but updates/removals require explicit removal of relevant fields to avoid modifying the entire series. Duplicate operations should always be tested on a test calendar.

13. CalendarPro’s asyncio.create_task() used for the message queue has no exception handling callback—tasks may terminate silently when the queue is full, and user messages will never be processed#

Solution: done_callback=_on_queue_task_done was added to all create_task calls; a cleanup handler was implemented to log exceptions and remove dead tasks; a close() method was added for closing.

Key Insight: asyncio background tasks are “forgotten” by default, so done callbacks must always be added for monitoring/cleanup, especially long-term tasks.

General Issues#

14. Manually querying token usage is cumbersome—users want automatic daily statistics#

Solution: ccusage@latest daily –json was called via a sub-process to integrate ccusage, and output was parsed; automatic collection was performed at all three entry points; a total table and model details were displayed in the token usage section; data was merged across devices.

Key Insight: Automate data collection by leveraging existing tools instead of re-implementing. Design considerations include: fault tolerance of sub-processes (silent skip if unavailable), multi-device aggregation strategy (summing tokens/costs, merging model details), and readable presentation (tables > lists).

15. MIHD GPU peak statistics always show zero (ResourceMonitor never calls update_peak_stats())#

Solution: ResourceMonitor was refactored: start_monitoring() started a daemon thread that samples every second, stop_monitoring() terminated the thread and sampled the final peak, and threading.Event lifecycle control was added.

Key Insight: Monitoring peak statistics requires continuous sampling during operation, not just start/stop snapshots. Background daemon threads are a standard solution, but proper lifecycle management is needed to avoid resource leaks.

16. The gadget test/catalog is a nested Git repository with its own remote address, causing nested repository conflicts during git add operations#

Solution: Git submodules were used: the test folder was moved to a backup location, ‘git submodule add git@github.com:TzJ2006/test.git test’ was run for cloning, the backup was removed, and .gitmodules automatically recorded the configuration. Key Insight: Git submodules are suitable for nested repositories with independent remote repositories. Key point: submodules record commit hashes rather than branches; git submodule update --init --recursive is required during cloning; when updating, the directory must be entered in the submodule and git pull must be executed, then the commit hash is modified.

17. CalendarPro’s start.bat cannot detect conda environments (cmd does not support ‘conda activate’ without conda init, CONDA_PREFIX is unavailable in new cmd windows)#

Solution: A start.ps1 script that supports native PowerShell conda functions was created; PowerShell can directly execute ‘conda activate calendarpro’. start.bat was updated to allow calling PowerShell under -ExecutionPolicy Bypass; PID tracking and stop.ps1 were added.

Key Insight: Windows batch files perform poorly in conda integration. For conda workflows on Windows, PowerShell is a better choice. Always test environment activation in a new shell, rather than using inherited conda sessions.

18. CalendarPro’s simulation patch failed because generate_with_fallback was imported inside the method, not at the module level#

Solution: The patch target was changed from ‘src.thoughts.thought_organizer.generate_with_fallback’ to ‘src.aiProvider_selector.generate_with_fallback’, so the patch could be applied in the source module.

Key Insight: During simulation, patches should act on the function definition location, not the import location—local imports create new references, thus bypassing the module-level patch.

19. After creating test_thoughts.py, pytest async tests for CalendarPro reported ‘coroutine never awaited’ warnings#

Solution: The pytest-asyncio package was installed, which can automatically detect async test functions and run them in the event loop.

Key Insight: pytest itself does not support async tests—the pytest-asyncio plugin must be installed in pyproject.toml dependencies.

Difference Analysis: Humans use structured root cause analysis (comparison between recording and replay environments), while AI gradually adjusts parameters. Humans consider threshold expansion as a real problem; AI treats it as a solution.

Practical learning outcomes#

  • Automate data collection using existing tools (ccusage) instead of re-implementing. Design considerations: subprocess fault tolerance (silent skip after failure), multi-device aggregation strategy (summation/merging), easy-to-read presentation format (tables>lists)
  • Use cases and management of Git submodules: suitable for independent remote sub-projects, record commit hash instead of branch, clone requires –recursive, update requires cd + git pull + commit hash change
  • Monitoring peak statistics requires continuous sampling during operation (background thread), not just startup/stop snapshots. Requires appropriate thread lifecycle management (event mechanism) to avoid resource leaks

  • Semantics of cluster file system: shared storage means same path between nodes, but SSH sessions default to home directory — always explicitly execute cd operation in remote commands
