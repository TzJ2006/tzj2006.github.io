Issues and Solutions#

Key Issues#

1. Post-fusion Harmony alignment improved batch mixing metrics but reduced the quality of cross-sample expertise retrieval#

Solution: After analysis, it was concluded that Harmony’s linear correction cannot handle non-linear dimensional meanings, leading to inconsistency in independent training of each part. It is recommended to use Joint STAIG multi-part training in the next iteration.Key Insight: Batch correction methods like Harmony assume a linear offset, but this correction fails when embeddings trained independently have inaccurate dimension semantics—batch mixing and semantic alignment are distinct properties. Linear correction on individually trained embeddings cannot maintain semantic consistency across samples.

2. CalendarPro can only handle a single intent per message, thus losing subsequent operations, such as “scheduling a meeting at 3 PM and changing dinner time to 7 PM”#

Solution: The dual validation process for a single intent was replaced by the Claude CLI MultiIntentAnalyzer, which returns a list of intents. The _process_message_queue function was updated to loop through intents and combine responses. The 7-layer keyword coverage system was removed.

Key Insight: Single-intent classification is a fundamental architectural limitation, not a parsing issue. Keyword techniques (always generic, dependent on context, 7-layer coverage) are symptoms of chaotic abstraction levels. Switching to native multi-intent processing in LLMs can eliminate all heuristic methods.

3. MimicGen enhancement failed: pos_delta was calculated but never applied to action deformation, resulting in a success rate below 5%#

Solution: replay_with_warping was fixed—pos_delta was applied to warped_actions[:, :3] before adding noise, achieving correct object-centered trajectory transformation. The expected success rate is above 50% when there are D0 translation errors.

Key Insight: MimicGen enhancement requires actual coordinate transformation, not just noise injection. The path from 10 to 1000 depends on: 10 seeds × 200 targets × 50% success rate = 1000 demonstrations. Without pos_delta correction, the success rate drops sharply.

4. Yuke Zhu’s initial deep-width analysis using a single 5MB prompt (100 full papers) far exceeds the processing capacity of LLMs, leading to failure#

Solution: A three-layer solution was implemented: (1) a threshold of _MAX_PROMPT_CHARS=150K was added to automatically trigger segmentation; (2) a greedy algorithm grouped by year and segmented per paper was used to process papers within a year; (3) an LLM was used to combine 47 analyses into a complete report.

Key Insight: The key to ultra-large text analysis is “segmentation + semantic merging”: technically, dynamic segmentation can control the burden on a single LLM, while cognitively, it guides the LLM to extract consistency across paragraphs rather than simply connecting via merged prompts. 150K characters correspond to about 15–20 medium-length papers—this is the empirically optimal point.

5. The task completion model training stagnated with a loss of approximately 0.035, despite grad_norm=0.7–1.0 and a positive sample ratio of 4% and a negative sample ratio of 96%#

Solution: Positive sample weighting (pos_weight=10) was applied to the BCE loss to balance gradient contributions, effectively increasing the positive sample ratio from 4% to about 30%.

Key Insight: Under low loss conditions, a good positive sample recall rate in an imbalanced dataset does not guarantee success. Focusing only on gradient magnitude is misleading because negative samples dominate. Class imbalance requires explicit gradient balance.

6. CalendarPro returns a “no events today” query result immediately after creating an event, applicable for queries “this week” and “tomorrow”#

Solution: A three-layer solution was adopted: (1) query intent classification was added to BASE_SYSTEM_PROMPT (not just INTENT_PROMPT_FRAGMENTS for multi_intent.py); (2)_handle_query() added keyword fallback detection to handle LLM failures; (3) get_today_events() was fixed to display already started events in get_today_events(); (4)_DPending_warnings was added for Discord error feedback.

Key Insight: INTENT_PROMPT_FRAGMENTS and BASE_SYSTEM_PROMPT serve different code paths—main LLM classification uses BASE_SYSTEM_PROMPT. Keyword fallback is a reliable LLM safety net. Past events must remain visible to prevent re-creation.

7. The code repository contains 8 fully implemented modules (about 2400 lines of code), all of which have comprehensive tests, but they are not imported at runtime, creating maintenance burden#

Solution: A systematic four-stage refactoring was adopted: (1) all import statements were mapped and isolated modules identified; (2) unused modules were archived with a README; (3) duplicate modules were merged into the specification location; (4) truly useless code was removed. All passed 373 tests.

Key Insight: For full implementations, archiving and removal should be used. Isolated but still usable code is saved in archive/ with relevant context for future integration. Audits found misconfigurations and import errors.

8. Due to always failing checks, duplicate dining events were repeatedly created (19 breakfast, 19 lunch, 18 dinner)#

Solution: The priority in _check_meal_exists was changed from start_time (displaying “08:00”) to start_iso field (ISO date and time). schedule_essentials function was changed to get_today_events(include_past=True) so already started dining events remain visible.

Key Insight: Field parsing order is crucial—ISO-form fields should always be processed first to avoid silent parsing failures. Past events must remain visible to prevent re-creation.

9. The finalization mechanism of the toolset caused a deadlock: historical log files with _finalized=False persisted permanently, making report._finalized never true, leading to sync-all continuously calling the LLM merge and wasting API costs#

Solution: The root cause was identified: a two-stage finalization mechanism (log + report) requires marking the report complete only after all source logs are finalized. Only when target_date != today() AND conversation_count unchanged does the export setting _finalized=True occur. The reason historical logs remain False is: (a) exported once only at target_date == today(), thus False; (b) after the first export, the number of conversations changes, resulting in False. _finalized flag is embedded in JSON content and synchronized via rclone. Solution: re-export on affected devices—since the date has passed and the number of conversations is stable, it will automatically be marked True. Another method is manually editing _finalized in JSON to True and uploading via rclone.

Key Insight: The two-stage finalization mechanism requires all source data to be finalized before the report is marked; _finalized flag in JSON content is synchronized via rclone to ensure cross-device consistency; however, historical False entries cause permanent deadlock. The core value is saving LLM API costs (merge stage), not rclone download time. Re-exporting via “data repair” respects the existing architecture better than “logical change,” which would disrupt consistency.

10. When using a block size of 60K for the first time, 100 papers were divided into 102 blocks (almost one paper per block), leading to excessive LLM calls and lack of context per paper#

Solution: The block size was increased from 60K to 150K, and the segmentation logic was adjusted to prioritize year integrity. The number of blocks was reduced from 102 to 47, significantly reducing LLM calls while preserving temporal context.

Key Insight: Segmentation granularity needs balance between “LLM processing capacity limits” and “semantic coherence”: too fine segmentation loses temporal relationships, while too coarse segmentation causes timeouts. 150K roughly corresponds to 15–20 medium-length papers—this is the empirically optimal point.

11. Confusion of researchers with the same name in academic databases: Semantic Scholar merged multiple researchers with the same name into a single entry, leading to misleading trajectory analysis (e.g., Yuke Zhu involves medical imaging, computer vision, and astrophysics—clearly different individuals)#

Solution: AI actively identifies confusion signals in analysis: large domain span, fragmented co-author networks, mismatch between citation counts and paper numbers. A warning is added at the beginning of the trajectory summary, suggesting manual splitting or paper-level analysis. For Yuke Zhu, based on institutional affiliation and research area consistency, it is distinguished from robot researchers at UT Austin/NVIDIA, researchers at Mybank Technology, mathematicians at Zhejiang University, and researchers at Ant Group.

Key Insight: The automated researcher profiling system must include multi-dimensional signal detection modules for the same name: co-author clustering, theme clustering, temporal continuity, and consistency in institutional affiliation. It cannot rely on the identity recognition features provided by the database.

12. Since _finalized defaults to True, old conversation logs were incorrectly skipped during export#

Solution: Line 1726 in daily_summary.py was changed from data.get('_finalized', True) to data.get('_finalized', False), and –force flag was added to explicitly control re-export.

Key Insight: Default values in data pipeline logic must be consistent with semantics: during export, missing _finalized should be treated as incomplete (False), while during merge, it can be treated as stable (True).

13. Multiple analysis failures due to LLM timeout (the initial 300 seconds is insufficient for 187K merged prompts, and 420 seconds is still insufficient)#

Solution: A dynamic timeout formula was designed: 300 + max(0, (len-50000) // 50000) * 120, i.e., 300 seconds as the base timeout, plus 120 seconds for each additional 50K characters. The final merge step was successfully completed within about 660 seconds of timeout.

Key Insight: Timeout design should be linearly related to data scale, not a fixed value: large models have relatively stable processing speed (about 200–300 characters per second). Estimating time based on prompt length plus 50% buffer is a reliable strategy.

14. Systematic unescaped quotes in the JSON fields of LLM-generated researcher profiles cause JSON parsing failure (over 12 errors)#

Solution: Special characters were identified in fields like trajectory_summary and breakthrough[].description, and manually escaped (e.g., “let the robot…” → “let the robot…”, single quotes in technical terms); for truncated JSON objects, missing right parentheses and array end symbols were added based on context.

Key Insight: LLM handling of embedded quotes is unstable when generating long JSON fields, especially in academic texts where terms are frequently referenced (e.g., “viewing while moving” becomes “viewing while moving”). Solutions include: (1) explicitly requiring escaping special characters in prompts; (2) setting a length limit for ultra-long text fields or using multi-round segmentation; (3) adding JSON pattern validation after generation to automatically fix common format errors.

15. Systematic format errors in LLM-generated long JSON outputs: truncation (especially in final fields), unescaped Chinese quotes (“”), missing closing brackets in nested structures, especially when including technical descriptions, Chinese text, and deep nesting (>3 levels)#

Solution: A four-stage repair process was implemented: (1) directly attempt json.loads; (2) extract ```json code blocks; (3) close unclosed structures based on depth matching; (4) use model upgrade (haiku → 14-line poem → long poem) to fix complex errors. A dedicated JSON repair prompt instructs AI to extract and fix JSON, returning only pure JSON without explanations. All failed cases are recorded in outputs/logs/json_repair_failed/ for pattern analysis and future optimization.

Key Insight: Long JSON generation in LLMs exhibits systematic failure patterns; even with the same prompt, differences exist between sessions (e.g., string escaping issues, truncation errors, nesting errors). A single repair strategy is insufficient; a layered fault tolerance mechanism is needed. Chinese quotes (“”) are semantically valid but must be converted to ASCII double quotes in JSON string values. Production systems should validate generated JSON and support automatic repair retries.

For high-volume researchers (over 130 papers), analyzing the entire corpus at once causes prompt length errors or insufficient depth. For the analysis of Yuke Zhu’s 206 papers, the error “too long prompt” occurred.Solution: Adopt an iterative analysis strategy segmented by year: Group papers by publication year, and analyze 1–3 representative papers per round to deeply explore their breakthroughs (description, why other methods were not used, impact, technical insights). While controlling the complexity of a single call, maintain the depth of analysis. Paper selection: based on year grouping + citation count ranking + identification of conference awards (best paper/highlight/focus/oral report identified by LLM), up to 10 papers per year can be analyzed.#

This strategy ensures both temporal integrity and paper quality. The “small but deep” iterative pattern is more suitable for academic analysis than the “large but superficial” one-time approach.

Repeating forward VLM prefix processing is required to complete the head reasoning (once in sample_actions, once in predict_task_completion)#

Key Insight: Process matching denoising consumes many resources, but unnecessary VLM forward processing increases measurable overhead. The unified method eliminates redundancy through minimal reconstruction.
