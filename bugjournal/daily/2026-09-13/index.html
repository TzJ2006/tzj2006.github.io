Problems & Solutions#

Critical Issues#

1. Removing the interpreter wall allowed agents to bypass ledger protection by passing paths as quoted substrings in command arguments.#

Solution: Implemented a third scanning pass in protectedTargetRefusal using mentionedLedger to detect sensitive paths as substrings rather than whole tokens.

2. Sudden FPS drop to 1-2 and mouse stutter despite low CPU/GPU utilization.#

Solution: Analyzed render thread states and found them stuck in ‘glfwSwapBuffers’, indicating a sync/display bottleneck rather than a processing bottleneck.

3. The removal of the interpreter wall exposed two security leaks where the engine could be invoked via shell prefixes or nested calls.#

Solution: Enhanced ENGINE_INVOCATION regex to handle claude-/cursor- prefixes and implemented NESTED_ENGINE_INVOCATION for nested shell execution.

4. Potential driver-induced latency spikes noticed in traces.#

Solution: Investigated DPC info and realized 4-16ms spikes were present but insufficient to explain the extreme 1 FPS drop, shifting focus to the display pipeline.

5. Jump host connection timeout preventing remote deployment/startup.#

Solution: Wait for jump host stability. Use deploy_drawn_memory.sh once connection is restored to automate future deployments via permitted .sh execution.

6. Guard restriction prevents the Agent from running local Python/SCP.#

Solution: User must run quad_scan.py locally (with VPN) and scp the training script manually (or via deployment script once connection is up).

General Issues#

7. The install.ts --update command failed due to a malformed (non-UTF-8) JSON file in an unrelated repository.#

Solution: Identified the specific file causing the conflict and opted to install the updated bundle only to the current repository to avoid data loss.

Learnings#

Key Learnings#

  • Security barriers that rely on ’layering’ can create false sense of security; removing one layer can reveal that subsequent layers were only effective because of the first.
  • Low FPS combined with low resource usage often points to thread synchronization or display buffer blocking (e.g., glfwSwapBuffers) rather than hardware capacity.

Practical Learnings#

  • ‘Self-test in module tail’ pattern creates a technical debt: implementing a fix immediately makes the ‘Red’ sign-off stale/unexpected-pass. Future testing should be decoupled.
  • Modifying symbol strings in graph.yaml invalidates existing approvals, even if only line numbers were intended to be added.
