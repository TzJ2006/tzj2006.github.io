Issues and Solutions#

Key Issues#

1. QFormer training is very slow (about 3.5 hours), using only 5% GPU utilization, because the Python loop processes 2700 points sequentially.#

Solution: Batch forward pass was implemented: padding neighbor index tensors were precomputed at the start of training, batch context was built using index_select, key_padding_mask was added in the transformer, and all points were processed in a single GPU parallel forward call. Key insight: During the Python loop, GPU utilization is extremely low—even though the batch semantics refer to “spatial position” rather than “samples,” batch processing is essential for Transformer models.

2. All 3 GPU evaluation nodes (m14_cpu/pi0/pi05) crashed at scenario 122/649 because the xml hash fingerprints of 130 natural capture scenarios were inconsistent, causing EnvironmentMismatchError.#

Solution: The EnvironmentMismatchError import statement was added to collector.py, and scene-level try-except wrappers were added around _run_episode() to log warnings and skip incompatible scenarios instead of terminating the program.

Key insight: The database contains two sets of fingerprint data (519 pulses/enhancement scenarios and 130 natural VLA generation scenarios); robust error handling at iteration boundaries prevents cascading failures, while –resume preserves completed work.

3. STAIG edge weight computation uses O(n²) nested Python loops, which takes 2–5 seconds for 2700 points, blocking the training process.#

Solution: scipy.spatial.distance.cdist was used for distance matrix calculation, scipy.special.softmax(axis=1) was applied for row normalization, and NumPy’s advanced indexing function was used to access edge probabilities instead of list comprehensions.

Key insight: Nested loops containing mathematical operations should always be vectorized—using basic functions from scipy/NumPy can achieve 100–500 times acceleration; the key is identifying the O(n²) pattern and finding appropriate library functions to handle paired distances.

4. It is currently unclear whether visual embedding improvements (scan_cluster: 1536d→256d) help improve multimodal fusion performance.#

Solution: Systematic ablation experiments were conducted: all 8 fusion methods were run with and without the improvement on section 151673, showing that the improvement helps weaker methods (average improvement 0.056, attention mechanism improvement 0.086 ARI), but harms stronger methods (qformer decreases by 0.054, concat decreases by 0.074 ARI)—the dimensionality reduction process requires balancing noise reduction and information retention.

Key insight: The value of dimensionality reduction depends on the capacity of downstream models: simple aggregation methods (e.g., mean, attention mechanism) can benefit from noise removal and avoid the dimensionality crisis, while complex learnable models (e.g., qformer/llava_mlp) can leverage rich information in high-dimensional embeddings—there is no universal answer.

5. Pi0.5 training task (job 46551) abruptly exited after approximately 580 steps because stdout buffering prevented monitoring, and the exit reason was unclear (code 0).#

Solution: PYTHONUNBUFFERED=1 + stdbuf -Ol was added for real-time log output, -eo pipefail + ERR trap was used for error reporting, health checks on the background GPU were performed every 30 minutes, and –resume was used to continue training from step 3000’s checkpoint.

Key insight: Python/JAX stdout buffering may hide training failures; no-buffer output, clear error capture, and regular health checks are essential for 50+ hour training tasks on shared clusters.

6. During STAIG fusion, the pipeline hardcodes vision_encoder=‘uni,’ limiting the possibility of trying other encoders (e.g., HIPT, ResNet50, etc.).#

Solution: The orchestration layer was refactored: STAIG_UNI_FAMILY was introduced to identify encoders that require staig_strict preprocessing (256×256 patches, no ImageNet normalization, frequency filtering), run_benchmark.py was updated to remove forced encoder coverage, and extract_planner and evaluation_planner were updated to conditionally apply different variants based on encoder family membership.

Key insight: Responsibility separation: The model layer (STAIGTrainer) already handles data of any size via PCA, but the orchestration layer imposes artificial constraints—good architecture makes this generality simple once determined.#### 7. evaluate_mimicgen.py lacks environment initialization, resulting in non-reproducible evaluation results across different runs.Solution: An env.seed(args.seed) call was added before each task’s episode loop to match the reference implementation in LIBERO/Phoenix main.py.

Key Insight: Reproducibility requires explicit initialization of the RNG and environment RNG; comparison with the reference implementation reveals missing initialization steps.

General Issues#

8. adaptiveDropoutAdj transfers edgeAttr to the CPU, generates random numbers on the CPU, and then returns them to the GPU—this incurs synchronization overhead per cycle (about 1–2 seconds over 1100 cycles in total).#

Solution: Directly use torch.rand(..., device=edgeAttr.device, dtype=edgeAttr.dtype) to generate random numbers on edgeAttr_device—eliminating all CPU transfers.

Key Insight: Transfers between small GPUs and the CPU accumulate a large amount of data after repeated operations; random numbers should always be generated on the same device as the operation tensor; CUDA synchronization overhead is significant.

9. UNI2 (ViT-H/14, patch_size=14) fails on STAIG’s 256×256 input, resulting in the error “256 is not divisible by 14”.#

Solution: When the strict mode of STAIG is detected, automatically adjust the size in UNI2VisionEncoder.extract() to 224×224 (divisible by 14), and then pass the patch to the model.

Key Insight: The visual transformer has strict input size requirements; when adjusting based on patch size, attention should be paid to divisibility constraints; for most ViTs, 224×224 is a safe default size.

10. The discriminability script encounters a ValueError when parsing the success field in JSONL: Invalid decimal base: ‘False’.#

Solution: Add conversion from string to boolean: success_raw = row.get('success', False); success = success_raw if isinstance(success_raw, bool) else success_raw.lower() == 'true'.

Key Insight: Consistent issues in JSONL serialization—the success field is stored as the string ‘False’, not as a boolean value; defensive type checking can prevent parsing errors, especially when assumptions about the pattern fail.

11. m14_cpu crashes under AssertionError: MUJOCO_EGL_DEVICE_ID(0) must be in CUDA_VISIBLE_DEVICES(5).#

Solution: Change MUJOCO_EGL_DEVICE_ID from 0 to 5 to match CUDA_VISIBLE_DEVICES=5, thereby satisfying the assertion about the device ID string in binding_utils.py.

Key Insight: binding_utils.py of Robosuite requires MUJOCO_EGL_DEVICE_ID to be a substring of CUDA_VISIBLE_DEVICES; when using a single GPU, both must match exactly.

12. Section 151676 causes NaN losses and zero embeddings in STAIG training, causing KMeans to fail on NaN-padded data.#

Solution: Add np.nan_to_num() in the KMeans fallback path; replace NaN with 0 before clustering, and replace infinity with a larger finite number.

Key Insight: Model crashes (NaN losses) are known failure modes that require graceful degradation handling; input should always be cleaned before passing it to external libraries that may not handle NaN robustly (such as sklearn); record known failure cases.

13. The discriminability script crashes under scipy.stats.kruskal ValueError, because all success rates are the same (all SR=0 cases).#

Solution: Wrap H, p = scipy.stats.kruskal(*groups) in a try-except ValueError block, returning H=0.0, p=1.0, significant=False, note='all values identical' in case of an exception. Key Insight: Statistical tests fail on degenerate distributions; explicit handling of edge cases and informative messages can prevent silent failures and help interpret results.

Learning Outcomes#

Key Learning Points- Batch processing is crucial for GPU efficiency: Continuous calls to small GPU operations in Python loops (even 2700 calls) lead to significant resource waste (QFormer uses 5% of GPU resources) — always look for opportunities to merge operations into a single GPU kernel launch to improve efficiency through batch processing.#

  • The value of dimensionality reduction depends on the capacity of downstream models: It helps simplify aggregation methods (such as mean or attention mechanisms), reducing the impact of noise and dimension collapse (+0.05–0.09 ARI), but for advanced learning models that can utilize high-dimensional information (such as qformer and llava_mlp), it has a negative effect (-0.05 ARI) — there is no universal solution; preprocessing methods must be adjusted according to model complexity.
  • Robust error handling at the iteration boundary (scene-level try-except) can prevent cascading failures during long-running batch processing, while retaining some results through a recovery mechanism.
  • Vectorization techniques can significantly improve the speed of array operations: Replacing nested Python loops with native functions in scipy/NumPy is almost always worth it — the key is identifying O(n²) patterns and knowing the correct library functions.
  • For long-term machine learning training tasks on remote clusters, unbuffered output (PYTHONUNBUFFERED=1 + stdbuf -oL) is essential — buffering may hide hours of failures, making debugging impossible.
  • In RL/robotics evaluations, clear initialization of the RNG for policy and environment must be done — comparing with reference implementations reveals potential missing initialization steps in the documentation.
  • Flexibility of the architecture is achieved through family-based conditional logic: When extending from hard-coded assumptions (only UNI), introduce semantic grouping (encoder families) and adopt conditional behavior instead of eliminating all constraints — this preserves optimization for special cases while providing flexibility.

Practical Learning Points#

  • In large-scale applications, eliminating data transfer between GPU and CPU is important: Small data transfers seem insignificant, but they accumulate over multiple iterations (1100 cycles × multiple dropout calls), totaling 1–2 seconds — generate and operate on local device data as much as possible.
  • Input requirements for visual transformers are very strict: ViTs require input sizes to be integer multiples of the patch size (UNI2: H%14=0, W%14=0) — when applying preprocessing methods designed for one architecture to another, size constraints need to be validated in advance; for most ViTs, 224×224 is a safe default value.
  • Statistical tests (such as scipy.stats.kruskal) fail on degenerate distributions; always add edge-case handling with informative error messages instead of letting library exceptions propagate.
  • Defensive type checking (isinstance() guard) can prevent parsing errors when serialization format assumptions are wrong; JSONL fields may have inconsistent types across different data sources.
  • Model crashes (NaN losses) require a graceful fallback path: When known failure patterns exist, add cleanup steps (np.nan_to_num) in the fallback path and log the issue — producing a fallback output (ARI=0 and clean data) is better than causing system crashes.
  • When debugging multi-GPU Slurm jobs, MUJOCO_EGL_DEVICE_ID and CUDA_VISIBLE_DEVICES must match exactly — substrings in binding_utils.py check both for compliance.
