Problems & Solutions#

Critical Issues#

1. AI reported completing non-existent tasks (weekly report generation, new scripts, commits) based on context compression artifacts rather than actual filesystem state.#

Solution: Performed direct CLI verification using git log, ls, and file content checks to prove the absence of changes. Confronted the AI with this ground truth to reset its operational context to reality.

Key Insight: Context compression can introduce hallucinated user intents that persist across sessions; reliance on AI summaries without external validation creates severe state divergence risks.

2. Conflict between ‘Private Deployment’ requirement and ‘GitHub Pages Public History’. Proposed new private repo but user rejected scope creep.#

Solution: Analyzed existing infrastructure. Realized Gadget source is already private; only the published Page is public. Adopted StatiCrypt for client-side encryption and used noindex/404 fallback for obscurity. Reverted the ’new repo’ decision.

Key Insight: Source privacy does not equal deployment privacy. Client-side encryption on static hosting is a viable pattern for personal dev tools without infrastructure complexity.

3. Gradio application crashes on Windows startup because environment proxy variables interfere with localhost health-check requests and missing WeasyPrint/Marker dependencies crash DOCX processing.#

Solution: Updated main() to explicitly set PROXY_BYPASS=127.0.0.1 before the server launch loop. Refactored core.py to identify .docx files by content (zip with word/document.xml) and process them directly using Python’s standard library zipfile and xml.etree.ElementTree.

Key Insight: Localhost should never be routed through external proxies in networked environments; environment variables must be overridden programmatically at startup. For structured formats like DOCX, avoiding the PDF intermediate layer is more robust on Windows.

General Issues#

4. Bash script failed with ‘unbound variable’ error when passing empty optional arguments via SSH command line due to word splitting. Also, exec engine verify commands failed due to cwd issues and lack of shell support.#

Solution: Replaced direct argument passing with printf %q serialization to safely encode variables. Proactively fixed ECL verify fields before execution by replacing complex shell checks with simple file existence tests.

Key Insight: Complex string handling over remote shells requires careful escaping; using printf for secure variable transfer is safer than direct interpolation. The exec engine’s verification step is brittle regarding environment context.

5. HPC home directory quota (25GB) was nearly exhausted by pip and datalab caches, blocking new operations.#

Solution: Identified /hpc/home/zt81/.cache/pip as the primary consumer (18GB) and executed python -m pip cache purge, while opting to preserve critical model files in .datalab.

Key Insight: Aggressive yet targeted cache management is essential on HPC systems with strict quotas; knowing which caches are re-downloadable vs. expensive models prevents unnecessary data loss.

6. Missing ‘in-progress’ data in existing DAG YAMLs, causing overview to show empty state incorrectly. Also, missing ‘in-progress’ data caused incorrect state derivation.#

Solution: Implemented a fallback UI that displays frontier_next (next available tasks) as the effective ‘in-progress’ indicator when no nodes are explicitly marked in_progress. Updated CSS classDefs to include in-progress. Derived state from dependency graphs rather than only explicit status flags.

Key Insight: DAG visualization must handle sparse metadata gracefully by deriving state from dependency graphs rather than only explicit status flags.

7. User repeatedly corrected UI direction: first ‘sidebars’, then ‘in-graph overlays’. Initial implementation used page-switching (render-dag style).#

Solution: Refactored render-overview.ts to support overlapping <div> layers filtered by a floating control panel within the same viewport. Ensured mermaid rendering worked on hidden layers via ‘render-then-hide’ pattern.

Key Insight: User mental models for UI often evolve during interaction. The AI must distinguish between ‘page navigation’ and ‘overlay filtering’ clearly, often requiring iterative correction to match user intent precisely.

General Limitations#

  • AI struggled with complex Bash argument serialization over SSH and generated verify commands that assumed shell capabilities (&&, pipes) the exec engine does not support. It also misdiagnosed Gradio crashes by ignoring stale background processes.
  • AI struggled with multi-turn UI clarification, consistently implementing ‘page switching’ when ‘in-graph filtering’ was visually required. Automated tool sequences could not dynamically adjust planning graphs without human ECL updates.

Learnings#

Key Learnings#

  • Always verify AI claims about state changes (files, commits) using direct system commands; never trust textual summaries of work completion in high-stakes environments. The ECL/DevCompanion pipeline is robust for complex features; using /ccdiscuss to settle topology before /ccplan prevents massive replanning.

Practical Learnings#

  • Creating a ’lenient’ read path and a ‘strict’ write/execute path creates a robust safety net. When updating code in a long-running background service, always verify active PIDs via netstat before relaunching; standard IDE reloads are insufficient for external subprocesses.
  • SSH agent forwarding is a critical pattern for securing git operations on temporary or restricted remote hosts. Knowing which caches are re-downloadable vs. expensive models prevents unnecessary data loss on HPC systems.
  • When designing deployment scripts for multi-user servers without sudo, rely on user-space tools and SSH agent forwarding. For UI features, local preview scripts are critical for immediate visual feedback before deploying encrypted versions.
