Issues and Solutions#

Key Issues#

1. VisiumHD Dataset Path and DLPFC-Oriented Process Incompatibility: Image files do not match, spatial coordinate loading fails, mclust cannot handle the number of high-definition intervals (17,502 intervals, while DLPFC has 4,992 positions) Solution: 5 rounds of debugging: fixed path parsing logic, refactored coordinate loading mechanism, implemented a fallback from mclust to KMeans for large datasets, added tqdm and PYTHONUNBUFFERED for better visibility. HD crop10large now runs the full STAIG process, with speed increased by 360 times (2 minutes vs over 40 minutes per part).#

Key Finding: DLPFC and VisiumHD differ in scale by more than 3 times; mclust’s EM algorithm cannot scale (17,502 partitions require 40 minutes), while KMeans provides acceptable quality trade-offs in exploratory spatial transcriptomics (ARI approximately 0.17 vs 0.20–0.25).

2. Coffee BC-RNN Achieves 0% Success Rate Across All 600 Cycles, While Stack Reaches 98%#

Solution: User identified the root cause: all 9 task configurations from the same template only contained robot-centered observation data (eef_pos, eef_quat, gripper_qpos), lacking 57-dimensional object state information (pod/holder position). Coffee’s multi-stage precise operations require object information; simple Stack tasks can rely on visual recognition. This issue was fixed by adding extra low_dim=[‘object’] to all tasks and regenerating the configuration.

Key Finding: Defects in the observation space have significant impacts depending on task complexity. Simple tasks can be compensated by visual recognition; complex tasks fail entirely. Configuration generation based on templates requires customization of observation data for each task.

3. MIHD Refactoring Phase Dependency Order: Large number of imports from run_benchmark.py for pipelines/modules, prevent direct deletion#

Solution: First execute Phase 2 (extracting shared functions into models/staig_utils.py, models/vision_extractors.py, models/Fusion.py, utils/clustering.py, and updating all pipeline imports), then execute Phase 3 (remove run_benchmark.py). Verify via grep checks on remaining references and dry-run pipelines.

Key Finding: Large-scale refactoring must follow a step-by-step decoupling principle: migrate dependent functions first, then delete source files to avoid import failures in between. Topological sorting is crucial.

4. Desktop Video PowerSave/PowerSave+ Mode Uses Per-Screen Update PlayState(for:) Logic, Causing New Windows to Only Affect Current Screen, While Other Screens Continue Playing#

Solution: Modified SharedWallpaperWindowManager.updatePlayState(for:) to delegate the .powerSave and .powerSavePlus cases to AppDelegate.shared?.updatePlaybackStateForAllScreens(), ensuring global re-evaluation during window events.

Key Finding: When pattern semantics require system-level decisions, the per-screen state method must explicitly delegate to a global evaluator; local and global combinations require careful routing.

5. When CUDA_VISIBLE_DEVICES="" is set to CPU-only for norm_stats, JAX crashes with “No GPU/TPU Found”Solution: The environment variable JAX_PLATFORMS=cpu was added and used together with CUDA_VISIBLE_DEVICES="" to force the initialization of JAX’s CPU backend.#

Key Finding: JAX needs to explicitly select the backend through JAX_PLATFORMS, rather than relying solely on the CUDA device mask. Using only CUDA_VISIBLE_DEVICES leads to backend initialization errors.

6. The pathologist annotation coordinates (micrometer-level across the slice) need to match the 8-micron partition grid compared with VisiumHD crop10large.#

Solution: A mapping rule of r_big//4 was discovered through experimental testing, achieving 100% barcode matching (17,502/17,502 partitions), which was verified via spatial overlay inspection.

Key Finding: The multi-resolution grid of VisiumHD (2-micron partitions, 4×4 aggregation to 8 micrometers) requires integer division coordinate conversion; the metadata on Zenodo lacks a clear mapping document.

7. The Desktop Video auto-mode does not have a battery status awareness function; even when macOS is in low-power mode, it always uses the PowerSave logic.#

Solution: A observer NSProcessInfoPowerStateDidChange was added to applicationDidFinishLaunching; a powerStateDidChange handler was implemented; shouldPauseAllVideos() was updated to check ProcessInfo.processInfo.isLowPowerModeEnabled: allOverlaysCompletelyCovered() is called when normal power mode is used, and anyOverlayCompletelyCovered() is called when low-power mode is active.

Key Finding: The low-power mode of macOS can be queried via ProcessInfo.isLowPowerModeEnabled, and observed through NSProcessInfoPowerStateDidChange; adaptive behavior requires both querying and observation simultaneously.

8. GPU memory exhaustion—all 8 GPUs are near full load, preventing new training tasks from being executed.#

Solution: It was found that Phoenix serve_policy.py (PID 2413737) consumes approximately 407 GB of memory on 7 GPUs, but the utilization is only 0% (idle server). The server and two other idle VLA servers (PID 2046779, 2138978, each约61 GB) were shut down. GPUs 0–6 were released.

Key Finding: If not monitored, idle model service processes may occupy GPU memory for days. Regular use of nvidia-smi and process auditing can prevent resource shortages. Multi-GPU models waste resources especially when idle.

9. Training stalls indefinitely under the condition that wandb.init() has a proxy error (no proxy is configured on the compute node).#

Solution: WANDB_MODE=disabled was added to the training command environment.

Key Finding: HPC compute nodes usually have no internet connection; for batch tasks, cloud logging services (such as W&B, MLflow, Comet) can be disabled or offline mode can be configured.

10. Gadget merging—sync downloads all logs and processes them as a batch, but only indicates multiple dates, requiring manual iteration to complete the filling work.#

Solution: cmd_merge() was modified to check whether args.date is None when args.sync is True, and then delegated it to dir_merge_sync_all(). This tool groups files by date (in the format YYYY-MM-DD_device.json), processes each date in a separate subprocess, skips dates already reported, and finally performs batch deployment.

Key Finding: Unifying the --sync behavior to match --sync-all eliminates confusion and makes the batch filling process more efficient (more than 50 manual commands were eliminated for the February history).

11. Training tasks 46551 and 46553 of Pi0.5 both failed/canceled.#

Solution: Training logs were analyzed: both tasks were manually canceled using the scancel command. Task 46551 completed only approximately 579 steps and did not reach the 100k target. The root cause was user intervention, not a system or code error.

Key Finding: Manual task cancellation is different from training failure—when diagnosing “failed” runs, it is necessary to distinguish between system errors and user-initiated stops.

12. The path for norm_stats does not match: the script checks checkpoints/<config>/norm_stats/, but compute_norm_stats.py writes the output to assets/<config>/benchmark/mimicgen_<task>/norm_stats.json.#

Solution: The skip check (step 1) and prerequisite check (step 2) were updated to use the correct asset/path structure.

Key Finding: The output path of the tool is not always consistent with the intuitive checkpoint directory structure; dry-run operations were used to verify the actual output location.

13. Bash tools completely fail: all commands (echo hello, true) return exit code 1 with no output.#

Solution: The user insisted on retrying (“try again”); the tool eventually recovered on its own. The root cause is unknown; it may be a sandbox binary file or a temporary issue with the NFS filesystem.

Key Finding: Tool-level failures sometimes only require simple retrying, rather than deep diagnosis. During Bash failures, read/write/glob tools can still work normally and can serve as a backup for partial tasks.

14. Complex multi-task dates (February 15, 16, 17, 28) exceed the 32K output token limit of the Claude API during merging operationsSolution: No immediate fix required; accept this limit. Due to natural distribution of daily workloads among devices, most reports do not exceed the limit.#

Key Insight: Daily reports caused by high cross-task activity on multiple devices may reach the API output limit. Future mitigation measures: chunking merging, processing segmented by device, or using hierarchical summarization (day→week→month).

Common Issues#

15. The training script encounters a parsing error when running --overwrite/--no-overwrite: the explicit parameter False is ignored.#

Solution: --overwrite=False was changed to --no-overwrite (boolean flag syntax, not key=value).

Key Insight: Python CLI boolean flags usually use the --flag/--no-flag pattern, rather than --flag=值 syntax.

Lessons Learned#

Key Lessons – mclust probabilistic clustering shows significant performance degradation when dealing with over 5,000 observations (more than 40 minutes for 17,502 intervals); KMeans provides 360 times faster performance (2 minutes vs over 6 hours for 11 parts), and the trade-off between quality and speed is also reasonable (ARI约为0.17, while KMeans is 0.20–0.25), making it suitable for exploratory spatial transcriptomics analysis.#

  • Without a comprehensive dependency analysis using grep, “legacy” code cannot be safely removed. During transition periods, new modular processes usually still import tools from old monolithic files. If new code imports from these “legacy” files, those files may remain critical infrastructure.
  • Best practices for large-scale refactoring include: analyzing dependencies (using grep to check all import statements) → migrating code in topological order (migrate dependencies first, then dependent items) → deleting source files → global verification (checking remaining references and dry-run tests) to ensure every intermediate state is runnable.
  • The design of the observation space has a non-linear impact on task performance: missing object keys result in 0% SR rate for Coffee, but Stack’s simple tasks still achieve 98%. Different tasks have varying degrees of dependence on observation information; configuration templates cannot be generalized.
  • BC-RNN performs significantly better than Pi0.5 on the normal MimicGen task (Stack D0: 98% vs 24%), but both perform poorly in error recovery (success rate is about 0%).
