Issues and Solutions#

Key Issues#

1. User prompts are too vague, leading to AI misunderstanding intent, exceeding scope, and ignoring constraints#

Solution: Design a required Spec template with five mandatory fields: Goal (one-sentence objective), Scope (modifiable/unmodifiable files), Constraints (library restrictions, backward compatibility requirements), Success Criteria (executable verification conditions), and Non-goals (clearly excluded tasks). The agent must complete and obtain user confirmation before execution.

Key insight: Structured specifications with required fields prevent AI misunderstanding better than natural language prompts; three issues (scope expansion, wrong direction, ignored constraints) directly correspond to the Scope, Goal, and Constraints fields.

2. Lack of verification mechanism, resulting in inability to determine if code changes truly solve the problem (e.g., 1000 data entries expected but only 100 are generated)#

Solution: Implement a verification mechanism, define success_criteria in spec (such as ‘python test.py’ executable command or expected output string). Validation is automatically executed after task completion: success enters the review phase, failure pauses in debugging mode.

Key insight: Acceptance tests should be part of spec, not added after implementation; success_criteria is an executable definition of “how success appears,” conceptually similar to the verification mechanism, not two independent steps.

3. PyTorch CUDA packages (torch==2.10.0+cu130, torchvision+cu130) cannot be obtained from standard PyPI, causing pip installation failure#

Solution: Add –extra-index-url https://download.pytorch.org/whl/cu130到pip依赖部分，以访问PyTorch的CUDA专用包索引 to all yaml files.

Key insight: PyTorch CUDA builds require explicit index URL configuration; standard PyPI only provides the CPU version.

4. Source installation packages (mimicgen, robosuite, gadget) cannot be obtained from PyPI, leading to failure in conda environment creation during pip stage#

Solution: Add –extra-index-url https://download.pytorch.org/whl/cu130到pip依赖部分，以访问PyTorch的CUDA专用包索引 to all yaml files.

Key insight: PyTorch CUDA builds require explicit index URL configuration; standard PyPI only provides the CPU version. Solution: Adopt a two-stage strategy: first create a yml file containing only conda (remove pip part), install the conda package, then install via pip from the filtered requirements.txt file, excluding unusable packages.

Key insight: Mixed conda/pip environments and source installation packages require manual separation and reconstruction; the integrated pip stage in conda env create cannot handle missing PyPI packages gracefully.

5. AI blindly retries or continues modifying after test failure without a reasoning process or user confirmation#

Solution: Designed a debugging mode that pauses on verification failure, generates structured hypotheses (Hypothesis 1: Because X, so Y, evidence: code location, confidence: high), outputs terminal summaries and detailed HTML reports (data comparison charts, execution flow diagrams, highlighted logs), and waits for user confirmation of direction before fixing.

Key insight: All AI judgments must have a transparent reasoning chain (“because→therefore”); pausing to wait for confirmation is more efficient than blind retries; users need to see the AI’s thinking process to determine if the direction is correct.

6. Lack of cross-session context recording, preventing the next session (or other agents) from knowing what was executed and why#

Solution: Implemented dual-format review logs: a human version .md (including modified files, reasons, impact scope, comparison of original plan and actual results, suitable for reviews and PR descriptions) and an agent version .agent.json (structured JSON, including files_modified, reasons, reasoning chain, test results, next steps, for reading by the next session or other agents).

Key insight: Humans and agents need different information densities and formats; a single format cannot satisfy both needs; humans need narrative content, agents need structured information; recording the original plan in review logs is very important for comparing “intent and result”.

7. Dependency conflicts in lifecopilot environment cause pip installation failure (ResolutionImpossible error)#

Solution: Use pip install –no-deps flag to force installation, avoid dependency resolution, and accept manual repair if conflicts cause runtime issues.

Key insight: Strict dependency resolution may hinder environment reconstruction; when a specific version can run from the original environment, –no-deps provides an escape route.

General Issues#

8. Self-deployment in gadget repository encounters PermissionError (WinError 32: Process cannot access file because it is used by another process) on AGENTS.md#

Solution: Since gadget is the source repository of the workflow, AGENTS.md, reviews/, and workflow/ directories already exist completely. The installation script tries to overwrite its own AGENTS.md, which is blocked by the current Claude Code process, but this does not affect functionality, so it can be skipped.

Key insight: The non-reproducibility of the installation script is important; deployment logic for source and target repositories should be handled separately (skip overwriting when the source repository already has files); Windows file locking requires special handling.

9. Path replacement in Windows PowerShell profile files fails due to backslash escaping issues, causing sed failure#

Solution: Switch from sed (-replace) using regular expressions to PowerShell’s .Replace() method, which can handle literal strings without regex parsing.

Key insight: Windows path operations in Bash require a lot of escaping or delegation to native PowerShell commands for more concise execution.

AI Limitations#

Key Limitations#

  • Background task output (run_in_background: true) is often truncated or lost (wc -l shows 0 lines), requiring rollback to foreground execution to see actual error messages
  • Initially underestimated the maturity of community tools, claiming “high learning costs” was inaccurate, and later admitting “the previous comparison was not honest”; prefers custom construction for control rather than using mature solutions first
  • Tends to design in excessive layers, splitting conceptually unified things (success criteria and verification gates) into two independent components, ignoring user cognitive consistency
  • Initially dealt with problems by directly modifying yml files and repeatedly trying conda env create; only after multiple iterations discovered the need for a two-stage approach (use conda first, then use pip separately)
  • Does not actively include the original plan in review logs to compare intent and result, only focusing on recording final results, ignoring the value of the process and reflection

General Limitations#

  • Tends to let users choose one format in option design to simplify implementation (e.g., terminal for quick failure summary, HTML for data comparison charts and deep analysis, execution flowcharts, highlighted logs), underestimating the necessity of a complete solution
  • Cannot directly diagnose dependency conflicts in lifecopilot environments because pip error output does not contain detailed conflict information; has to use –no-deps workaround
  • sed commands for Windows path operations require multiple attempts due to complex escape of backslashes; the final solution is to delegate to PowerShell .Replace() method

Lessons Learned#

Key Experiences#

  • Structured specifications with required fields (goal, scope, constraints, success criteria, non-goals) are more effective than natural language prompts in preventing AI misunderstanding, forcing consideration of constraints and boundaries
  • Acceptance tests should be part of the specifications (success_criteria), not a supplement after implementation; success_criteria is an executable definition of “how success appears”, essentially the same as verification gates
  • All AI judgments must include a transparent reasoning chain (“because X, so Y” with evidence and confidence); waiting for user confirmation after failure is more efficient than blind retries; structured hypotheses (Hypothesis dataclass) force AI to express the reasoning process clearly
  • Mature community tools (Spec Kit 95K stars, Entire CLI 4.3K stars, git-cliff 11.8K stars) are more reliable than custom construction, and should be used first; build custom versions only for filling gaps (e.g., custom debugging mode) and adding layers (e.g., AGENTS.md protocol)
  • PyTorch CUDA packages must be installed via https://download.pytorch.org/whl/cu130 indexing; standard PyPI only provides the CPU version, the +cu130 version string cannot be parsed via pip
  • Conda environments with mixed conda/pip dependencies are very fragile; a two-stage approach (use conda package first, then use pip separately with error tolerance) offers more control and recovery options than integrating conda env create
  • Cross-session context transfer requires two formats: human version (narrative, suitable for review and PR descriptions) and agent version (structured JSON, suitable for program reading); a single format cannot satisfy both needs
  • Subagent-driven development is ideal for parallel execution of independent tasks: assign a new subagent (independent context) to each task, perform two-stage review after completion (spec compliance → code quality), avoiding contamination of the main session context
  • AGENTS.md as a cross-agent protocol is more general than SKILL.md, readable by Codex/Cursor/Claude/Copilot; .cursorrules are Cursor-specific supplements, combining both covers all agents
  • Source packages installed from git/local paths need to be identified and excluded from automatic pip installation during environment reconstruction, then manually reinstalled later
  • Recording the original plan in review logs is important for review and learning, enabling comparison between intent and result (what was planned vs. what was actually done), which is the basis for reflection and improvement

Practical Experience#

  • Power of installation scripts is important; deployment logic for source and target repositories should be handled separately (avoid overwriting when the source repository already has files), and Windows file locking requires special handling
  • Windows path operations in bash/sed are error-prone; for complex string replacement in Windows paths, delegating to native PowerShell commands (Get-Content | .Replace() | Set-Content) is more reliable
