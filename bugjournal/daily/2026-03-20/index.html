Issues and Solutions#

Key Issues#

1. Personal data files (dialogue logs, AI summaries, blog content, research cache, benchmark test results) are tracked via git and pushed to GitHub, leading to blurred boundaries between code repository and data storage, with privacy risks#

Solution: A three-layer cleanup mechanism was designed: (1) Current working directory: use git rm –cached to delete tracking records; (2) Rewrite git filter-repo to regenerate all 24 commit histories; (3) After forced push, use rclone to manage personal files uniformly (remote path gdrive:gadget). Repository size was reduced from 22MB to 516KB.

Key insight: Clear responsibility boundaries between git and rclone are necessary: git manages public code and reproducible configurations, rclone manages personal data and runtime output. Mixed usage leads to repository expansion (94MB of personal data), privacy leaks, and collaboration difficulties. Clear separation can establish data privacy boundaries.

2. When users perform merge operations on other devices and generate final reports, local –sync-all still considers all dates as unfinished, causing repeated LLM calls#

Solution: AI discovered that _rclone_download_logs only downloads logs without downloading reports, resulting in failure of local completion checks. The _rclone_download_reports() function was implemented to pull existing reports from remote before synchronizing all status checks.

Key insight: In distributed collaboration scenarios, status synchronization must synchronize both inputs (logs) and outputs (reports) simultaneously; otherwise, repeated processing logic will fail. Complete status synchronization can prevent resource waste (repeated LLM calls).

3. The CPU BLAS matrix_size recorded in test/CLAUDE.md is incorrectly labeled as 8192 (single-core) and 4096 (all cores), with GPU set to 2048#

Solution: Confirmed actual code: CpuSingleCoreBLASBenchmark.MATRIX_SIZE=2048, CpuAllCoresBenchmark.MATRIX_SIZE=4096, GpuBenchmark.MATRIX_SIZE=8192. The document was updated to match the actual situation.

Key insight: Differences between documents and code accumulate over time; line-by-line verification ensures no numerical errors are missed. Systematic thorough verification is crucial for correctness.

General Issues#

4. git filter-repo deleted the.gitkeep file and filtered directories, destroying directory structure preservation#

Solution: Recreated the.gitkeep file (research/cache/, research/projects/, research/reports/) using touch and git add -f, then as a separate “restore directory structure” commit after filter-repo+forced push.

Key insight: git filter-repo’s –invert-paths removes the entire directory tree, including structure files; restoration of.gitkeep must be done in a commit after filter-repo, not during add operations before filtering.

There is a lack of forward-looking consideration for the integrity of distributed collaboration state synchronization.
  • AI initially did not suggest line-by-line document verification until users explicitly requested “sentence-by-sentence check”; the default mode is based on target/sampling reviews, which may miss numerical errors (such as matrix_size, duration of doctoral degrees).

General Limitations#

  • AI launched 3 parallel exploration agents to scan the code repository (personal file list, rclone logic, git history), which is comprehensive but may not be efficient enough — this information can be obtained quickly with a few grep/ls/git commands, and the overhead of agents may be excessive.
  • AI did not predict that the .gitkeep files would be deleted by git filter-repo –invert-paths (problem with directory structure preservation); these files need to be manually restored by users after post-filter-repo.

Learning Outcomes#

Key Learning Points#

  • Clear boundaries for responsibility should be defined between Git and rclone: Git manages copyable public code and configurations (requirements.txt, scripts, Claude.md), while rclone manages personal data and output (logs, reports, cache, test results, website content). Mixing them leads to repository expansion (94MB of personal data), privacy risks, and collaboration obstacles. Clear separation can establish appropriate data privacy boundaries.
  • Discrepancies between documents and code are inevitable and accumulate over time; regular line-by-line verification (using parallel exploration agents to increase speed) is necessary to detect numerical errors, path references, and internal contradictions that cannot be seen with plain reading. System verification can prevent the accumulation of small errors.
  • Design principles for distributed collaboration state synchronization: Not only input data (logs) should be synchronized, but intermediate output (reports) also should be synchronized; otherwise, logic dependent on output states (such as final checks) will fail on different devices. Full state synchronization can prevent resource waste (repeated calls to LLM).
  • git filter-repo is the correct tool for removing large files/sensitive data from git history (repository size reduced from 22MB to 516KB), but a complete workflow is required: backing up .git files, running filter-repo, restoring structure files (.gitkeep), forced push, and updating all clones. Risk management checklist: (1) backup must be done on all devices, (2) forced push is required, (3) all other clones will be damaged and need re-cloning. A clear user confirmation process (AskUserQuestion) should be used to ensure users understand the destructive consequences.

Practical Learning Points#

  • When building a centralized synchronization infrastructure (sync.py), supporting –dry-run and –category flags from the beginning enables safe incremental testing and selective synchronization without fully uploading data; rclone remote path migration (gdrive:summarize/ → gdrive:gadget/) is less risky because atomic move operations are used. Configuration migration checklist for modifying remote paths: (1) must update config.json reading of summarize/daily_summary.py, (2) research/research_scout.py configuration, (3) test/sync logic, (4) website/Hugo integration, (5) global config of sync.py, (6) existing remote data migration scripts.
