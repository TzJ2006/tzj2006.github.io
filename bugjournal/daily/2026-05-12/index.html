Issues and Solutions#

Key Issues#

1. Summary reports cannot be deployed to GitHub Pages — 72-day reports do not appear in staging#

Solution: Modified _cmd_merge_sync_all in daily.py to deploy all non-staging reports in the entire report directory, rather than only the currently processing dates

Key Finding: Reports that were finally determined but never deployed were permanently skipped, as the deployment logic only traversed dates_to_process (current batch), ignoring historical backlog

2. GitHub Pages site does not update despite successful local build — Step 9 of update.sh fails silently#

Solution: After discovering the missing independent .git in the public/ directory, re-cloned the tzj2006.github.io repository into the website/public/ directory

Key Finding: The public/ directory was git-ignored in the main repository but was not a correct git submodule or independent clone, resulting in a silent failure of git push

AI Limitations#

Key Limitations#

  • Initially only diagnosed code logic errors (_cmd_merge_sync_all), and infrastructure issues (missing git repository in public/) were noticed only when humans observed the actual website status
  • No end-to-end deployment path from staging → content → Hugo → GitHub Pages was verified before the first fix was announced

Lessons Learned#

Key Experiences#

  • When debugging deployment processes, verify the entire infrastructure chain (code logic + file paths + git repositories + remote endpoints), not just code logic
  • Clearly verify git-ignored directories as independent git submodules — the absence of .git in expected locations is a key diagnostic signal

Practical Experience#

  • The unified proxy workflow can be installed and verified through its test suite (33 tests) and module import checks; when there are no active tasks, the “no active specification” error is expected
  • It is recommended to use ‘python -m workflow.verify’ rather than direct script execution
