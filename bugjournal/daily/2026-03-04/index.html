Lessons Learned#

Key Lesson – QueST Evaluation Framework: When no ready-made benchmark labels exist, use Wasserstein Weisfeiler-Lehman plots to verify cell type annotations and construct synthetic benchmarks, then validate model similarity rankings using Pearson correlation coefficients.#

  • A multi-task machine learning pipeline built via incremental prototype design (starting with one task) retains scattered single-task configurations (removed task list, hardcoded paths). To scale to a production environment, systematic review of data preparation scripts, dataset mapping JSON files, checkpoint directories, and evaluation configurations is required.
  • Documentation synchronization pattern: Use parallel exploration agents (one per major directory), verify all numbers come from actual files (summary.json, file system statistics), and then systematically update document content part by part. Do not rely on statements in the document—always check code and data actual conditions.
  • Debugging checklist for training and evaluation mismatch: If a strategy performs well in training but fails in evaluation, systematically check: (1) observation dictionary keys; (2) environment initialization parameters; (3) action space boundaries; (4) data normalization; (5) camera rendering settings. BC-RNN has a 0% recovery rate on normal tasks and 0.28% on error recovery tasks, indicating environment mismatch rather than strategy failure.
  • Cross-sample query evaluation requires: (1) batch-invariant embeddings obtained via adversarial training; (2) benchmarking using graph kernels when labels are unavailable; (3) dual metrics, including highest accuracy and overall ranking correlation.
  • For spatial transcriptomics, Wasserstein Weisfeiler-Lehman graph kernels can convert discrete cell type labels into continuous segmentation similarity scores by calculating graph-level Wasserstein distances between subgraph representations.
  • Large-scale HPC training orchestration requires clear dependency mapping (Stage 0→Stage 1+2 parallel→Stage 3→Stage 4→Stage 5), GPU allocation plans for each stage, and persistent session management (tmux) to continue running over multi-day training activities and SSH disconnections.
  • Multi-source data collection architecture should be clearly stated in the document: Error scenarios benefit from diverse sources (demonstration injection for replicability, strategy deployment injection for realism, natural failure capture for realism). The flow diagram must present all sources as equal citizens, not hide them in script options.
  • M14 evaluation results show baseline performance: 6,474 scenarios involving 4 strategies, with a random strategy having a 0% recovery rate and a recovery ratio of 1.9%; BC-RNN has a 0.28% recovery rate and a recovery ratio of 0.3%; Pi0 has a 0% recovery rate and a recovery ratio of 0.2%; Pi0.5 has a 0% recovery rate and a recovery ratio of 0%. Near-zero error recovery rates verify the difficulty of the benchmark and provide a foundation for future improvements (M15 human recovery data and LoRA fine-tuning are expected to show positive effects).
  • Best practices for checkpoint inventory: Record complete paths, sizes, last modification dates, and availability status of all model checkpoints. Large checkpoint directories (180GB) indicate many steps saved—specific steps for evaluation need to be recorded. Date-based naming helps track training timelines, but steps must be clearly linked to dates.
  • Scalability of error frameworks: A total of 53 Python files (about 1.47 thousand lines of code) include 6 detectors, 4 injectors, 4 validators, and 20 error classifiers, covering 3 domains (operation, planning, progress). The plugin architecture is scalable through DECTOR_REGISTRY, INJECTOR_REGISTRY, VALIDATOR_REGISTRY, CLASSIFIER_REGISTRY. A cooling time of 20 steps per detector prevents detection of junk behavior.
