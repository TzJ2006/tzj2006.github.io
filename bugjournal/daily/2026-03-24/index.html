Issues and Solutions#

Key Issues#

1. daily_summary.py is 2930 lines long with mixed responsibilities, exceeding maintainability thresholds#

Solution: Split it into 8 modules based on functional boundaries: configuration (75 lines), remote (100 lines), parser (460 lines), usage (460 lines), summarizer (340 lines), formatter (440 lines), daily (750 lines), CLI (130 lines). Keep daily_summary.py as a fallback to maintain backward compatibility.

Key insight: Large-scale refactoring requires Smoke tests (47 import contract tests) for migration to ensure zero disruption. Parallel agent execution can accelerate module extraction.

2. In LLM pipeline code exceeding 2930 lines, 5 dialogue parser and hierarchical merging logic have no test coverage#

Solution: Create 72 tests in 5 test files: test_imports.py (47 Smoke tests), test_config.py (7 tests), test_parsers.py (6 tests), test_formatter.py (6 tests), test_summarizer.py (6 tests).

Key insight: Write import contract tests before refactoring (run twice: before and after transformation). This provides a safety net, making large-scale changes more reliable.

3. Technical documentation generated by code summary skills is too flat, lacks narrative and context, and is not suitable for different readers#

Solution: Re-design as a six-part structure similar to a paper (highlights → introduction → architecture → implementation → results → conclusion and future work). Add scale-adaptive adjustments (≤3 files: simplified version, 4–10: standard version, 11–50: full version, >50: focus on architecture). Implement a three-level fallback mechanism for results (read output → read documentation example → infer from code).

Key insight: Documentation needs to match scale and audience. Critic Agent review identified a contradiction between “all readers” and “fixed structure”; this was resolved by layering within each part.

4. TokenMonitor users initially wanted direct rendering of cost text onto tray icon pixels for unified cross-platform display, but Windows/Linux trays are fixed-size squares (16–32px), making ‘$12.45’ unclear to display#

Solution: Switch to a hybrid approach after feasibility probing: macOS continues using native set_title() for the icon next to the text; Windows/Linux use set_tooltip() for hover-based cost display (simplified rendering like ‘$12’ may be provided in the future).

Key insight: Research via parallel agents revealed that platform constraints (tray icon size) hindered architecture progress before implementation; feasibility probing identified this issue, avoiding unnecessary effort.

5. Initially planned integration of ccusage backend called direct CLI subprocess invocation, but supporting multiple providers (Claude, Codex, OpenCode, Pi, Amp) required managing 5 npm packages with different binary names#

Solution: Found that ccusage provides @ccusage/mcp (model context protocol server), which already aggregates CLI from all providers via stdio JSON-RPC. Changed architecture to a single long-lived MCP process instead of generating subprocesses repeatedly.

Key insight: Phase 1 assumption verification revealed ‘ccusage’ was actually 5 independent packages; deeper research showed MCP server is a better integration point, solving performance and multi-CLI coordination issues.

6. Using sys.path.insert() techniques in 3 places (mcp_server.py, monthly_summary.py, weekly_summary.py) causes fragile module identity issues#

Solution: Packaged summarize/ via init.py, updated pyproject.toml package list, and changed all imports to ‘from summarize.xxx import …’. Remove all sys.path operations. Key insight: Workarounds for sys.path cause module identity issues (_cached_config loaded twice). Correct packaging can completely avoid such errors.

7. ccplan skill workflow terminates early at phase boundaries, failing to complete the full cycle#

Solution: Add “continue execution instruction” at the skill header and insert “→ Next: immediately enter Phase X” prompts at each phase boundary (10 phases total), completing multi-round protocol parts for all 9 phases, with phase transition marked as mandatory.

Key insight: For multi-phase workflows, prompt engineering needs to explicitly indicate continuation at each boundary. Implicit expectations (“just continue”) cannot be reliably enforced.

8. Original TokenMonitor plan included retaining change_stats and subagent_stats functions after migration to ccusage (currently marked as #[allow(dead_code) dead code), but ccusage lacks corresponding features#

Solution: After user confirmation, decided to retain a simple JSONL reader for these two functions during migration of token/cost/pricing logic to the ccusage MCP server.

Key insight: Adversarial review (FIND-001 CRITICAL) forced us to clarify feature scope before migration; recording the retention plan avoids implicit loss of features.

Limitations of Artificial Intelligence#

Key Limitations#

  • The original ccplan skill design lacks clear instructions for continuing operations between stages, leading to premature termination of the workflow. Prompts for “continue execution instruction” and “→ next step” are needed at each boundary.
  • AI initiated 4 background agents for adversarial review and research, but 3 agents never completed or returned empty output files—yet AI continued stage 8 review without waiting for their results, making architectural decisions under incomplete analysis.
  • AI cannot execute Rust cargo commands on users’ Windows systems (cargo is not in the Git Bash PATH), so it relies on type-checking logic instead of compilation verification—this caused runtime errors (E-1 to E-6) in 6 completed code changes.
  • The initial summary skill design did not address the conflict between “all reader levels” and “fixed chapter structure” requirements until the Critic Agent conducted review.

General Limitations#

  • The.skill file being a ZIP archive was not automatically detected, requiring manual extraction using the Python zipfile module to read its content.
  • When users ask “What about Windows and Linux systems now?” after tutorial creation, AI offers 3 options but does not consider this as implicit approval for cross-platform work—/ccplan must be explicitly called instead of treating it as a signal to continue operations.

Lessons Learned#

Key Experience – ECL method successfully identified key issues before implementation through hypothesis verification, adversarial filtering, and feasibility probing. Examples include: tray icon size limitation, lack of ccusage function, and performance impact of child process startup. This verifies the premise that “needs are assumptions”—every proposed need should be questioned.#

  • ECL documentation enables persistent and traceable design decisions across sessions. State fields track workflow stages, and the pending_input field maintains continuity during context compression.
  • Migration smoke tests are crucial for large-scale refactoring: write import contract tests covering all external consumers and test them before and after migration. This ensures reliable changes (47 tests × 2 runs = 94 verifications).
  • Tauri v2’s tray.set_title() is only applicable on macOS (not explicitly stated in TokenMonitor code); set_tooltip() is the alternative for Windows/Linux. This is an important cross-platform consideration for Tauri menu bar applications.
  • Adversarial review (Critic Agent) identified blind spots in design: more than 12 issues were found, including serious contradictions between two projects. Red-blue adversarials during the requirement phase can prevent rework later.
  • Multi-stage prompt workflows require clear continue instructions at each boundary: continuous execution instruction (global), “→ NEXT:” transformation (per stage), multi-round protocol (per stage). Implied expectations do not apply.
  • When migrating from platform-specific code to a cross-platform architecture, removing all platform-specific features (such as glass blur, Dock icon visibility) is easier to maintain than finding minimal common standards alternatives—in infrastructure code, simplicity outweighs functional equivalence.
  • Parallel agent execution can accelerate independent tasks: 5 module extraction agents run simultaneously, reducing sequential bottlenecks. Clear task boundaries are needed, and shared state is not allowed.
  • Adaptive scale design can improve user experience across different project sizes: fewer than 3 files yield simplified output (avoiding over-documentation), 11–50 files receive full processing, and more than 50 files are grouped to focus on architecture (avoiding context overflow).
