Limitations of AI#

  • When starting VLA evaluation, mismatched domain checkpoints were used (LIBERO optimized model used in PickPlace task), without questioning its effectiveness. Humans should pause and ask, “Which checkpoints are you using?”
  • AI did not anticipate the potential for combinability when implementing vision refinement; it passively followed the user’s dual-stage idea without actively proposing other combination schemes (e.g., stego_refine + attention, byol_spatial + qformer), lacking creative exploration of method combinations.
  • Although known to be more robust in HPC clusters via Slurm SSH access, AI did not actively recommend this approach. Humans need to identify stability issues from experience and explicitly request changes to the workflow.
  • Despite 8 A800 GPUs available, AI still uses a conservative single-GPU allocation, requiring humans to correct it to effectively utilize cluster resources. This indicates lack of intuition for high-performance computing resource optimization.
  • In project organization tasks, AI entered planning mode and conducted comprehensive exploration, but the user interrupted ExitPlanMode twice, indicating that the plan presentation process does not match the user’s expected rhythm (users prefer “direct execution + immediate adjustment” over “complete plan + approval before execution”).

General Limitations- Before starting the VLA server, no check was performed on port availability, resulting in a failed startup due to a port 5555 conflict. A check like lsof -i :5555 should be run first.#

  • When organizing MIHD files, the location of ENHANCEMENT_PLAN.md was initially misjudged (thought to be the root directory instead of docs/), and ls verification was needed. In large projects, path verification should be conducted more carefully.
  • Multiple attempts were made to exit the planning mode, but users kept interrupting it, indicating that AI did not anticipate the need for iterative improvement before finalizing the plan.
  • When generating the daily historical report, there was no questioning why the same date required multiple iterations/sessions, nor was there a suggestion to integrate report generation into a more efficient single process.

Lessons Learned#

Key Lesson – Two-stage fusion (self-supervised refinement → multimodal integration) created new experimental dimensions, connecting image-based and multimodal methods; however, preliminary tests show that under different fusion strategies, refined embeddings are not generally superior to original embeddings—consistency of optimization goals is crucial.#

  • The choice of baseline model has a decisive impact on the validity of experiments. Using checkpoints from mismatched domains (e.g., LIBERO adjusted for PickPlace task) weakens its usefulness. The baseline model must be explicitly verified or fine-tuned to ensure fair evaluation.
  • The implementation of the visual refinement process proves the feasibility of inserting intermediate processing steps in run_benchmark.py: adding about 50 lines of code at appropriate positions (after visual encoding and before fusion) can create a completely new experimental paradigm while fully compatible with existing cache/naming/logging systems.
  • Accessing GPUs in an HPC cluster via Slurm job attachment (srun –jobid) is more stable than direct SSH, as the cluster resource management system can be utilized, and it is suitable for long-running scientific workloads. The job ID remains unchanged between sessions and can be reattached even after disconnection.
  • The research project structure (infrastructure building → validation experiments) of the first/second stage benefits from clear milestone tracking. The completion rate of M1-M11 error recovery benchmarks (649 scenarios) provides a solid foundation for M14 baseline evaluation, although currently it is hindered by insufficient Pi0.5 memory.
  • In an HPC cluster, GPU availability should be judged by the free memory space (at least maintaining more than 50% free space), not just its idle state. If memory allows, multiple jobs can coexist on the same node, enabling parallel task execution and maximizing cluster utilization.
  • The dependency topology diagram should appear before the execution plan. Clearly visualizing M14 as a critical path blocker helps adjust resource allocation decisions and timeline estimates, leading to a more strategic scheduling.
  • The collector resumes function makes long-running evaluations fault-tolerant. The合理性 check of M14 confirms that interrupted evaluations can restart from the last checkpoint, which is important for 6-hour full-time runs.
  • The “cleanup day” mode for project maintenance is very effective: using 3 parallel exploration agents for a comprehensive project survey, followed by systematic cleanup (removing redundant files, moving logs, reorganizing documents, updating references/memory), simplifies the root directory and makes the document hierarchy clear and traceable.
  • Systematic documentation audit via /init skills is very effective in detecting long-term gaps accumulated during iterative development, especially for multiple tool projects independently recorded for each tool.
  • The error detection process (20 classifiers, PolicyErrorMonitor) works reliably at scale. In the合理性 check, 37–74 errors were detected per set, proving that the classification method can be put into production use.
  • The conversion process from MimicGen to LeRobot requires careful handling of flat and nested HDF5 layouts. Images used in Phoenix paper (84×84) are adjusted to 224×224 for training, and this preprocessing method must be preserved during conversion.
  • JAX can automatically detect all visible GPUs for multi-GPU training when the batch size is divisible by the number of GPUs. When batch_size equals 64, setting CUDA_VISIBLE_DEVICES=0,1,3,4 enables efficient 4-GPU parallel processing without explicit configuration.
  • Exploration agents perform well in organizing tasks of large projects: they can recursively traverse directories, read file headers to quickly identify content, calculate code lines, and compare redundant parts in documents—their efficiency is several orders of magnitude higher than manual exploration.
  • During cleanup work in large projects, if users have clear goals and are willing to take responsibility for plan quality, user-controlled planning (bypassing the approval of ExitPlanMode) may be more efficient. In this case, the AI role becomes an executor rather than a designer.

Practical Experience#

  • When a project accumulates a large amount of work history, batch generation of historical reports is valuable for establishing searchable archives, even though these reports are mainly meta-work rather than main development content. The gadget project now has a comprehensive report covering more than 3 weeks of project activities.
  • QFormer and other fusion methods based on learnable queries exhibit the characteristic of “high VRAM + low GPU utilization” during training: parameters and intermediate results consume memory, but actual computation (cross-attention mechanism) is lightweight, with most time spent on CPU-intensive k-NN graph construction and loss calculation. This is architectural, not a performance issue.
