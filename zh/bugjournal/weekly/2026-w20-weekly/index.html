问题与解决方案#

1. 模糊的用户提示导致AI超出范围或忽略约束 [统一智能体工作流系统]（2026-05-11）#

解决方案： 强制使用包含五个必填字段的Spec模板（目标、范围、约束、成功标准、非目标），在实施前需明确确认。

2. 缺乏客观验证导致无法确定变更是否真正解决了问题 [统一智能体工作流系统]（2026-05-11）#

解决方案： 将可执行的成功标准直接集成到规范中，触发验证门，若通过则继续工作流，否则暂停进入结构化调试模式。

3. PyTorch CUDA包因非标准托管方式导致标准pip安装失败 [开发环境迁移]（2026-05-11）#

解决方案： 配置–extra-index-url指向PyTorch官方CUDA发布索引，以正确解析包。

4. 源安装的Python包在conda重建过程中导致pip依赖冲突 [开发环境迁移]（2026-05-11）#

解决方案： 采用两阶段安装策略：先安装仅conda包，必要时再选择性重新安装pip源，并使用–no-deps参数。

5. 72天的Summarize报告因管道静默失败而未出现在GitHub Pages中 [Summarize部署管道修复]（2026-05-12）#

解决方案： 修正daily.py中的部署迭代逻辑，将公共/目录重新初始化为指向tzj2006.github.io的独立git克隆。

经验教训#

架构（architecture）#

  • 包含必填字段的结构化规范可防止AI范围扩展和约束违反；成功标准和验证门是功能上相同的概念，应统一处理而非拆分为独立步骤。
  • 跨会话上下文需要双格式：人类审查者使用叙述/markdown格式，程序化智能体读取使用结构化JSON格式，单一格式无法同时满足两种需求。

调试（debugging）#

  • 部署失败需要全面验证代码逻辑、文件路径、git子模块和远程端点；仅检查应用日志会遗漏如公共文件夹中缺失.git目录等基础设施层问题。
  • 在审查日志中记录原始实现计划有助于分析意图与结果的关系，突出跳过步骤、意外偏差和实际故障根源。

工具（tools）#

  • 具有混合依赖的conda环境需要两阶段重建方法（先安装conda包，再单独安装pip），以优雅地处理PyPI无法原生满足的源安装包。
  • 标准CLI约定（如全局使用-y/–yes）以及优先使用成熟社区工具而非自定义实现可降低认知负担，加速迭代并提升跨仓库一致性。

领域知识（domain）#

  • AI辅助质量与提示具体性直接相关；富含上下文的明确指令始终优于简单命令或模糊请求。此外，AI编码工具中的后台终端执行容易因截断而失败，需要主动的前置备用方案进行诊断。

AI使用注意事项有效模式：#

  • ✓ 在编写自定义代码之前，优先使用成熟的社区工具（Spec Kit、Entire CLI、git-cliff）作为基础层。
  • ✓ 采用基于假设的诊断流程（“因为X → 因此Y”），并设定置信度等级，而非盲目重试循环。
  • ✓ 对破坏性操作使用AskUserQuestion协议，并在确认修复完成前进行端到端验证。
  • ✓ 将AGENTS.md与.cursorrules结合使用，以最大化Claude、Codex和Cursor环境之间的跨代理兼容性。

限制：

  • ✗ 后台任务输出经常被截断，不得不依赖前台执行来准确诊断错误。
  • ✗ 倾向于最初低估社区工具的成熟度，过度强调自定义构建以追求控制而非可靠性。
  • ✗ 部署调试期间缺乏实时基础设施可见性，需要人工验证最终状态来发现git/config中的缺陷。
  • ✗ 初始选项设计有时被迫做出权衡（例如终端与HTML可视化），而不是提供全面的双输出解决方案。
