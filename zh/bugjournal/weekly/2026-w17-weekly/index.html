经验教训#

架构 (architecture)#

  • 多阶段管道需要在权威源处进行修复，以在同步操作中存活；资产部署应与内容状态检查分离。
  • 分阶段交付平衡了速度与价值以及技术复杂性；根据 YAGNI 原则，直接服务层交互（如 Discord 命令）绕过了不必要的 REST 层。
  • 本地 ML 部署需要跨平台工厂模式和单例初始化来管理成本与延迟，因为动态加载的服务本质上绕过了静态依赖跟踪。

调试 (debugging)#

  • 小型上下文敏感的翻译模型依赖于提示语框架；目标语言指令能实现可靠的输出切换。
  • 最终状态验证优于基于假设的中间调试，在复杂的同步/部署/重新渲染管道中表现更好。
  • 通过比对 manifest 中的运行时导入项可以最好地检测依赖变化，现在缓存读取占 LLM 令牌消耗的超过80%，需要基于缓存的分析。

工具 (tools)#

  • 机器可读取的审计输出使基于规则的清理工具能够建立可重复的维护基准，超越模式匹配。
  • 长期存在的功能分支会积累大量合并冲突；频繁交互式重分支在结构上比批量合并更安全。由子代理驱动的 TDD 与双阶段审查使高速并行开发成为可能。

领域知识 (domain)#

  • 实施前的市场验证确认产品独特性，而快速研究开源技术实现能迅速发现减少设计开销和调试周期的成熟架构模式。
