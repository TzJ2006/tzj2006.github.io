问题与解决方案#

关键问题#

1. Claude Code JSONL 格式变更导致成本膨胀2.4倍：包含多个内容块的助手消息被写成独立行且使用率相同，但当 requestId 缺失时去重被跳过#

解决方案： 修改了 create_claude_unique_hash() 函数，当 requestId 为 None 时仅使用 message.id 作为后备。现在相同 message.id 在多行中正确通过单一 API 调用进行去重

关键洞察： 新的 Claude Code 格式许多条目缺乏顶层 requestId；由于内容块共享相同的 message.id，因此 message.id 是足够的唯一标识符

2. SSH 远程同步导致数据膨胀10-25倍：提取脚本生成重复的内容块行，本地 append 使用 -newer 文件过滤导致每次更新时完全重新提取文件，且未进行去重#

解决方案： 双层修复：（1）远程 Python 脚本在提取过程中保持 seen={} 基于 message.id。（2）本地 sync_host() 加载现有缓存，从 (ts, model, in, out) 元组构建键集，在 append 前过滤新记录

关键洞察： 基于文件的增量同步（-newer mtime）并不意味着记录级别的去重。每一层（提取、摄入、聚合）都需要明确的重复检测

3. ccusage 报告的令牌使用量比 TokenMonitor 高约1.75倍，导致对实际消耗量的困惑#

解决方案： 在 ccusage 的 createUniqueHash() 中识别出根本原因，需要同时使用 message.id 和 requestId——当 requestId 缺失时（20,116 条中的13,960条），不会进行去重，导致重复项被多次计数。此外，ccusage 使用“先胜”策略，保留令牌数量较低的早期快照

关键洞察： 流式 API 每次响应写入多个 JSONL 快照并增加 output_tokens；“先胜”去重保留令牌数量较低的早期快照，而 TokenMonitor 的“最大输出令牌”策略能正确捕获最终值

4. Apple Speech 字幕保持灰色（部分状态），从未变为白色（完成状态），新文本覆盖而非追加之前文本#

解决方案： 修改了 _on_result 回调条件，从“如果 text 且 text != self._last_text”改为“如果 text 且 (is_final 或 text != self._last_text)”，确保最终回调不被去重逻辑跳过

关键洞察： Apple 的 SFSpeechRecognizer 在最终结果和最后部分结果中返回相同文本；去重必须明确检查 is_final 标志

5. Agent 的 claude_parser.rs 提取导致 ssh.rs 回退到旧版本，丢失了 Task 3 的 device_aggregation 重构#

解决方案： 人工检查文件行数发现问题（ssh.rs 回到1536行）。手动重新应用所有 ssh.rs 更改：移除聚合函数，更新导入为 device_aggregation::*，修复所有调用方。通过 cargo check + 测试验证

关键洞察： 如果系统提醒包含过时的 lint 状态，代理驱动的文件修改可能会撤销未提交的变化。代理操作后始终验证关键文件

6. Apple Speech 音频捕获在将音频样本复制到 AVAudioPCMBuffer 时因 ctypes.memmove 的“错误类型”问题停止工作#

解决方案： 通过使用 ctypes 直接调用 objc_msgSend sel_registerName(‘floatChannelData’)，获取与 native ctypes 兼容的 float** 指针，而非 PyObjC 包装对象，从而绕过 PyObjC 桥接

关键洞察： PyObjC 桥接类型与 ctypes 函数不兼容；需要使用 objc_msgSend 进行低级 C API 互操作

7. SSH 远程提取仅找到 ~/.claude/projects 和 ~/.config/claude/projects，缺少自定义安装如具有不同模型的 ~/.claude-code#

解决方案： 用 glob 模式 ‘for _cd in $HOME/.claude*; do [ -d $_cd/projects ] && …’ 替代硬编码路径，自动发现所有 .claude-prefixed 目录；同时source shell rc文件以获取 CLAUDE_CONFIG_DIR 环境变量

关键洞察： 用户可能同时有多个具有不同配置的 Claude CLI 安装；基于 glob 的发现比硬编码更健壮

8. GitHub Actions 缓存接近10GB限制，因缓存整个目标目录及增量构建工件和文档#

解决方案： 将 actions/cache@v5 替换为 Swatinem/rust-cache@v2，后者仅缓存依赖项，为 CI 作业添加 CARGO_INCREMENTAL=0，实现 80% 的缓存减少

关键洞察： 增量编译对本地开发有益，但由于运行器无状态，会浪费 CI 缓存空间；专门的 Rust 缓存动作比通用文件缓存更智能

9. 图表线条 Y 坐标与工具提示值不匹配：$51.45 点显示在 $0 附近，而工具提示正确显示为 $51.45#

解决方案： 将 lineData 段查找从 find() 改为 filter().reduce((sum, s) => sum + s.cost, 0)，按桶计算所有匹配段的总和关键洞察： 聚合数据（工具提示）和可视化编码（行位置）必须使用相同的求和逻辑。设备级分解意味着一个模型可以在每个时间桶中有多个部分

10. DevicesView 和主图表显示不同的设备细分总数。DevicesView 使用 archive + frontier 过滤，主页面读取 raw remote-cache usage.jsonl 而不排除存档时段#

解决方案： 统一两个代码路径，调用 build_device_summary_merged() 并使用 archive.frontier() 过滤，跳过已被存档条目覆盖的紧凑记录

关键洞察： 存档系统创建双数据源（存档 JSONL + 实时缓存）。所有消费者必须使用 frontier 截止时间以避免重复计算过渡期

一般问题#

11. CI 失败提示“无法找到 FloatBallSizes 类型” — Linux 下的 #[cfg] 块使用了 FloatBallSizes，但 mod.rs 未为 Linux 导入它#

解决方案： 添加 #[cfg(target_os = “linux”)] use layout::FloatBallSizes; 和 #[allow(unused_imports)] 到 FloatBallAnchor 上（仅在非 Linux 的 #[cfg] 块中使用）。通过 cargo clippy 验证

关键洞察： 平台条件编译需要特定平台的导入。未使用的导入警告可能取决于平台；使用 #[allow(unused_imports)] 与 #[cfg] 文档说明

12. 图表 Y 轴缩放过粗：$50→$100 的跳跃使得 $51-75 的数据看起来“平坦”（仅使用图表高度的一半）#

解决方案： 在 niceMax() 序列中添加中间阈值：10-50 之间为 15/30，50-100 之间为 75，100-500 之间为 150/300 等。现在 $51 对应 $75 上限而非 $100

关键洞察： 常用范围内的好数字缩放需要更密集的步长。2 倍跳跃对于通常 $10-100 的成本数据来说过于激进

经验教训#

关键经验- 多层数据管道需要在每个边界进行防御性去重：提取（远程脚本）、摄入（本地追加）、聚合（解析器）和归档（前沿过滤）。基于文件的增量同步无法保证记录级的唯一性#

  • 针对流式 API 的正确 JSONL 去重：相同的 message.id 在 output_tokens 递增的情况下会被重复写入。必须保留最后一条记录或限制 max(output_tokens)。仅依赖 requestId（可能缺失）会导致去重失败。“先到优先”策略会低估输出令牌数量
  • 开源工具正确性验证：ccusage 存在两个未解决的漏洞——#797（requestId 缺失导致过度计数）和 #705（“先到优先”导致输出令牌低估）。跨工具比较 + GitHub 问题搜索能有效验证算法正确性
  • Apple 的 SFSpeechRecognizer 在 isFinal=True 和最后部分结果时返回相同的文本；去重逻辑必须明确检查 is_final 标志，避免跳过最终处理回调
  • 带有共享可变状态的工厂闭包模式（例如，resizeOrchestrator 有 19 个状态变量）不应强制重构。成本效益分析：只有 6/573 行是纯函数；提取操作需要传递 19 个参数或引入状态对象，增加认知负担
  • 重复使用成熟的架构模式（LiteLLM fetch/cache）用于类似功能（汇率）可确保一致性并减少错误。两者都采用：fetch API → 磁盘缓存（TTL）→ OnceLock<RwLock<» → 启动加载 + 异步刷新 + 后台循环检查
  • GitHub Actions 缓存策略：增量编译在 CI 中无益（每次运行都进行冷构建）。Swatinem/rust-cache 智能地仅缓存依赖项而非整个目标目录，使缓存减少 80% 同时保持速度
  • 用户对系统行为的直觉理解（SSH 同步重复）通常比 AI 的代码路径分析更快速，可用于识别根本原因。当症状具有明确模式时，假设驱动的调试优于全面的追踪
  • 流式 API 去重需要“最后优先”或“最大值”策略而非“先到优先”，因为早期块包含不完整的累积值（尤其对于 output_tokens）
  • PyObjC 桥接对象与 ctypes 不兼容；使用 ctypes objc_msgSend 配合 sel_registerName 进行直接 C API 互操作以获取原生指针
  • 基于 glob 的路径发现（~/.claude*/）比硬编码特定目录名称更易于维护，当用户可能并行安装不同配置的软件时尤其如此
  • 大型 Rust 文件的模块提取模式：目录模块（foo/ 包含 mod.rs + layout.rs）清晰地将纯逻辑与有状态/特定平台代码分离。成功应用于 float_ball.rs（几何结构 → layout.rs，IPC/窗口 → mod.rs）和 parser.rs（Claude 解析 → claude_parser.rs）
  • 图表视觉编码和工具提示聚合必须使用相同的数据管道。如果工具提示汇总所有设备段，但行 Y 仅使用第一个段，即使两者在其各自上下文中都“正确”，差异也立即显现
  • jq 作为无状态 JSON 处理器无法实现去重——需要像 Python/awk 这样的有状态工具。多路径提取逻辑（jq/python/grep）必须保证行为一致性
  • 归档系统创建双重数据源（归档 JSONL + 实时缓存）。所有消费者必须使用前沿截止时间以避免过渡期重复计数
  • MimicGen 增强需要深入语义理解：任务阶段编码操作进度，对象锚定防止无效场景，变形保留相对姿态，成功验证至关重要。没有上下文感知的适应能力的纯轨迹重放会失败
  • 去重键构建应使用备用策略（例如，requestId 缺失时使用 message.id），而不是返回 null，以避免意外将重复项视为唯一条目

实际经验#

  • 优秀的数值比例需要针对领域典型值范围进行经验调整。通用的几何级数（1/2/5/10/20/50/100）对于集中在 10-100 美元的成本数据来说过于粗糙；中间步骤（15/30/75）可以提高数据墨水比
