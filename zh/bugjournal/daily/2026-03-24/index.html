关键问题#

1. daily_summary.py长达2930行，职责混杂，超出可维护性阈值#

解决方案： 按功能边界拆分为8个模块：配置（75行）、远程（100行）、解析器（460行）、使用（460行）、总结器（340行）、格式化器（440行）、日常（750行）、CLI（130行）。保留daily_summary.py作为回退补丁以保持向后兼容性

关键洞察： 大规模重构需要迁移smoke测试（47个导入合同测试）以确保无破坏。并行代理执行可加速模块提取

2. 2930多行LLM管道代码包含5种对话解析器及层次合并逻辑，测试覆盖率为零#

解决方案： 在5个测试文件中创建72个测试：test_imports.py（47个smoke测试）、test_config.py（7个测试）、test_parsers.py（6个测试）、test_formatter.py（6个测试）、test_summarizer.py（6个测试）

关键洞察： 在重构前编写导入合同测试（运行两次：之前和之后）。这提供了安全网，使大规模变更更加自信

3. 代码总结器技能产生的技术文档过于扁平，缺乏针对不同读者的叙事与上下文#

解决方案： 重新设计为文档式六部分结构（亮点 → 介绍 → 架构 → 实现 → 结果 → 结论与未来工作）。添加规模适配（≤3个文件：简化版，4-10个：标准版，11-50个：完整版，50+个：以架构为重点）。实现结果的三层fallback（读取输出 → 读取文档示例 → 从代码推断）

关键洞察： 文档需匹配规模和受众。Critic Agent审查揭示了“所有读者”与“固定结构”之间的矛盾，通过内部分层解决

4. TokenMonitor用户最初希望将成本文本直接渲染到托盘图标像素中以实现统一跨平台显示，但Windows/Linux托盘图标为固定大小的正方形（16-32px），其中’$12.45’无法清晰显示#

解决方案： 在可行性探测后转向混合方案：macOS保持native set_title()用于文本旁图标显示；Windows/Linux使用set_tooltip()进行悬停时成本显示（未来可添加如’$12’等简略形式）

关键洞察： 通过代理式研究发现的平台限制（托盘图标大小限制）在实施前避免了架构死胡同；可行性探测阶段发现了此问题，避免了无效努力

5. ccusage后端集成最初计划为直接CLI子进程调用，但支持多个提供方（Claude、Codex、OpenCode、Pi、Amp）需要管理5个不同二进制名称的独立npm包#

解决方案： 发现ccusage提供了@ccusage/mcp（模型上下文协议服务器），已通过stdio JSON-RPC聚合所有提供方CLI；将架构改为单一长期MCP进程，而非重复创建子进程

关键洞察： 第一阶段假设验证揭示“ccusage”实际上是5个独立包；深入研究表明MCP服务器是更好的集成点，同时解决了性能和多CLI协调问题

6. 3处位置（mcp_server.py、monthly_summary.py、weekly_summary.py）的sys.path.insert()技巧导致脆弱的模块身份问题#

解决方案： 通过添加__init__.py将summarize/打包成包，更新pyproject.toml包列表，将所有导入改为‘from summarize.xxx import …’。删除所有sys.path操作关键洞察： sys.path 的修改导致模块身份冲突（_cached_config 被加载两次）。正确的打包方式可完全避免此类错误

7. ccplan 技能工作流在阶段边界处过早终止，未完成完整流程#

解决方案： 在技能标题中添加“持续执行指令”，在每个阶段边界处添加“→ NEXT：立即进入第 X 阶段”标注（10/10 个阶段），完成所有阶段的多轮协议部分（9/9 个阶段），将阶段转换标记为必须执行

关键洞察： 多阶段工作流的提示工程需要在每个边界处明确指示继续执行。隐含的期望（“直接继续”）无法可靠生效

8. 原始 TokenMonitor 计划包含保留 change_stats 和 subagent_stats 功能（当前被标记为 #[allow(dead_code)）的死代码），但在 ccusage 迁移后没有相应功能，而 ccusage 也没有类似功能#

AI 限制#

关键限制#

  • 原始 ccplan 技能设计缺乏阶段间的明确继续执行指示，导致工作流过早终止。需要在每个边界处添加“持续执行指令”和“→ NEXT:”标注
  • AI 启动了 4 个背景代理进行对抗性审查和研究，但 3 个代理从未完成或返回空输出文件——然而 AI 仍继续第 8 阶段的审查，未等待结果，导致架构决策缺乏完整分析
  • AI 无法在用户的 Windows 系统上执行 Rust cargo 命令（cargo 不在 Git Bash PATH 中），迫使依赖类型检查逻辑而无需编译验证——在 6 个已完成的代码变更（E-1 到 E-6）中引入了运行时错误风险

一般限制#

  • 未能自动检测 .skill 文件是 ZIP 压缩包，需要使用 Python zipfile 模块手动解压才能读取内容
  • 当用户在教程创建后提问“那现在 Windows 和 Linux 系统怎么办？”时，AI 提供了 3 种选项，但未意识到这相当于隐含同意进行跨平台工作——需要明确调用 /ccplan，而非将其视为继续执行的信号

学习成果#

关键学习点- ECL 方法通过假设验证、对抗性过滤和可行性探测，在实施前就捕捉到关键问题。例如：托盘图标大小限制、缺失 ccusage 功能、子进程启动对性能的影响。这验证了“需求属于假设”的原则——每个提出的需求都应受到质疑#

  • ECL（不断发展的约束语言）文档使得设计决策可以在不同会话间持久保存且可追溯。Status 字段跟踪工作流阶段，pending_input 字段在上下文压缩过程中保持连续性
  • 大规模重构时的迁移测试至关重要：编写包含所有外部消费者在内的导入契约测试，在重构前和后运行。这为可靠的变更提供了保障（47 次测试 × 2 次运行 = 94 次验证）
  • Tauri v2 的 tray.set_title() 仅适用于 macOS（TokenMonitor 代码中未明确说明）；Windows/Linux 需要使用 set_tooltip() 作为替代方案。这是 Tauri 菜单栏应用在跨平台层面的关键问题
  • 对抗性审查（Critic Agent）能够发现设计盲点：发现了 12 多个问题，包括两个项目之间的关键矛盾。在需求阶段进行红蓝对抗可以避免后续返工
  • 多阶段提示工作流需要在每个边界处明确说明继续执行指令：全局的连续执行命令，每阶段的 “→ NEXT:” 过渡，每阶段的多轮协议。隐含的期望无法发挥作用
  • 从单体平台特定代码迁移到跨平台架构时，完全移除平台特定功能（如玻璃模糊、 Dock 图标可见性）比寻找最低通用替代方案更易于维护——在基础设施代码中，简单性优于功能均等
  • 并行代理执行可以加速独立任务：5 个模块提取代理同时运行，减少了顺序瓶颈。需要明确的任务边界且无需共享状态
  • 规模自适应设计可以提高不同项目规模下的用户体验：≤3 个文件得到简化输出（避免过度文档化），11-50 个文件得到完整处理，50 个以上文件进行架构导向分组（避免上下文溢出）
