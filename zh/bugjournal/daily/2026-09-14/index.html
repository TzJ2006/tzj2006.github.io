Problems & Solutions#

Critical Issues#

1. pi0.5 Libero goal suite 报告 0% 成功率（与报告的 benchmarks 相矛盾）。#

Solution: 在本地运行了未量化的 (float) baseline，达到了 100% 的成功率，证明问题与 quantization 或环境配置有关，而非 evaluation pipeline 本身。

2. 4-bit activation (W4A4) 在 NPU 上的表现明显差于/慢于 FP16。#

Solution: 使用最小化 probe 隔离了原因：NPU 缺乏原生的 INT4 activation kernel，导致 tensor upscaling/expansion 带来了高额开销。

Key Insight: 4-bit activation 是该硬件上的一个性能陷阱；weight bitwidth 可以节省 bandwidth，但没有原生 kernel 的 activation bitwidth 只会增加 unpacking 开销。

3. AI Hub 弃用了 ‘qnn_context_binary’ target runtime，导致自动化失效。#

Solution: 修改了 ‘aihub_submit.py’ 以显式传递 ‘–target_runtime qnn_dlc’，并更新了所有相关的文档/图表 (I-029) 和 RESULTS.md。

4. AI Hub 的 ‘peak_memory’ 字段报告的数据与预期的 model footprint 不符。#

Solution: 对 context-binary（使用 mmap，报告为零 weight footprint）和 DLC（需要显式 allocation）进行了对比，澄清了测量差异。

5. 缺乏用于直接 error recovery 研究的 Out-of-Distribution (OOD) 数据。#

Solution: 将研究重点转向 ‘interface’ 问题：即高层级判断如何通过视觉提示传达给低层级 policy。

Key Insight: 研究瓶颈在于高层级 reasoning 与低层级 execution 之间的通信渠道。

6. Evaluation script 在运行 pi0.5 时泄露约 25GB 的 GPU memory。#

Solution: 确定了 ‘conda run’ 无法将信号转发给 policy server；计划采用 collaborator 的 PID tracking 修复方案。

General Issues#

7. 由于高 Vitest 并发和 WeChat timer thrashing 导致系统无响应。#

Solution: 通过 WPR/xperf 分析进行了诊断，并建议通过 VITEST_MAX_WORKERS 或配置文件来限制 workers。

8. CUDA device indices 与 nvidia-smi indices 之间的混淆。#

Solution: 建议使用 CUDA_DEVICE_ORDER=PCI_BUS_ID 来对齐 indices。

Learnings#

Key Learnings#

  • 在此 NPU 上，权重 bitwidth 是一种线性的带宽节省机制，但只有在消除高 bitwidth ‘islands’（如 softmax）时，activation bitwidth 才能提供收益。
  • Libero 中的 ‘goal’ suite（例如拉动把手）对 action head 中的量化误差高度敏感，这与简单的 pick-and-place 任务不同。
  • Visual prompts 作为高层 VLM 推理与底层 VLA 执行之间有效的通信接口。
  • 如果文件结构未在 idea graph 中正确注册，companion guards (D16/D17) 可能会阻碍 productive work。
