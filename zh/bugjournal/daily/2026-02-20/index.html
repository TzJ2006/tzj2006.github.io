问题与解决方案#

关键问题#

1. run_benchmark.py 每次运行都重新实例化编码器和提取嵌入，浪费了已计算好的 UNI2/SCAN 特征的时间#

解决方案： 将 CacheManager 集成到 has/load/save_*_embedding() 方法中；在编码器实例化前添加缓存检查，支持变异类型（标准/频率/staig_strict）；将覆盖标志传播到两个调用点

关键洞察： 用户期望正确——run_benchmark.py 本应像流程一样使用缓存。AI 最初提出了替代方案（独立评估脚本、手动缓存），而不是修复根本原因

2. BC-RNN 策略预期输入尺寸为 65，但环境提供 37 维，导致 RuntimeError#

解决方案： 根本原因是对象数量不匹配（训练时使用 8 个对象=56 维，评估环境使用 4 个对象=28 维）。修复 _to_robosuite_obs() 以将‘对象状态’映射为‘对象’键，并在注入和自然捕获路径中使用环境原始观测数据，而非使用 StateExtractor

关键洞察： 初始修复仅覆盖注入路径（_generate_from_single_rollout）；自然捕获路径（_capture_single_rollout）也有同样问题。修复观察流程时需要检查所有代码路径

3. eval_scan_fusion.py 的 staig_fusion ARI 约为 0.39，低于预期#

解决方案： 调查发现存在双重归一化错误——未传递 staig_alignment_config，因此 STAIGTrainer 在上游预处理后已使用 StandardScaler，同时未找到之前的 151673 staig_fusion 基线可供比较

关键洞察： “低于预期”没有基线数据属于推测。在假设回归之前必须确认存在基线。此外：独立的评估脚本容易忽略规范流程正确处理的配置细节

一般问题#

4. MimicGen 数据集增强失败，出现‘env_class unexpected keyword argument’ 错误#

解决方案： 修复 robomimic_utils.py 以使用 inspect.signature() 根据 robomimic 0.3.0 API 签名过滤 kwargs，但仍受 pip 安装的 robomimic 中 mujoco_py 依赖的限制。决定跳过 MimicGen，通过更多 BC-RNN/VLA 部署来扩展

关键洞察： 环境隔离问题需要深入依赖分析。当受阻时，应转向替代方法，而非强制使用不兼容的依赖

学习成果#

关键学习点#

  • 当用户质疑冗余工作（“既然已有嵌入，为何重新实例化？”）时，他们通常是在识别本应存在的缺失基础设施——在提出替代方案前，先调查用户的期望
  • 多路径代码库中的观察管道错误（注入与自然捕获）需要全面分析——仅修复某一路径不能保证所有路径都正确；查找该模式的全部使用场景
  • 缓存变体（标准/频率/staig_strict）可避免相同编码器基于预处理标志生成不同嵌入时产生冲突——变体系统比独立编码器名称更稳健

实用学习点#

  • 大规模 GPU 任务从跨设备并行启动中受益，使用不同的日志文件（m12_bc_rnn_injection.log、m12_bc_rnn_natural.log）进行独立监控
  • 环境依赖问题（robomimic 0.3.0 中的 mujoco_py）可能是阻碍因素——遇到障碍时，应转向替代数据源，而非强制使用不兼容的依赖
