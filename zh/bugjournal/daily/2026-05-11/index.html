问题与解决方案#

关键问题#

1. 用户提示过于通用，导致AI误解意图、超出范围并忽略约束条件#

解决方案： 设计必填Spec模板，包含五个必填字段：目标（一句话目标）、范围（可修改/不可修改文件）、约束（库限制、向后兼容要求）、成功标准（可执行验证条件）、非目标（明确排除的工作）。代理必须在执行前完成并获取用户确认

关键洞察： 结构化规格中的必填字段比自然语言提示更能防止AI误解；三个问题点（范围扩展、方向错误、约束忽略）直接对应Scope、Goal和Constraints字段

2. 缺乏验证机制，导致无法确定代码变更是否真正解决问题（例如，预期1000个数据条目但仅生成100个）#

解决方案： 实现验证机制，在spec中定义成功标准（可执行命令如’python test.py’或预期输出字符串）。任务完成后自动运行验证：成功则进入审查，失败则暂停进入调试模式

关键洞察： 验收测试应属于规格的一部分，而非实施后补充；成功标准是“成功表现”的可执行定义，与验证机制概念上相同，而非两个独立步骤

3. PyTorch CUDA包（torch==2.10.0+cu130, torchvision+cu130）无法从标准PyPI获取，导致pip安装失败#

解决方案： 在所有yaml文件中添加–extra-index-url https://download.pytorch.org/whl/cu130到pip依赖部分，以访问PyTorch的CUDA特定包索引

关键洞察： PyTorch CUDA构建需要明确索引URL配置；标准PyPI仅提供CPU版本

4. 源安装包（mimicgen、robosuite、gadget）无法从PyPI获取，导致conda环境创建在pip阶段失败#

解决方案： 在所有yaml文件中添加–extra-index-url https://download.pytorch.org/whl/cu130到pip依赖部分，以访问PyTorch的CUDA特定包索引解决方案： 采用两阶段策略：创建仅包含 conda 的 yml 文件（删除 pip 部分），先安装 conda 包，再从筛选后的 requirements.txt 文件中通过 pip 安装，排除无法获得的包。

关键洞察： 混合使用 conda/pip 环境与源安装包需要手动分离和重建；conda env create 中的集成 pip 阶段无法优雅地处理缺失的 PyPI 包。

5. AI 在测试失败时盲目重试或继续修改，没有推理过程或用户确认#

解决方案： 设计了调试模式，在验证失败时暂停，生成结构化的假设（假设 1：因为 X，所以 Y，证据：代码位置，置信度：高），输出终端摘要和 HTML 详细报告（数据对比图表、执行流程图、突出显示的日志），在修复前等待用户确认方向。

关键洞察： AI 的所有判断必须包含透明的推理链（“因为→所以”）；暂停等待确认比盲目重试更高效；用户需要看到 AI 的思考过程以判断方向是否正确。

6. 缺少跨会话上下文记录，导致下一会话（或其他智能体）无法知道已执行内容及原因#

解决方案： 实现双格式审查日志：人类版本 .md（包含修改文件、理由、影响范围、原始计划与实际结果的对比，适合审查和 PR 描述）和智能体版本 .agent.json（包含 files_modified、理由、推理链、测试结果、下一步行动等结构化 JSON，供下一会话或其他智能体阅读）。

关键洞察： 人类和智能体需要不同的信息密度和格式，单一格式无法同时满足两者需求；人类需要叙述性内容，智能体需要结构化信息；在审查日志中记录原始计划对于“意图与结果”对比非常重要。

7. lifecopilot 环境中依赖冲突导致 pip 安装失败（ResolutionImpossible 错误）#

解决方案： 使用 pip install –no-deps 标志强制安装，不进行依赖解析，接受如果冲突导致运行时问题则需要手动修复。

关键洞察： 严格的依赖解析可能阻碍环境重建；当已知特定版本从原始环境可正常工作时，–no-deps 提供了规避途径。

一般问题#

8. Gadget 仓库自部署在 AGENTS.md 上遇到 PermissionError（WinError 32：进程无法访问文件，因为该文件被其他进程使用）#

解决方案： 由于 gadget 是工作流的源仓库，AGENTS.md、reviews/ 和 workflow/ 目录已完全存在。安装脚本试图覆盖自己的 AGENTS.md 被当前的 Claude Code 进程阻止，但不影响功能，因此跳过此操作。

关键洞察： 安装脚本的幂等性很重要，源仓库和目标仓库的部署逻辑应分开处理（当源仓库已有文件时跳过覆盖）；Windows 文件锁定需要特殊处理。

9. Windows PowerShell 配置文件路径替换因反斜杠转义问题导致 sed 失败#

解决方案： 从使用包含正则表达式的 sed (-replace) 改为使用 PowerShell 的 .Replace() 方法，后者能处理字面字符串而不进行正则解析。

关键洞察： Bash 中的 Windows 路径操作要么需要大量转义，要么委托给原生 PowerShell 命令以实现更清晰的执行。

角色 方法

差异分析： 人类认识到记录原始意图对审查和学习很重要（计划做了什么与实际做了什么，哪些步骤被跳过，出现了哪些新问题），这是反思和改进的基础；AI 只关注记录最终结果，忽略了过程和比较的价值。

差异分析： 人类表现出耐心并将问题解决权委托给 AI；AI 必须通过试错发现 conda env create 中的集成 pip 阶段无法处理缺失的 PyPI 包。

AI 局限性#

关键局限性#

  • 后台任务输出（run_in_background: true）经常被截断或丢失（wc -l 显示 0 行），需要依赖前台执行才能看到实际错误信息
  • 最初低估了社区工具的成熟度，声称“高学习成本”并不准确，后来承认“之前的比较不够诚实”；倾向于使用自定义构建以获得控制，而非优先重用成熟解决方案
  • 倾向于过度分层设计，将概念上统一的项目（成功标准与验证门）拆分为两个独立组件，忽视了用户认知一致性

  • 没有主动考虑在审查日志中记录原始计划，用于意图与结果的比较，只关注最终结果的记录，忽视了流程和反思的价值

学习成果#

关键学习点#

  • 包含必填字段的结构化规范（目标、范围、约束、成功标准、非目标）比自然语言提示更能防止 AI 误解，迫使考虑约束和边界
  • 验收测试应作为规范的一部分（success_criteria），而非实施后补充；success_criteria 是“成功表现方式”的可执行定义，本质上与验证门相同
  • AI 的所有判断必须包含透明的推理链（“因为 X，所以 Y”并附证据和置信度）；在失败时等待用户确认比盲目重试更高效；结构化假设（Hypothesis dataclass）迫使 AI 明确表达推理过程
  • 成熟的社区工具（Spec Kit 95K 个星，Entire CLI 4.3K 个星，git-cliff 11.8K 个星）比自定义构建更可靠，应优先采用这些工具，仅为填补空白而构建自定义版本（如自定义调试模式）和粘合层（如 AGENTS.md 协议）
  • PyTorch CUDA 包必须从 https://download.pytorch.org/whl/cu130 索引安装；标准 PyPI 仅提供 CPU 版本，+cu130 版本字符串无法通过 pip 解析
  • 混合 conda/pip 依赖的 conda 环境迁移非常脆弱；两阶段方法（先安装 conda 包，再单独安装 pip 并允许错误容忍）比集成 conda env create 提供更多控制和恢复选项
  • 跨会话上下文传递需要两种格式：人类版本（叙事形式，适合审查和 PR 描述）与智能体版本（结构化 JSON，适合程序读取），单一格式无法同时满足两者需求
  • 子智能体驱动开发非常适合并行执行独立任务：为每个任务分配新的子智能体（独立上下文），完成后再进行两阶段审查（规范符合性 → 代码质量），避免主会话上下文污染
  • AGENTS.md 作为跨智能体协议比 SKILL.md 更通用，可被 Codex/Cursor/Claude/Copilot 读取；.cursorrules 是 Cursor 特定的补充，结合两者可覆盖所有智能体
  • 从 git/local 路径安装的源包需要在环境重建过程中被识别并排除在自动 pip 安装之外，之后手动重新安装
  • 在审查日志中记录原始计划对审查和学习很重要，使得“意图与结果”比较成为可能（计划做什么 vs 实际做了什么），这是反思和改进的基础

实用学习点#

  • 安装脚本的幂等性很重要，源仓库和目标仓库部署逻辑应分开处理（当源仓库已有文件时跳过覆盖），Windows 文件锁定需要特殊处理
  • bash/sed 中的 Windows 路径操作容易出错；对于 Windows 路径中的复杂字符串替换，委托给原生 PowerShell 命令（Get-Content | .Replace() | Set-Content）更可靠
