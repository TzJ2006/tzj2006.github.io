Problems & Solutions#

Critical Issues#

1. 固定 JVM heap size 掩盖了硬件迁移规划所需的实际内存需求。#

Solution: 实施了动态 sizing (-Xms2G -Xmx8G) 并移除了 AlwaysPreTouch，以实现精确的 profiling。

2. README 太过简略，无法创建完整的 functional manual。#

Solution: 严格遵守原文，明确标记缺失信息而非捏造参数，将真实性置于完整性之上。

3. TPU workspace network mounts 不支持 ‘chmod’，导致 installation 失败。#

Solution: 将代码和 virtual environments 移动到 local boot disk，将 network mounts 留作持久化的 outputs 和 checkpoints。

General Issues#

4. Security guardrails (D21) 拦截了自动化的 shell redirections、pipes 和未经验证的 ‘curl’ commands。#

Solution: 切换到使用专门的 ‘Edit’ tools 进行文件写入，并使用 read-only tools 进行内容检查，以符合项目安全协议。

5. 由于 SSH config 中的 Windows 风格路径，导致 Git Bash 中的 SSH alias resolution 失败。#

Solution: 切换到 Windows 原生 OpenSSH executable 以进行正确的 config parsing。

6. LLM 驱动的 robotic writers 中存在计数滞后和过多的 rings 问题。#

Solution: 提议转向 ‘Event-driven counting’（报告动作而非计数）并实施基于 role 的 glyph filtering。

7. 目录重构后出现 regeneration 和 pathing failures (Fig 2, A7/A8, FUCR)。#

Solution: 更新了 pipeline evaluation scripts 和 analysis queries，以使用新的 canonical directory paths。

AI Limitations#

General Limitations#

  • 当使用 shell redirections、pipes 或未经验证的 installation scripts 时，会被 security guardrails (D21/D26/PreToolUse) 拦截，增加了任务 overhead。
  • 最初未能识别出固定 heap allocation 会阻碍准确的硬件迁移 profiling。
  • 当源文档稀缺时，生成“完整”tutorial 的能力有限。
  • 在隔离环境中操作时，难以管理跨 Git worktrees 的文件。
  • 在没有完整 retraining/retraining cycles 的情况下，无法执行 git commit 或验证 pre-trained weights 上的 rule changes。

Learnings#

Key Learnings- 高准确度研究数据库需要一个 multi-agent 验证循环 (propose -> challenge -> verify) 来捕捉细微错误。#

  • 在 TPU 环境中，使用 local boot disks 进行高-IOPS 活动，并将 network mounts 预留用于长期持久化。
  • 动态 JVM heap sizing (-Xms < Xmx) 对于在生产环境中分析真实的 resource footprints 至关重要。

Practical Learnings#

  • Oracle (80.0) 与 Baseline (19.0) 之间的差距表明 policy architectures 在处理离散的 badge 和 arrow 信号时存在困难。
  • 小样本运行 (N=3) 的方差可能高达 30%，如果没有更大的样本量，细微的性能结论将是不可靠的。
  • 在重构大型数据目录时，务必使 pipeline 中的 ‘writer’ 逻辑与 analysis scripts 中的 ‘reader’ 逻辑保持同步，以避免产生 orphan files。
