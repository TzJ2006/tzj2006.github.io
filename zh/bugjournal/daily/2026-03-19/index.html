问题与解决方案#

关键问题#

1. Post-fusion Harmony 对齐改善了批量混合指标，但降低了跨样本领域检索质量#

解决方案： 分析结果后得出结论，Harmony 的线性校正无法处理非线性维度含义差异，导致各部分独立训练后的不匹配。建议下一轮采用 Joint STAIG 多部分训练。

关键见解： 如 Harmony 这样的批量校正方法假设线性偏移，但当独立训练产生的嵌入具有不一致的维度语义时则失效——批量混合和语义对齐是不同属性。对单独训练的嵌入进行线性校正无法保持样本间的语义对应。

2. CalendarPro 只能处理每条消息的单一意图，丢失了后续操作如“安排下午 3 点的会议并将晚餐时间改为晚上 7 点”#

解决方案： 用 Claude CLI MultiIntentAnalyzer 返回意图列表替代单一意图双重验证流程。更新 _process_message_queue 以循环处理意图并组合响应。移除 7 层关键词覆盖系统。

关键见解： 单一意图分类是根本性的架构限制，而非解析问题。关键词技巧（总是通用、依赖上下文、7 层覆盖）是抽象失效的表现。转向 LLM 原生多意图处理无需所有启发式方法。

3. MimicGen 增强失败：计算了 pos_delta，但从未应用于动作变形，导致成功率低于 5%#

解决方案： 修复 _replay_with_warping，在添加噪声前将 pos_delta 应用于 warped_actions[:, :3]，从而实现正确的以对象为中心的轨迹变换。预期成功率：D0 翻译错误达到 50% 以上。

关键见解： MimicGen 增强需要实际的坐标变换，而不仅仅是噪声注入。10→1000 路径取决于：10 个种子 × 200 个目标 × 50% 成功率 = 1000 次演示。没有 pos_delta 修复，成功率会急剧下降。

4. 对 Yuke Zhu 的初步深度广泛分析使用单个 5MB 提示（100 篇论文全文）远超 LLM 处理能力导致失败#

解决方案： 实施三层解决方案：①在 _MAX_PROMPT_CHARS=150K 阈值中自动触发分割；②按年份分组并当单年过大时按论文拆分的分块算法；③使用 LLM 将 47 个分块分析合并为完整报告。

关键见解： 超大规模文本分析的关键在于“分而治之 + 语义合并”：技术上通过动态分割控制单个 LLM 负载，认知上引导 LLM 提取跨段一致性而非简单拼接。150K 字符约对应 15-20 篇中等长度论文，这是经验最优点。

5. 任务完成模型训练在 grad_norm=0.7-1.0、4% 正样本和 96% 负样本下损失约为 0.035，但停滞不前#

解决方案： 在 BCE 损失中应用正样本加权（pos_weight=10）以平衡梯度贡献，有效将正样本比例从 4% 提升至约 30%。

关键见解： 低损失不能保证不平衡数据集中的正样本召回率良好。当被大量学习过的负样本主导时，仅依赖梯度大小具有误导性。类别不平衡需要明确的梯度平衡。

6. CalendarPro 日历查询在创建事件后立即对“本周”和“明天”查询返回“今天无事件”#

解决方案： 三层修复：（1）在 BASE_SYSTEM_PROMPT 中添加查询意图分类（不使用仅服务于 multi_intent.py 的 INTENT_PROMPT_FRAGMENTS），（2）在 _handle_query() 中增加关键词回退检测以覆盖 LLM 故障，（3）修复 get_today_events() 为 include_past=True 显示已开始的事件，（4）添加 _pending_warnings 用于 Discord 错误反馈。

关键见解： INTENT_PROMPT_FRAGMENTS 和 BASE_SYSTEM_PROMPT 服务于不同代码路径——主 LLM 分类使用 BASE_SYSTEM_PROMPT。关键词回退是可靠的 LLM 安全网。过去事件必须保持可见以防止重新创建。

7. 代码库包含 8 个完全实现的模块（约 2400 LOC），有全面测试，但在运行时未导入，造成维护负担解决方案： 系统化的四阶段重构：(1) 映射所有导入项并识别孤立代码， (2) 将未使用的模块存档并添加说明README， (3) 将重复代码合并到标准位置， (4) 删除真正无用的代码。通过373次测试验证成功。#

关键洞察： 对于完整实现而言，应选择存档而非删除。将孤立但可运行的代码保存在存档/中并附带上下文，便于未来重新整合，同时清理现有代码。审计发现配置变化及导入错误。

8. 由于存在性检查总是失败，导致重复创建了19次早餐、19次午餐、18次晚餐的用餐事件#

解决方案： 将_check_meal_exists函数改为优先使用start_iso字段（ISO时间格式）而非start_time（显示字符串“08:00”）。将schedule_essentials改为get_today_events(include_past=True)，以便已开始的用餐仍可被看到。

关键洞察： 字段解析顺序至关重要——应始终优先使用ISO格式字段而非显示字符串，以避免无声的解析失败。过去事件必须保持可见，以防止重复创建。

9. Gadget总结最终化机制死锁：带有_finalized=False标记的历史日志文件永久存在，导致_finalized永远无法变为True，使得sync-all反复调用LLM合并，浪费API资源#

解决方案： 诊断出根本原因：双层最终化机制（日志+报告）要求所有源日志在报告标记为最终化之前都完成最终化。仅当(target_date != today() AND conversation_count unchanged)时，导出文件才设置_finalized=True。历史日志保持False的原因包括：(a) 当target_date == today()时仅导出一次，因此保持False；(b) 首次导出后对话数量发生变化，导致变为False。_finalized标志嵌入JSON内容中，通过rclone同步。解决方案：在相关日期对受影响的设备重新运行导出——由于日期已过去且对话数量稳定，将自动标记为True。另一种方法：手动将JSON中的_finalized字段改为true并通过rclone上传。

关键洞察： 双层最终化机制要求所有源在报告完成前都进行最终化；通过rclone同步的JSON内容中的_finalized标志确保跨设备一致性；但历史False条目导致永久死锁。核心价值在于节省LLM API资源（合并阶段），而非rclone下载时间。通过“数据修复”方法（重新导出以自动标记）比“逻辑修改”（移除所有_sources_finalized检查会破坏一致性）更能尊重现有架构。

10. 首次采用块大小为60K的分割实现导致100篇论文被分成102个块（每个块约1篇论文），导致LLM调用次数过多且单篇论文缺乏上下文#

解决方案： 将块大小从60K增加到150K，调整分割逻辑以优先保持年份完整性，最终从102个块减少至47个块，显著减少LLM调用次数同时保留时间上下文。

关键洞察： 分割粒度需要在“LLM处理能力限制”和“语义连贯性”之间平衡：过于细碎会丢失时间关系，过于粗糙则引发超时；150K大致对应15-20篇中等长度论文，经验上这是最佳点。

11. 学术数据库同名研究者混淆：Semantic Scholar将多个同名研究者合并为单一个人资料，导致误导性轨迹分析（例如，Yuke Zhu涉及医学成像、计算机视觉和天体物理学——明显是不同人）#

解决方案： AI主动识别分析中的同名混淆信号：领域跨度过大、合著者网络分散、引用数量与论文数量不匹配。在trajectory_summary中标记警告，建议手动拆分或按论文级别分析。对于Yuke Zhu：根据所属机构和研究领域一致性，将其与UT Austin/NVIDIA机器人研究员、Mybank Technology研究员、浙江大学数学研究员以及蚂蚁集团研究员区分开来。

关键洞察： 自动化的研究者画像系统必须包含使用多维度信号的多重名检测模块：合著者聚类、主题聚类、时间连续性、机构归属一致性。不能依赖数据库提供的身份识别功能。

12. 由于_finalized的默认值为True，旧版对话日志在导出时被错误跳过#

解决方案： 将daily_summary.py中的第1726行从data.get(’_finalized’, True)改为data.get(’_finalized’, False)，添加–force标志以明确控制重新导出。

关键洞察： 数据管道逻辑中的默认值必须与语义一致：导出阶段应将缺失_finalized视为未完成（False），而合并阶段可将其视为稳定（True）。

13. 多次分析因LLM超时失败（初始300秒超时不足以处理187K个合并提示，420秒仍不足）#

解决方案： 设计动态超时公式：300 + max(0, (len-50000) // 50000) * 120，即300秒基准，每50K字符额外增加120秒。最终合并步骤在约660秒超时下成功完成。

关键洞察： 超时设计应与数据规模线性相关，而非固定值：大模型处理速度相对稳定（约200-300字符/秒），根据提示长度加50%缓冲时间的估算方法可靠。

14. LLM生成的研究者个人资料JSON长文本字段出现系统性未转义引文问题，导致JSON解析失败（12+次错误）#

解决方案： 在trajectory_summary、breakthroughs().description等字段中手动转义特殊符号（例如，“让机器人…”→“让机器人…”，技术术语中的单引号）；对于截断的JSON对象，根据上下文语义补全缺失的右括号和数组结束符号。

关键洞察： LLM在生成长文本JSON字段时转义嵌入引文不稳定，尤其是在学术文本中频繁引用术语的情况下（例如，“看图理解”变为“边看边动”），引发格式错误。解决方案包括：(1) 在提示中明确要求转义特殊字符；(2) 为超长文本字段设置长度限制或采用多轮分段生成；(3) 在生成后添加JSON模式验证步骤以自动修复常见格式错误。

15. LLM生成的长JSON输出系统性地出现格式错误：截断（尤其是最终字段）、未闭合引文、未转义的中文引号（""）、嵌套结构中缺少闭合括号，尤其是在包含技术描述、中文文本和深度嵌套（>3层）时#

解决方案： 实施四阶段修复流程：(1) 直接尝试json.loads；(2) 提取```json代码块；(3) 基于深度匹配补全未闭合结构；(4) 通过模型升级（haiku→sonnet→opus）进行复杂错误的LLM修复。专门的JSON修复提示指示AI提取并修复JSON，仅返回纯JSON而不提供解释。所有失败记录到outputs/logs/json_repair_failed/用于模式分析和未来优化。**关键洞察：**LLM 长格式 JSON 生成在不同会话中会出现系统性故障，即使提示相同也会如此（字符串转义问题、截断问题或嵌套错误）。单一修复策略不足，需要多层容错机制。中文引号（“”）在语义上有效，但在 JSON 字符串值中必须作为 ASCII 双引号进行转义。生产系统需要生成后的 JSON 验证和自动修复重试机制。

16. 对于高生产力研究人员（130篇以上论文），全语料单遍分析会导致提示长度错误或分析深度不足。Yuke Zhu 的206篇论文分析因“提示过长”错误失败。#

**解决方案：**采用按年份分层的迭代分析策略：按发表年份将论文分组，每轮分析1-3篇代表性论文，深入探究突破点（描述、为什么不先……、影响、技术见解）。在控制单次调用复杂度的同时保持分析深度。论文选择：基于年份的分组 + 引用次数排名 + 会议奖项识别（通过 LLM 识别的最佳论文/亮点/聚焦/口头报告），每年最多10篇。

**关键洞察：**按年份分层的分析策略优于全语料单遍分析（提示过长/分析深度不足）或随机采样（遗漏时间演变）。平衡了时间维度完整性与论文质量。“少量但深入”的迭代模式比“大量但浅层”的一次性模式更适合学术分析。

17. 完成头推理需要重复的 VLM 前缀正向传递（在 sample_actions 中一次，在 predict_task_completion 中一次）#

**解决方案：**创建了 sample_actions_with_completion() 函数，捕获第一个 VLM 正向传递的 prefix_out 并重新用于完成头，返回 (actions, completion_prob) 元组。

**关键洞察：**流匹配去噪占成本优势，但不必要的 VLM 正向传递会增加可测量开销。统一方法通过最小重构消除冗余。

18. 尽管物理连接正常，SpaceMouse 设备打开失败是因为独占驱动锁#

**解决方案：**终止 3Dconnexion 驱动进程，修改 robosuite macros_private.py 设置 SPACEMOUSE_PRODUCT_ID=0xc63a 以访问物理设备。

**关键洞察：**macOS 系统驱动可以独占锁定 HID 设备。使用 macros_private.py 覆盖模式而非修改主配置。

19. 每日报告合并任务：如何避免完全复制所有任务项，而是合成综合视图#

**解决方案：**具体操作：(1)将相似任务合并为一条记录并保留最新状态；(2)整合相同主题人类与 AI 分析；(3)将同一项目的多个会话合并为一次对话总结；(4)在去重时保留重要性较高的项。需要 LLM 理解任务因果关系（例如“实现功能”→“修复错误”→“验证修复”被视为同一工作阶段的阶段）和主题相似性。

**关键洞察：**直接连接会导致信息冗余。合成需要识别任务之间的因果关系（顺序阶段还是真正并行）和主题相似性（对同一模块的重复调试应视为一个具有阶段的任务），而不仅仅是字符串匹配。

AI 局限性#

关键局限- 长JSON生成存在系统性的格式不稳定问题：即使提示词相同，不同会话也会产生不同的错误模式（中文引号混合、截断、嵌套错误等）。在每日报告和研究分析中，需要超过12次修复循环才能处理包含大量中文文本、技术术语和嵌套结构（深度超过3层）的数据。在输出前缺乏JSON完整性的自我验证机制。#

  • 在没有确认是否需要探索时，便在空目录上启动了资源密集型的Explore代理，导致时间被浪费，直到用户中断才停止。
  • 当添加–force标志时，未能对导出与合并阶段的最终默认值逻辑进行审计；需要用户自行发现语义不一致问题。
  • 尽管任务需要整体架构判断，却将代码库审计任务过度委托给3个并行代理。用户意识到这会破坏理解效率，因此停止了委托。
  • 未能识别数据污染风险：最初建议生成场景而不进行训练/测试分割，直到用户明确要求分开的目录。
  • AI在Yuke Zhu分析过程中共尝试5次重试，每次迭代都调整参数（块大小、超时公式），但无法通过单次分析或推理预测最优参数，显著延长了总时间（约2-3小时）。
  • 由于提示词长度限制，无法处理具有完整发表历史（200多篇论文）的研究员资料。包含206篇论文的Yuke Zhu分析因“提示词过长”错误而失败。缺乏针对大语料的内置采样或分层分析策略。
  • 最初仅通过论文元数据无法自主识别同名研究员，需要用户明确标记才能区分不同名称的研究员。经过第一次修正后，能够主动标记机构/领域不一致问题。
  • 在每日报告合并任务中，最初倾向于列举所有细节而非主动整合，需要用户反复强调“重点在于综合与提炼，而非逐字复制条目”，才能触发整合逻辑，表明缺乏“可读性”与“信息密度”平衡意识。
  • 当多次分析同一研究员时，未能识别不同年份论文之间的时间演变关系。每次分析都是孤立的，没有时间因果推断维度。
  • 在分析学术论文时，倾向于描述“做了什么”和“产生的影响”，但挖掘“之前为何不可行”的历史维度需要用户明确提示才能深化。默认结果为技术总结，缺乏历史洞察。
  • 最初无法在没有明确提示的情况下检测研究员名称冲突，生成来自不同研究员的论文统一轨迹，直到用户标记出领域不一致问题。
  • 最初的重命名方案仅涵盖显示名称/代码引用，缺少基础设施层（conda环境、文件夹、仓库、systemd）。需要人工修正以扩展范围。
  • 对性能低效率进行了合理化处理：接受重复的VLM前向传递作为“可接受的开销”，不进行优化，直到用户质疑冗余问题。
  • 在INTENT_PROMPT_FRAGMENTS中添加了查询意图分类功能（仅由multi_intent.py使用），而不是使用BASE_SYSTEM_PROMPT（由主分类流程使用），未理解代码路径差异。
  • 在处理超长文本字段时（例如86篇论文的完整轨迹摘要），存在截断风险，导致JSON对象不完整（field_impact及其他字段在中间被截断）。缺乏主动输出长度监控和警告机制。
  • AI最初选择60K块大小（过于保守导致生成102个块），一次尝试未能识别“合理的块数量”这一隐含约束，需要超时失败反馈后才调整为150K。缺乏关于“用户期望合理的块数量（10-50）”的先验推理。
  • 最初在搜索带有‘from src.browser’模式的模块使用时，未能识别相对导入（来自..browser），错误地将browser/视为死代码。直到直接检查executor.py才发现错误。
  • 无法自主捕捉用户的隐含意图。用户对同一研究员不同年份子集的多轮分析实际上测试了工具的论文选择鲁棒性，但AI unaware这一验证目的。
  • AI批量处理gadget/总结工具导致4-5个日期因API 32000 token输出限制失败，但AI没有主动检测输出长度限制或提出批量处理方案，被动接受失败结果。
  • 无法主动识别自生成的JSON格式错误，需要人工外部验证（如JSON解析器）来发现问题后再提供反馈。
  • 缺乏批处理任务的全局进度跟踪——无法主动告知用户“还需要N天的历史数据处理”或当前完成百分比。用户必须手动跟踪任务进度。
  • 最初设计的每日报告工具为单层端到端生成，缺少分层聚合需求（对话→设备摘要→每日报告），直到用户通过递归架构进行修正。

一般限制#

  • 对领域术语理解错误：‘按标题’和‘按摘要’被误认为可能意味着基于LLM的选择逻辑，而用户实际意思是“仅总结标题”与“总结摘要”。需要明确说明。
  • 处理大量历史每日报告数据时，无法有效跟踪已处理的日期列表和待办任务。需要用户提供的明确任务清单和逐一确认机制。
  • 最初仅添加日历API失败的终端ERROR日志，而非用户可见的Discord消息输出。需要用户说明以理解聊天中错误反馈的产品需求。

经验教训#

关键经验- 如Harmony这样的批量校正方法能够实现全局分布混合，但在独立训练产生维度含义错配的嵌入时无法保持语义对齐。这需要共享训练（Joint STAIG）或基础模型。批量混合与语义对齐是互斥的属性。#

  • MimicGen风格增强本质上属于坐标变换，而非噪声注入。必须对动作轨迹应用pos_delta（源对象到目标对象的偏移量）。若缺乏此操作，10→1000的增强效果会因成功率低于5%而失效。
  • 超大规模文本分析工程范式：①自动分割（15万字符左右，约15-20篇论文的最佳粒度）；②语义合并（由LLM驱动合并而非直接拼接）；③动态超时机制（根据提示词长度线性调整，基准为300秒+每5万字符120秒）；④缓存机制（避免重复尝试的成本）。这四项是深度广泛模式可用的关键要素。
  • 学术轨迹分析多视角验证方法：通过迭代分析同一研究者不同论文子集（从1篇到100篇），可以从微观层面（对单个代表性工作进行深度分析）到宏观层面（完整出版列表的轨迹特征描述）构建立体认知。Yuke Zhu的案例表明：视觉理解（Visual Genome）→具身智能（AI2-THOR）→机器人学习生态系统建设（robosuite/RoboTurk）→LLM驱动的具身智能（MineDojo/Voyager）→几何中间表示与VLM对齐的清晰演变轨迹，只有完整论文列表才能完整呈现这一过程。
  • Yuke Zhu的研究轨迹呈现出清晰的“感知→操控→基础设施→开放世界”演变路径：从2012年初的视觉强化学习到2026年的DreamDojo世界模型，始终以“使机器人能够高效从数据中学习并推广到现实世界”为核心理念。代表了从“数据基础设施构建者”到“基础模型先驱”再到“世界模型架构师”的演进过程。
  • 单一意图分类属于架构限制，无法通过关键词技巧解决。CalendarPro的7层关键词覆盖系统只是解决了抽象失效的问题。多意图LLM分析则消除了所有启发式方法的需要。
  • 二元分类中的类别不平衡需要明确的梯度平衡处理。当96%的样本属于同一类时，较低的整体损失可能会掩盖少数类的学习不佳情况。pos_weight能够有效重新平衡梯度贡献。
  • 分析模式设计关键维度：①数据规模（论文数量/年份）；②分析深度（摘要 vs 全文）；③计算成本（LLM调用次数）。五种模式系统通过两个布尔维度加一个数值维度组合，可满足从“快速概览”到“深度挖掘”的完整需求范围。
  • 结构化数据生成提示工程要点：对于固定模式的JSON输出，必须在提示中明确声明所有所需字段、其类型（字符串/数组/对象）、长度限制、默认值（无数据时使用占位文本）以及特殊字符转义规则。gadget summarize工具每日概览分层格式的发展表明：仅依赖示例推理无法保证输出一致性，必须采用枚举式说明来明确每个字段的生成逻辑。
  • 机器人学习领域研究基础设施构建路径：Yuke Zhu的学术轨迹揭示了重要规律——领域突破通常伴随基础设施类工作（AI2-THOR仿真环境、robosuite标准基准、RoboTurk众包平台、MineDojo互联网规模数据集），这些工作的引用次数虽未超过算法创新论文，但对整个领域发展的实际影响可能更大。对于任何新兴研究方向而言，建立可重复评估基准和数据收集工具链具有更战略性的价值，而非发表单一算法论文。
  • 两级最终处理机制（日志+报告）要求所有源日志在报告完成前完成最终处理；JSON内容中的_finalized标志通过rclone同步确保跨设备一致性；但历史上的错误条目会导致永久性的僵局。核心原则是节省 LLM API 成本（合并阶段），而非 rclone 下载时间。修复方案为：重新执行幂等操作（导出），以自动修正历史元数据，同时遵循架构设计原则。
  • 批量迭代工作流（按日期处理每日报告，按年份进行学术分析）比单次批量处理更可靠，能有效避免 JSON 截断和分析深度不足的问题。对于工具类应用而言，需添加自动重试机制及 JSON 验证功能。
  • 学术数据库中的同音异字消除问题属于自动化研究者画像中的高频且影响重大的数据质量问题。必须通过多维信号建立同音异字检测模块：合著者聚类、主题聚类、时间连续性、机构归属一致性等。
  • 训练/评估数据的分离在机器学习管道中至关重要。评估集绝不能泄露到训练中。不同数据用途需要不同的生成配额和策略。
  • 对于已完全测试的实现，应将其归档而非删除，即便其处于孤立状态。通过归档/说明 README 文件来保留可重新整合的可能性，同时清理当前活跃项目。
  • 数据处理管道中的默认值必须与阶段语义一致：导出时缺失值视为不完整→False，合并时缺失值视为稳定→True。细微的不一致会导致隐性错误。
  • 日期时间字段的解析顺序至关重要——始终优先处理 ISO 格式字段（start_iso），而非显示格式字符串（start_time ‘08:00）以避免隐藏的解析失败导致存在性检查失效。
  • 工具项目的每日报告生成工具在复杂的多设备、多项目、跨时间场景中展现了强大的信息提取与结构化能力。能够准确区分跨设备并行工作，识别任务因果关系，合成对话摘要，验证生产就绪性。
  • 研究分析工具能持续识别 Yuke Zhu 在不同年份论文子集中的核心研究方向与方法演变趋势，证明该工具具备学术轨迹提取能力。
  • Voyager（2023）展示了 LLM 作为自主智能体的模式：在 Minecraft 中独特物品数量增加 3.3 倍，技术树解锁速度提升 15.3 倍。技能以可执行的 JS 代码形式存储而非神经权重，避免灾难性遗忘。
  • Open X-Embodiment（2023）：22 台机器人、21 家机构、16 万项任务展示了跨形态间的积极迁移效果，为机器人数据整合建立了 ImageNet 标准。
  • 研究者个人资料信息密度层级：第一级 = h-index/引用数量（定量指标），第二级 = 代表性作品列表（可枚举事实），第三级 = 研究轨迹叙述（需 LLM 提取隐含演变逻辑）。三层分别对应快速/正常/深入模式输出复杂度。- LLM长文本JSON输出容错性需要多层机制：直接解析→代码块提取→花括号匹配→LLM修复（模型升级）。单一策略无法覆盖所有故障模式。所有故障都应被记录以便人工审查和后续优化。
  • 突破性论文特征分析框架（why_not_before + 影响程度 + 技术洞察）能有效揭示技术创新的历史必然性、领域影响及核心见解，比简单的抽象总结更有价值。
  • 研究者分析论文选择策略应平衡时间完整性与质量。按年份分组+引用数排名+通过LLM识别的会议奖项三层机制可以在可控的计算成本下平衡早期基础研究与近期前沿突破。
  • LLM生成的JSON系统错误模式识别：通过12项以上JSON修复任务发现，未转义引号的错误主要出现在：（1）学术术语引用（如“看图理解”）；（2）中文与英文引号混合；（3）技术名词中的特殊符号（如C++中的+，数学符号如σ_w²）。解决方案需要多层保护：提示词明确要求转义规则+输出格式验证+正则表达式自动修复常见模式。
  • 按年份分组的分析策略优于全语料单次处理（提示词过长/分析深度不足）或随机采样（遗漏时间演变）。平衡时间维度的完整性与论文质量。“少量但深入”的迭代模式比“大量但浅层”的一次性模式更适合学术分析。

  • robosuite提供官方工具（input2action、input_utils）可正确处理设备→动作转换。手动解析action_dict会丢失坐标变换和控制器缩放。
