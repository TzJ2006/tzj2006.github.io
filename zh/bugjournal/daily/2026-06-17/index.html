问题与解决方案#

关键问题#

1. TokenMonitor 单实例启动失败，因为锁定端口被无法终止的进程占用。#

解决方案： 实施 Windows 命名互斥体（Local\TokenMonitor-SingleInstance）作为可靠的 fallback 锁定机制，与 TCP 端口检查结合使用，避免访问被拒绝错误。

关键洞察： 像命名互斥体这样的操作系统级原语能够在 TCP 端口因旧版或受保护进程而失效时提供可靠的单实例 Enforcement。

2. MIHD staig_fusion 输出中基因编码来源的模糊性。#

解决方案： 对嵌入数组进行内容哈希（MD5）处理；真正的编码路径会产生每个基因的唯一哈希值，而 HVG-path 基线则匹配无基因的基础哈希值，从而明确证明来源。

关键洞察： 元数据无法用于科学来源验证；针对已知基线的直接内容哈希是机器学习管道中唯一的可靠验证方法。

3. TokenMonitor 设置中因易变的 slug 元数据（如操作系统标签、哈希）导致设备条目重复。#

解决方案： 在 format.ts 中创建 deviceIdentityKey 辅助工具以去除后缀和哈希值，使用标准化字符串作为去重的标准身份。

关键洞察： 不应使用原始标识符进行匹配；在显示流程早期就需要采用标准表示形式以避免重复。

一般问题#

4. GitHub CLI（gh）在自动创建 PR 时认证失败。#

解决方案： 检测 gh auth 无效情况，绕过直接 API 推送，生成标题/Markdown 内容供手动验证或使用替代 MCP 连接器。

关键洞察： 自动化代理必须预见到本地令牌不匹配的情况，转而生成可执行代码/文本而不是依赖可能无效的会话上下文。

5. ’tianhe2’ 上的 Cursor 远程 SSH 服务器安装失败，由于代理不匹配和损坏的归档文件。#

解决方案： 识别本地 SSH RemoteForward（10087）与远程代理 127.0.0.1:18080 之间的冲突；清理损坏文件，调整端口，并通过隧道手动传输正确的服务器包。

关键洞察： 代理环境变量在会话间保留；本地隧道与远程配置不匹配会导致开发工具无声地连接失败。

经验教训#

关键经验#

  • 对于 Windows 上的单实例应用程序，仅依赖端口锁定方式不够稳健；结合基于 TCP 的 IPC 与命名互斥体可提供强大的冗余机制，以应对被占用或受保护的端口问题。
  • 在审计缺少元数据的科学输出时，针对已知基准进行内容哈希是证明嵌入数组来源最可靠的方法。

实用经验#

  • 使用 git worktree 进行本地开发的仓库应在提交前明确忽略 .claude/worktrees/ 或类似代理工作空间文件夹，以防止未来仓库膨胀。
  • 调试远程工具故障时，应检查本地和远程 Shell 配置中的代理环境变量，因为端口不匹配是常见的隐性故障点。
