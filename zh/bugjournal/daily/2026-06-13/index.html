问题与解决方案#

关键问题#

1. TokenMonitor高CPU：后端循环统计每2秒处理14,769个文件，即使仅追加内容（非结构信息）也会使缓存失效；导出时缺失Cursor/SSH数据。解决方案： 重构了 parser.rs，以区分“目录变更”（全量重新扫描）和“仅内容变更”（增量更新）。通过添加明确的 SSH 刷新操作并接受 local:cursor 源密钥，修复了导出逻辑。#

关键洞察： 缓存失效逻辑必须意识到所检测到的变更类型；确保本地和远程刷新操作的对称性，可保证像导出文件这样的时间点快照保持最新。

2. 研究模块：LLM 超时导致整个流程崩溃，因为 call_llm_raw 仅能捕获 RuntimeError，而 subprocess.TimeoutExpired 则泄露了。#

解决方案： 修复了 common/llm.py，使其统一捕获所有子进程和 SDK 异常，确保超时时返回失败字典而非导致进程崩溃。

关键洞察： 基础设施级别的异常契约必须在所有后端中保持一致，以防止部分失败变成整个系统中断。

3. Windows PC 尽管解决了致命崩溃，却频繁出现 PCIe 可纠正错误（WHEA 事件 17）；Xcode 构建失败也源于环境不匹配。#

解决方案： 编写了解码器脚本，直接解析 WHEA XML，发现所有错误都是监控软件对 GPU 配置空间进行的“不支持请求”良性噪声。对于 Xcode，使用 swiftc -typecheck 作为备用方案，在用户修复 IDE 插件环境之前验证代码正确性。

关键洞察： 被标记为 URI/ANFE 的 PCIe 可纠正错误通常只是软件引起的良性噪声；当高级工具因环境状态而失败时，较低级别的语言编译器有时可作为验证正确性的可靠备用方案。

经验教训#

关键经验#

  • 在诊断基于文件的观察器的 CPU 热点时，检查缓存失效是否过于“广泛”（例如，在仅内容追加时清除最小/最大缓存，因为数学上无法改变）。
  • 高端 GPU 上的 Windows WHEA 事件 17 “可纠正错误”通常是由监控工具探测不支持的 PCIe 配置寄存器引起的，而非物理退化。
  • 在 TokenMonitor 中，archive_completed_hours 是幂等且安全可靠的。这允许安全地扩展归档源（如 Cursor），无需担心重复计数，前提是源密钥有效。

实际经验#

  • Xcode 的 xcstrings 格式使用特定的分隔符（: ）和非字母顺序排序（历史插入顺序）。保持这种顺序对于维持干净的 diff 至关重要。
