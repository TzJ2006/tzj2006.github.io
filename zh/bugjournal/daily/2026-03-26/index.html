问题与解决方案#

关键问题#

1. ccplan 自动执行阶段（4-6）因浅层分析而进展过快，受到“持续执行要求”的推动。#

解决方案： 增加明确的深度要求：阶段4扩展为10个维度，并设定最低发现阈值；阶段5变为4层分析（链/交叉/数据流/合同）；阶段6需至少1次探测及结构化风险评估。

关键洞察： 自动执行阶段需要定量深度要求和最低输出阈值；像“ thorough”这样的定性指示不足以应对效率激励。

2. WebSearch/WebFetch工具返回 标签时，ccplan工作流中断，导致技能列表重新加载并失去阶段上下文。#

解决方案： 添加工具调用状态保存协议，包含3步恢复机制：在工具调用前记录当前阶段，工具返回后重新锚定至 ECL 状态字段，忽略系统提醒元数据；在0/3/7阶段添加内联注释，提示可能进行搜索。

关键洞察： 复杂的多阶段工作流在调用返回大量元数据的外部工具时，需要明确的状态保存协议；无法依赖隐式上下文的连续性

3. 修复漏洞时功能的退化——Claude Code 因上下文压缩而忘记某些功能，导致意外删除#

解决方案： 实施“功能保护协议”，包含包含 feature_guard 部分的持久性 ECL 文档，配备具有安全加固功能的 guard-check.py 命令行工具（包含命令执行的互动确认机制），采用 Phase 10 自动生成方式，以及预修改检查协议

关键洞察： 内存和上下文是短暂的，但磁盘数据却具有持久性。写入 ECL 文件中的保护机制能在不同会话和压缩过程中保留下来。可移植性（随技能目录一起携带）优于针对特定项目的解决方案。

4. Float 球拖拽失败的原因在于 setTimeout 回调中调用了 startDragging()，从而失去了 Windows 所需的指针事件上下文解决方案： 改为手动捕获指针：onPointerDown 捕获指针并记录起始位置，onPointerMove 检查 180ms 阈值并调用 move_float_ball_to IPC，onPointerUp 若低于阈值则切换展开状态#

关键洞察： Windows 要求拖拽操作必须在原始指针事件上下文中启动；setTimeout/async 会破坏这一约束

5. CSS max-height 过渡期间窗口调整导致底部边缘失去任务栏对齐，原因是多次快速的 ResizeObserver→IPC 调用#

解决方案： 将 .detail CSS 过渡改为 ‘opacity 0.8s ease, max-height 0s linear 0.8s’——先通过透明度淡出而不改变布局，随后在延迟后瞬间压缩 max-height，触发单次调整

关键洞察： 影响布局尺寸的 CSS 过渡会在每一帧触发 ResizeObserver；将布局变化延迟到动画完成可避免 IPC 调用风暴并保留窗口重新定位的原子性

6. 浮球展开面板溢出屏幕时靠近边缘；Windows 窗口调整始终以底部为锚点，无论实际位置如何#

解决方案： 添加 EXPAND_MARGIN=8.0 常量以确保展开时与边缘至少保持 8px 距离；实现动态锚点检测，以 5px 为阈值——接触顶部边缘时以顶部为锚点，接触底部时以底部为锚点；添加 SWP_NOCOPYBITS 标志防止旧客户端区域内容被复制回

关键洞察： 展开和收缩状态需要不同的定位策略；锚点应基于当前窗口位置动态确定而非硬编码；Windows 默认调整行为会保留旧内容导致视觉偏移

7. 浮球透明框伪影和悬停延迟由同时存在的窗口系统引起（主窗口全局 CSS + 浮球页面）#

解决方案： 从浮球页面移除全局 CSS 复用，添加 Windows 原生区域裁剪（SetWindowRgn），用统一的 rect 计算重写窗口几何状态机，确保底部边缘始终与工作区底部对齐

关键洞察： 同时存在的窗口系统导致样式和容器堆叠冲突；需要完全分离而非补丁修复

8. 图表悬停细节覆盖解决方案导致元素间视觉重叠，违反 UX 要求#

解决方案： 转向块式布局，通过 onDetailToggle 回调协调明确的窗口高度动画（遵循现有的 AccordionToggleDetail 模式），在 App.svelte 中实现 handleChartDetailToggle 并添加观察器抑制机制

关键洞察： 当涉及原生窗口操作时，在协调动画期间必须抑制被动观察（ResizeObserver），以防止双重触发和视觉伪影

9. 当前成本计算使用本地硬编码定价表，与 ccusage 官方计算不一致#

解决方案： 添加 ccusage CLI 适配器（ccusage.rs），使用 Windows CREATE_NO_WINDOW 静默执行，实现基于优先级的机制（先尝试 ccusage，失败则回退到解析器），UsagePayload 包含 usage_source 和 usage_warning 字段，前端显示明确的警告

关键洞察： 透明回退机制至关重要：不要将降级结果伪装为正常状态；明确告知用户数据来源和限制

10. 非 macOS 平台过于透明，因为 glassEffect 被应用于所有平台而缺乏原生模糊支持#

解决方案： 在 applyGlass() 中添加 isMacOS() 检查以强制非 macOS 为不透明，将默认值改为 false，更新测试快照

关键洞察： 平台差异（macOS 有原生模糊，Windows/Linux 没有）导致相同配置产生不同的视觉结果；需要应用层平台检测和补偿

一般问题#

11. 编辑工具的 replace_all 需要先读取文件；跨多个文件的批量路径更新因“文件尚未读取”错误而失败#

解决方案： 改为使用 sed 进行跨文件批量替换（crate::parser → crate::usage::parser 在多个 .rs 文件中）

关键洞察： 对于跨多个文件的大规模路径更新，shell 工具（sed、grep）优于逐个工具的 Edit 调用，因为存在读前编辑的限制

差异分析： 人类系统地应用“搜索优先”原则并带有质量约束；AI 倾向于立即实施。人类的做法确保从成熟解决方案中学习，而非从零发明。

AI 局限性#

关键局限性#

  • 未能主动识别 ccplan 中的“连续执行要求”会在自动执行阶段鼓励浅层分析；直到用户观察到问题（第4-6阶段过快）后才发现设计缺陷
  • 对 Windows 窗口大小调整行为的理解最初不完整：没有意识到默认行为会保留并复制旧客户端内容，从左上角开始，导致视觉偏移；需要用户指出“内容向上移动”后才添加 SWP_NOCOPYBITS
  • 没有预料到多意图提示处理是需求之一，尽管这是常见的现实使用场景；理论设计忽略了实际使用模式
  • 没有立即意识到可移植解决方案（携带技能目录旅行）在架构上优于项目特定解决方案，适用于可复用组件
  • 初始解决方案（覆盖式）用于图表悬停细节在技术上合理，但未能满足隐含的 UX 要求（无重叠），该要求直到实施后才被明确
  • 在实现固定浮动球行为后，仍保留设置菜单依赖关系，直到用户指出才意识到逻辑一致性问题

一般局限性#

  • 在 ccplan 第0阶段意图校准过程中需要多次调用 AskUserQuestion 来消除歧义，无法直接从上下文中直接推断用户的确切意图
  • 过度依赖规划文档，而用户真正的担忧（“无终端弹出窗口”）是更简单的技术细节；当用户需要直接约束验证时，却花费时间从文档中解释 MCP 逻辑

经验教训#

关键经验- 复杂的多阶段工作流在调用返回大量元数据的外部工具时，需要明确的状态保存协议；不能依赖隐式的上下文连续性。返回标签的工具可能会破坏工作流状态。#

  • 工作流中的自动执行阶段需要定量深度要求（至少N个发现点、M层分析、至少1次探测）以防止“快速但浅层”的行为；像“彻底处理”这样的定性指示不足以应对效率激励。
  • 持久性保护机制（ECL feature_guard）+ 自动化检查（guard-check.py）可以防止不同会话中功能的退化。内存和上下文是短暂的，但磁盘是持久的。测试很理想，但保护机制为增量开发提供了更轻量的安全网。
  • Windows GUI应用程序静默执行子进程的最佳实践：使用std::os::windows::process::CommandExt创建标志加上CREATE_NO_WINDOW（0x0800_0000）以避免控制台窗口弹出。
  • Windows窗口调整大小的视觉锚点控制：默认行为通过左上角复制旧客户端内容导致视觉偏移；需要SWP_NOCOPYBITS来禁用复制并强制完全重绘，再加上动态detect_vertical_anchor来修复适当的边缘。
  • 影响布局尺寸的CSS过渡会触发每帧的ResizeObserver；将布局变化延迟到视觉过渡完成之后（例如‘opacity 0.8s ease, max-height 0s linear 0.8s’）可以防止IPC调用风暴并保留原子窗口重新定位。
  • 基于波形的执行配合验证检查点（cargo check、cargo test、每波后vitest）可以通过早期发现问题来防止大型重构中的级联故障。
  • 使用目录mtime的智能缓存失效比无条件失效更高效；现有的基础设施（DirectoryStamp）可以用于低开销的变化检测。
  • 当涉及原生窗口操作时，在协调动画期间必须抑制被动观察（ResizeObserver），以防止双重触发和视觉伪影。
  • 透明回退机制至关重要：不要将降级结果伪装成正常状态；通过数据模型字段和UI警告明确告知用户。
  • 提示工程技能应在意图提取之前分解多意图输入；单一意图假设是实际使用中的常见失败模式。第一步：多意图分解使得每个跟踪独立处理。
  • 以研究为先的方法结合质量约束（例如，>1k GitHub stars）比孤立发明产生更好的设计；借鉴经过验证的解决方案可以减少盲点。
  • Tauri v2能力系统需要对所有窗口API进行明确的权限声明；缺少权限会导致无声失败（返回null）而不是可见错误。需要：core:window:allow-outer-position、allow-scale-factor、allow-current-monitor以实现拖拽功能。
  • 大文件分解应保持每个模块单一责任，同时将测试代码放在同一文件中；987行的usage_query.rs是可以接受的，因为大部分都是测试。
  • 混合工具策略（复杂逻辑使用并行代理，批量字符串替换使用sed/bash，针对性修复使用直接编辑）在代码库范围内的重构中同时优化正确性和速度。
  • 遵循现有代码库模式（例如，AccordionToggleDetail回调机制）比引入新的通信范式更能实现可维护的解决方案。
  • 跨平台UI一致性问题通常源于平台API差异（macOS的模糊与Windows/Linux的无模糊）；需要应用层平台检测和补偿。
  • 固定的UI行为不应有运行时配置依赖。如果行为是恒定的，代码应通过删除条件逻辑、提高清晰度和可维护性来反映这一点。
