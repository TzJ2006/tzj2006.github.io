  • 实现方式： 创建了多步骤 SLURM 批处理脚本以及基于 tmux 的监控系统，采用并行执行策略，并配置了调试集群访问权限

为 pi0.5 和 mimicgen 基线模型创建了评估管道脚本，但受集群 GPU 访问权限限制无法实施

任务#

实施与修复#

  • ❌ 执行评估运行 — 无法提交 SLURM 作业或向 GPU 节点 (an49, an16 等) 发送 SSH 连接——用户组 ‘sysu_gbli2’ 缺乏所有分区的权限，且 pam_slurm_adopt 在没有活跃作业时禁止 SSH
  • ✅ 创建评估管道脚本 — 开发了 run_full_eval.sh（3步SLURM管道）、launch_eval_tmux.sh（基于tmux的并行执行）和 monitor_eval.sh（状态检查工具），用于运行 pi0.5 和 BC-RNN 评估

问题与解决方案#

关键问题#

1. 向 GPU 节点 (an49, an16 等) 的 SSH 连接被 pam_slurm_adopt 阻止，需要活跃作业才能访问；尽管用户历史记录显示曾直接访问，但 an49 不在任何 SLURM 分区中#

解决方案： 确认 sinfo 输出中完全未出现 an49，建议管理员介入，同时保留可执行的脚本

关键发现： 历史 bash_history 记录中的多次 ‘ssh an49’ 命令证实了之前的访问方式，但节点从集群管理中移除需要管理员恢复权限

2. 所有 xy-a800、ai、lava 及其他分区的 SLURM 作业提交均因“用户组未被允许使用该分区”而失败#

解决方案： 创建了基于 tmux 的替代启动器 launch_eval_tmux.sh，可通过直接 SSH 或 srun 在恢复访问后使用；为管理员升级提供了障碍说明

关键发现： 当集群访问根本中断时，应准备独立的变通方案并提供清晰文档，以便在访问恢复时立即恢复工作，而非不断尝试不同的权限配置

一般问题#

3. 使用 –gres=gpu:1 和 –gres=gpu:2 时，SLURM sbatch 失败，提示“无效的通用资源 (gres) 配置”#

解决方案： 发现集群没有 GRES 配置（sinfo 显示所有节点均为 null）——移除 –gres 参数，仅通过节点分配请求 GPU

关键发现： 并非所有 SLURM 集群都配置 GRES；部分集群在计算节点上直接提供 GPU，无需资源调度

人工智能局限性#

一般局限性#

  • 尽管早期迹象表明没有分区可访问，但仍花费大量时间尝试不同的 SLURM 权限配置（不同分区、明确的 –account 标志、sacctmgr 查询），本应更早转向其他方案
  • 试图使用 –gres=gpu:1/2 而不先验证集群 GRES 配置，导致一次提交周期浪费后才发现 GRES 未配置（sinfo 显示所有 GRES 字段均为 null）

经验教训#

关键经验#

  • HPC 集群访问方式差异很大——始终检查 SLURM (sbatch/srun/squeue) 和直接 SSH 访问，使用 –gres 参数前验证 GRES 配置，并查看 bash_history 以了解历史访问方式
  • 当基础设施障碍根本无法解决（无分区访问、SSH 被 pam_slurm_adopt 阻止）时，应提供可直接运行的自动化脚本及清晰文档，而非临时变通方案，这样一旦管理员恢复访问即可立即恢复工作
