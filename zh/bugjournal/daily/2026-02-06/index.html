问题与解决方案#

关键问题#

1. 公共用户无法向仓库推送，但需要贡献基准测试结果#

解决方案： 设计三层架构：用户向中继端点提交 → 中继验证并将数据转发到 repository_dispatch → GitHub Actions 队列/摄取/发布。中继持有写入令牌，用户没有仓库权限

关键洞察： 众包数据管道需要不可信的摄取路径；带有验证工作流的 GitHub Actions 提供审计跟踪和滥用控制，而不授予贡献者写入权限

2. 条形图渲染时长度倒转（较高分数显示较短条形），尽管 CSV 中的数值正确#

解决方案： 根本原因是二进制编码的图表数据（bdata）和 CDN 版本不匹配。通过以下方式修复：(1) 固定 Plotly JS 与安装的 Python 版本，(2) 将所有图表的 x/y/text 转换为普通 Python 列表而非 Pandas Series，(3) 在加载时强制 flops_gflops 为数值，(4) 设置 yaxis rangemode=‘tozero’

关键洞察： 客户端绘图库中的二进制序列化格式在 CDN 版本变动时可能导致隐式渲染错误；明确的列表转换和版本固定确保可视化确定性

3. 无需用户同意的自动基准测试上传引发伦理问题#

解决方案： 在保存运行后实现交互式提示（默认拒绝），为自动化添加明确的 –upload/–no-upload 标志，在提示前要求配置中继 URL，非交互式运行在指定 –upload 时跳过提示

关键洞察： 遥测和数据收集需要明确的可选性及清晰披露；默认拒绝提示和自动化需要标志的模式尊重用户自主权

4. HOSTNAME_RE 正则表达式过于宽泛，导致有效数据中的时间戳和版本字符串损坏#

解决方案： 将 HOSTNAME_RE 从匹配任何点分隔的令牌缩小为要求顶级域名后缀（.[A-Za-z]{2,}\b），避免对 ‘13.0’ 或 ‘2026-02-07’ 模式产生误报

关键洞察： 隐私净化规则需要精确的边界；过于激进的正则表达式可能导致与 PII 具有相似表面结构的合法技术元数据损坏

一般问题#

5. 趋势图移除不完整，留下导致 AttributeError 崩溃的过时方法调用#

解决方案： 添加兼容性回退 create_trend_chart() 返回空图形，使旧式/过时的调用路径优雅失败而非引发 AttributeError

关键洞察： 通过无操作 stub 的防御性编程可防止重构移除功能时出现脆弱故障；兼容性层平滑迁移路径

战略层面#

公共贡献模式设计#

角色 方法
人类 人类质疑将提交到 GitHub 是否为正确模式（“另一个公共用户如何推送以更改网站？”），并提出交互式同意提示（“在基准测试完成后询问用户是否要上传”）
人工智能 人工智能最初提出 GitHub Pages 流程，直到人类指出不可信贡献者问题才提出；然后设计基于中继的摄取

差异分析： 人类立即识别了初始设计中的安全/访问控制漏洞，并通过同意提示优先尊重用户自主权；人工智能需要明确提示以解决这些问题

上传同意 UX 默认设置#

角色 方法
人类 人类希望在上传前获得明确确认，建议“询问用户：您是否要上传您的结果？”并采用可选行为
人工智能 人工智能在决策树中提供可选和不可选选项，然后根据人类选择实施默认拒绝 [y/N] 提示

差异分析： 人类优先采用带有可选同意的伦理数据收集；人工智能在不进行伦理框架的情况下提供中性选项，直到人类做出明确选择

角色 方法

差异分析： 人类通过渲染输出的视觉检查定位到呈现层的问题；人工智能默认进行数据验证，再考虑可视化特定问题

经验教训#

关键经验#

  • 众包数据管道需要三层架构（不可信提交 → 可信网关 → 受保护存储），并配备验证/审计日志，以防止滥用，同时不授予写入权限
  • 伦理数据收集需要明确的同意选项，并默认禁用提示；自动化场景需要明确的标志，而非依赖交互检测
  • 客户端端可视化错误通常源于序列化格式不匹配而非数据正确性；明确的列表转换+版本锁定可防止隐式渲染失败
  • 隐私清洗规则需要精确的边界条件；过于激进的正则表达式模式可能会破坏合法的技术元数据共享语法并包含个人身份信息

实际经验#

  • 功能移除重构应包含兼容性模板，以便逐步迁移；无操作回退机制可避免因旧调用路径导致的脆弱 AttributeError 崩溃
