Problems & Solutions#

Critical Issues#

1. ButtonUnmask tasks 中的 early memory marks 导致 policy 跳过 subgoals。#

Solution: 在 writer_probe/gemini_v2_env 中添加了一个 ‘prerequisite_done’ latch，要求在视觉/物理感知到第一步之后，必须连续获得 3 个 ‘done’ 信号才能启用 marks。

2. StopCube 具有 low training loss 但 low success rate。#

Solution: 重新计算了 phase-specific loss 并分析了 error distribution，发现 loss 被 ‘waiting’ phases 主导，从而忽略了关键且持续时间短的 ‘pressing’ timing error。

3. 一次性刷新所有数据导致 CPU spikes 和 UI stuttering。#

Solution: 设计了一个 scheduler，将独立的 jobs (archiving, pricing, budgeting) 均匀分布在 refresh interval 中，并使用单一的 atomic publish。

4. Duke LiteLLM proxy 的 API quota exceeded。#

Solution: 等待用户重置 quota 或注入新 key。

5. 由于固定的 ±20% error margin，初始的 budget estimation 太不精确。#

Solution: 实现了一种“基于 stretch”的校准方法，利用一个 model 占主导地位的离散 segments 来计算每个百分点点的真实成本。

6. InsertPeg 失败模式不明确。#

Solution: 分析了 loss 和视频，确定这是一个 contact-precision 问题，而不是 memory 或 learning 问题。

7. Codex limit estimation 缺乏新安装环境的历史数据。#

Solution: 构建了一个专门的 log parser，直接从现有的 Codex session JSONL 文件中 backfill plan budget 数据。

General Issues#

8. Golden test ’test_golden_fusion_gen.py’ 因输出数组的 assertion mismatch 而失败（预期仅为 ‘gt’，而 pipeline 现在写入 ‘gt’ 和 ‘gt_labels’）。#

Solution: 通过 git log (eb3f29d) 确认 dual-write 是为了统一 schemas 的有意架构决策；更新了测试以断言两个 keys 并验证它们的相等性。

9. Minecraft server 在新的 r6a.large 实例上进行 player chunk generation 时出现 lag (TPS drop)。#

Solution: 确定原因是高负载 chunk generation 期间只有一个 physical core (2 hyperthreads) 的限制；建议减少 view distance 或使用 pre-generation tools。

10. AI 尝试使用 shell redirection/piping，这被 system guard 拦截。#

Solution: 切换到使用 Edit tool 来写入文件，并移除了 bash 命令中的 redirection，以符合安全约束。

11. 在长时间运行的 remote tasks 期间出现间歇性 tunnel failure。#

Solution: 集成了自动 tunnel reconnection 逻辑，并通过 remote sleep/ssh 监控 session health。

AI Limitations#

Critical Limitations#

  • AI 未能考虑到不同 models 对 total limit 的影响速率不同（例如 cache hits vs. full input），导致早期估算不精确。

General Limitations#

  • AI 最初在处理由 environment guard 强制执行的 shell command syntax 约束（redirection/piping）时遇到困难。
  • 由于 repository security guards（保护 ‘git commit’ 动词），AI 无法直接执行 git commit，需要人类执行最终命令。

Learnings#

Key Learnings#

  • 在成功取决于单一、短暂且关键动作窗口（例如 StopCube timing）的长程任务中，Average loss 可能会产生误导。
  • 通过单个 model 使用的 ‘stretches’ 来计算 budget，提供了一种能够适应 provider 变化的自我修正准确性机制。
  • training loss 与 success rate 之间的 Rank correlation 可能很低 (-0.51)，尤其是在 ’easy’ 阶段稀释了 loss 时。

Practical Learnings#

  • 对于 Minecraft servers，相比于原始的 vCPU 数量，CPU core count（physical cores vs hyperthreads）和 single-core speed 对于 chunk generation 期间的稳定性更为关键。
  • 当脚本在某一行失败时，同一脚本中后续的其他 assertions 也可能是 stale 的；必须手动探测单个 test functions 以确保完全覆盖。
