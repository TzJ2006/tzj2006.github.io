Problems & Solutions#

Critical Issues#

1. 研究协议约束导致因 ‘audit-hold’ 状态无法启动新的 evaluation jobs。#

Solution: 在 tuning harness 中实现了一种 ‘ready_split_limited’ 状态，允许对 ‘val’ split 进行授权，同时保持 ’test’ split 锁定。

Key Insight: 基于 split 的细粒度授权可以在遵守严格审计限制的同时推进研究进度。

2. Model sharing 和文件管理中的法律与技术风险。#

Solution: 研究了 Hugging Face licenses 以防止 gated models 的非法重新分发，并使用基于脚本的 workaround 来绕过特定环境的 guard hooks。

Key Insight: 遵守 gated model licenses（个人注册）必须优先于简单的文件共享。

3. ErrorRecoveryBenchmark 初次发布中存在的技术缺口和损坏的 scripts。#

Solution: AI 准备了缺失的 BC-RNN configurations，并更新了 training scripts/README 以确保可复现性。

Key Insight: 可复现性要求提供研究结果中所使用的确切 configuration files。

4. 存储耗尽以及开发 artifacts 的不受控增长。#

Solution: 进行了深度磁盘审计，实施了优化的 Cargo profiles (line-tables-only)，并为 Rust caches 创建了自动化的、与工作流集成的 cleanup hook。

Key Insight: 自动化的、由工作流触发的清理比计划性的后台任务更有效且干扰更少。

5. 自动化 Windows scripts 中的文件损坏和执行错误风险。#

Solution: 为 Cargo/Rust 实施了 process-lock checks，添加了 ‘-ExecutionPolicy Bypass’ flags，并使用基于 fixture 的 test suite 进行验证。

Key Insight: 在 Windows 上进行鲁棒的自动化需要显式处理 process ownership、file locks 和 execution policies。

6. 关于 ECE 661 课程资源的信息不一致和安全限制。#

Solution: AI 通过交叉引用多封邮件解决了 credit 差异，并提供了手动 curl commands 以在 API testing 期间绕过 security classifiers。

Key Insight: 官方沟通可能包含矛盾；安全系统可能会拦截自动化的 API testing 以防止数据外泄。

7. 关于 ‘mechanism violation’ 检查和 simulator truth data 的协议边界。#

Solution: 更新了 preregification document，规定如果在缺乏 truth data 的情况下观察到显著收益，则将决策委托给人工审核。

Key Insight: 要求省略 truth data 的协议约束，必须为自动化决策提供显式的 contingency logic。

8. PhD outreach 内容和数据检索的效率低下。#

Learnings#

Key Learnings#

  • 标记为 ‘TPU workspace only’ 的 ECE 661 key 实际上授予了对 Gemini 模型的访问权限，包括 gemini-4-argon。
  • 像 UNI, UNI2-h, CONCH, 和 Virchow2 这样的 gated models 需要个人用户注册，并严格禁止重新分发到共享的 lab directory。
  • 在 dependency packages 中使用 Cargo 的 ‘debug = “line-tables-only”’ profile 是在保留有用 stack traces 的同时显著减小 build artifact 大小的一种有效方法。
  • 在自动化高风险个性化内容时，严格的多轮验证（编写 -> 事实核查 -> checksum 校验）是必不可少的。
  • 实现分级授权（例如 ‘val’ vs ’test’）是在遵守审计强制停滞的同时推进研究的一种有效方法。
  • 在 Windows 上，自动化清理开发 artifacts 时必须对 process handles 和 ‘.cargo-lock’ 文件保持极端谨慎。
