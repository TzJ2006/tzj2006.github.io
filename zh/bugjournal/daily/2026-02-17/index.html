问题与解决方案#

关键问题#

1. MIHD视觉编码器的单模态ARI极低（约0.065），与历史UNI2性能不符；嵌入向量显示出异常模式（最初有许多重复行）#

解决方案： 对tissue_positions_list.csv的深入调查表明，col4是pxl_row_in_fullres（Y轴）而非pixel_x，col5是pxl_col_in_fullres（X轴）而非pixel_y，但代码命名相反。通过分析array_row/array_col的步长变化确认：col4每步变化119.8px（Y轴），col5每步变化68.9px（X轴）。通过修正列名为（pxl_col, pxl_row）顺序解决

关键发现： 数据错误比模型错误更隐蔽：代码运行正常，缓存生成成功，测试通过，但所有结果都基于错误数据。需要从宏观层面的异常（ARI低）追溯到原始数据来源（CSV列定义）。空间距离欧几里得不变性意味着图构建不受影响，但视觉补丁内容完全错位

AI 局限性#

关键局限#

  • 未能独立诊断 MIHD 坐标错误根源；完全依赖用户提供的分析和修复方案。面对“异常低的 ARI”宏观指标时，AI 缺乏自主数据来源追踪能力（从结果 → 嵌入向量 → 补丁提取 → 坐标 → CSV 列定义反向链条）
  • tianhe BC-RNN 集成在两次会话中尝试了三次修复失败；AI 没有预见到 robosuite 不同任务（PickPlace 与 Lift）具有不一致的观察键命名，也最初没有意识到 StateExtractor 重建的观察结果无法保证键名一致性。需要多次用户修正才能找到正确解决方案。使用已废弃的 MuJoCo C API（mujoco.mj_name2id）代替先检查 robosuite 包装器 API，导致三个注入器立即崩溃。应该在修改其他注入器之前，检查现有有效代码（ImpulseInjector）以了解正确的 API 模式
  • 在最初的日常报告工具设计中没有考虑多设备分布式使用模式——假设单设备工作流，要求用户重新设计两阶段架构
  • 在 JSON 接近限制时生成，AI 可能在结构中间截断输出，产生格式错误的 JSON，需要在生产系统中采用防御性解析和修复逻辑
  • ccusage 修复的初期实现错误使用 mb.get(‘model’) 字段，而实际 JSON 中有 modelName，未先验证第三方工具输出结构。导致修复完全无效，直到人类发现数字仍然错误并重新调查。还启动了过多的并行探索任务，导致冗余信息收集（多次读取相同日志文件）
  • 最初建议用 LIBERO/droid 配置测试 VLA 模型，未验证环境兼容性。未能保持语义上下文，即目标环境是 robosuite/mimicgen，而非 LIBERO。需要人类修正以指向适当的配置
  • 跨会话内存不足：2026-02-16 tianhe 会话中的 AI 无法自主回忆前会话的 VLA 检查点下载内容，需要用户提示搜索更广泛的服务器路径
  • 无法主动预测用户对对话摘要等功能的需求——这些产品洞察来自用户对生成报告中空白的观察
  • 处理深度嵌套的元任务困难：当对话中包含关于对话的对话时，AI 难以确定分析哪个层级，缺乏关于任务范围和预期输出的明确指导
  • 在生成 2026-02-17 日常报告时，作为日常报告分析师的 AI 本身成为观察对象——“观察者被观察”的元级复杂性存在。AI 需要分析当天的自身行为（生成日常报告的行为），需要一定的自我意识能力

一般局限- 每日报告自动化部署计划模式设计被用户拒绝；AI未能捕捉到用户意图的变化，也无法判断实施计划的具体性是否符合用户的期望，直接进入退出计划模式，而非先征求用户反馈。多次失败的退出计划模式尝试表明，在判断计划优化完成与用户希望继续迭代之间存在困难。用户在不同会话中三次拒绝该计划，说明AI应询问“此计划是否准备就绪？”而非假设已完成。#

  • 无法直接分析视频内容以评估策略质量。BC-RNN推广视频需要手动提取关键帧并由人工检查以识别机器人悬停行为（忽略抓取目标）。在没有视觉确认的情况下，无法推断0%的成功率，说明模型存在质量问题。

  • 在报告生成过程中遇到API ConnectionRefused错误时，未主动提出替代解决方案（先完全修正数据，再单独处理报告生成）。工作流程解耦的灵活性不足。

  • 创建了包含服务器端和本地客户端指令的长篇统一计划文档，未考虑执行边界。需要用户反馈才能将其重构为可执行的独立成果。项目分解能力较弱。

  • 当用户用中文询问“我们现在在哪里？”时，启动探索型代理并阅读大量文档，而非先检查最近会话上下文或TODO跟踪系统。过度依赖文件读取，而对话上下文可能就足够了。

经验教训#

关键经验教训- 数据错误比模型错误更隐蔽且更具破坏性：MIHD坐标交换错误导致所有视觉实验结果失效，但代码逻辑完全正常，所有测试均通过。需要从宏观层面的指标异常（ARI）回溯到数据来源（CSV列定义）来排查问题。这需要完整的数据科学家思维链；仅靠单元测试无法发现此类错误。#

  • 跨框架集成命名规范差异是隐藏陷阱：robosuite的_main后缀、不同任务观察键名称差异（对象与对象状态）、LiteLLM的模型名-v1后缀——这些细节在文档中并不明显，但会导致运行时错误。机器人模拟框架通过层抽象覆盖原始物理引擎（robosuite封装了MuJoCo）。直接调用API绕过框架层会引发问题——必须使用框架提供的包装器来处理命名规范（如_main后缀）和状态管理。robosuite的观察键命名规则：环境会自动在分组模态后添加-state后缀（例如object → object-state），但训练数据通常使用原始名称。适配器层必须处理这种不匹配问题。最安全的策略是：(1) 使用框架包装的API而非底层API；(2) 使用原始数据结构而非手动重建；(3) 打印实际输出以验证字段名称，而非依赖文档说明。修改前务必检查同一代码库中的可用参考代码。
  • 框架正确性与模型质量需要不同的验证策略。单元测试/集成测试可确认代码逻辑并消除KeyError等错误。视频可视化可揭示行为质量问题（机器人悬停与抓取情况）。即使单元测试通过，GPU集成测试也至关重要——BC-RNN通过了79次单元测试，但需通过GPU部署和可视化检查才能发现0%的SR问题和未充分训练的检查点。每个验证层都有不同的作用。
  • 多设备协作每日报告工具建立了闭环：每台设备导出本地日志 → 中心节点合并远程日志 → 统一部署到Hugo → 发布到GitHub Pages。该流程在2026-02-17被大量使用（处理4个历史日期），证明两阶段架构的可行性。下一步是自动化（用户已提出但未实现）。元工具（用于分析工具使用的工具）需要仔细考虑工作流分配——每台设备上的情况、数据同步方式、部分信息处理方式。两阶段架构（本地导出+集中聚合）比单体单阶段设计更适合分布式场景。
  • 错误恢复基准测试场景库从251扩展至454是渐进式扩展的成功案例：首先实现脉冲注入器（M4）→ 发现需要非脉冲类型（M5）→ 修复MuJoCo API兼容性 → 通过检测器候选扩展机制生成多类型场景。这展示了从最小可行产品到功能完备的迭代路径。错误场景生成是一个漏斗：检测器触发→错误规范生成→注入器应用→验证→场景接受。启用注入器并不保证生成场景——取决于检测器触发频率。不同错误类型的接受率因任务动态而差异巨大。姿态扰动在拾放任务中比摩擦/抓取异常更通用。程序化规范增强（_augment_specs_with_alternatives()）可弥补检测器覆盖不足。
  • 第三方工具集成防御性编程：零成本补丁（ccusage）、字段名称兼容性（modelName或model）、为未来修复设计的自我退化机制（当LiteLLM修复时，回退变为无操作）。这种“仅在必要时激活”的补丁策略可最小化维护成本。第三方工具定价缺陷应通过本地回退机制解决，而非等待上游修复。设计回退应仅在异常值情况下触发（成本=0）以确保向后兼容性。LiteLLM使用版本化模型名（anthropic.{model}-v1带可选:0后缀），而Claude Code日志使用简化名称，导致系统性不匹配。成本跟踪错误可能导致90%以上的低估（观察到13次），严重影响财务规划。定期审计成本指标至关重要。
  • 人机协作效果最佳时，人类指定系统架构和战略决策，AI负责技术实现和优化。本次会议中，用户的架构见解（两阶段设计、多设备同步）非常重要；人工智能的技术执行能力（解析备用方案、配置优化）填补了空白。领域专家的定性判断对于发现系统性问题至关重要。人工智能的数据驱动分析与人类经验直觉形成了有效的互补关系
  • 在不稳定的连接环境下进行远程开发，需要多层防御机制：连接保持活跃（预防）、会话持久性（应对中断）、多重连接（快速重连）以及自动化脚本（恢复）。单层解决方案在真实网络环境中会失败。对于共享服务器账户，用户特定的定制设置应放在条件块或独立的启动脚本中，而非影响所有用户的通用 .bashrc 配置。tmux 同时承担状态持久化与环境边界的功能。会话范围的代理配置（非全局 bashrc）可避免影响其他共享账户用户
  • LLM生成的结构化数据需要采用多种备用解析策略进行防护。原生 JSON 模式（Anthropic 使用 tool_use，OpenAI 使用 json_object）有一定帮助，但无法完全避免失败——始终将修复作为最后手段。每个备用层针对特定失败模式：代码块处理 Markdown 格式，花括号匹配处理截断问题，修复功能处理语法错误
  • 每日总结工具可以从逐步的架构演进中受益：从简单的任务/问题列表开始，添加会话总结以提供上下文，添加优先级元数据以便筛选。每层都满足不同读者的需求。批量文档工作流受益于两阶段架构：（1）基于本地上下文的源文件提取；（2）跨源整合与全局去重。这种模式也出现在总结工具（导出→合并）、MIHD 流程（第一阶段缓存嵌入→第二阶段融合）和错误恢复测试（生成场景→收集数据）中
  • MimicGen 发布政策：仅提供数据集，不提供预训练模型检查点。正式版本可能只提供数据而不提供训练好的模型——在规划前务必确认资源是否可用。BC-RNN（带有 RNN 的行为克隆）是一种简单的监督学习方法：收集人类演示（状态、行为）对，训练 LSTM 预测行为，然后作为策略部署。当有足够演示时，这是处理操纵任务的简单有效基础方案。当无法获取预训练检查点时，从演示中训练成为必要的备用方案
  • 事后工作日志分析（总结过去一周的工作）是一种有价值的实践，能够将原始对话日志转化为结构化的知识成果，有助于在长时间范围内识别模式并跟踪进展- 幂等设计模式（跟踪已处理内容，避免重复工作）对于可能被中断或重新运行的流程至关重要。_merged_devices 跟踪机制避免了在重新处理部分完成的聚合数据时产生昂贵的重复 API 调用。
  • 大型模型资产管理（47GB+ VLA 检查点）需要基于符号链接的组织方式，以避免重复的同时保持集中式可发现性。文件系统中的分散检查点会阻碍可复现性和配置管理。集中化的检查点目录可以提高可发现性。
  • 在修复历史数据质量错误时，将数据修正（导出）与下游消费（报告生成）分离。避免因下游依赖失败（例如 LLM API 不可用）导致整个流程中断。导出阶段依赖 Node.js 工具（ccusage），合并阶段依赖 LLM API——即使合并被阻塞，也可以继续导出。
