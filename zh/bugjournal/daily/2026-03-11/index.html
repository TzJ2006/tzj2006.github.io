问题与解决方案#

关键问题#

1. MIHD 缺陷查询返回错误的物理位置：“查询的补丁与当前补丁不匹配”#

解决方案： 根本原因：缓存（sc.read_10x_h5 顺序）与可视化（sc.read_visium 顺序）之间的条形码排序不一致。通过明确添加条形码到缓存索引的映射来修复：{str(b): i for i, b in enumerate(cache_barcodes)}。同时修正了数据路径和坐标约定。

关键洞察： 当数据源顺序不同时，基于索引的查找会失败。在连接缓存数据和运行时重新加载时，始终使用明确的基于键的对齐方式（本例中为条形码）。

2. K8s 容器 PID 命名空间隔离导致 nvidia-smi 无法显示进程信息#

解决方案： 开发了自定义 GPU 监控工具，通过 /proc//fd/ 扫描 /dev/nvidia* 设备文件和 CUDA_VISIBLE_DEVICES 环境变量。过滤掉打开所有 GPU 的监控工具（nvitop、gpustat、claude）。实现了带有丰富库的 nvitop 风格 TUI。

关键洞察： 容器化 GPU 监控需要检查进程文件系统。/proc/fd 符号链接可揭示已打开的设备；CUDA_VISIBLE_DEVICES 是真实信息。打开所有 GPU 的监控工具属于误报，应通过检查 CUDA_VISIBLE_DEVICES 是否缺失来过滤。

3. 两个项目中相同命令的训练时间相差 33%（openpi 15小时 vs pi05 20小时），尽管硬件和配置相同#

解决方案： 通过并行探索代理识别出 JAX 版本差异（0.5.0 vs 0.5.3）为主要原因。系统性地对齐了 6 个依赖版本：JAX 0.5.0→0.5.3，torch>=2.5.1→2.7.1，orbax-checkpoint 0.11.1→0.11.13，numpy，beartype，transformers。添加 override-dependencies 以解决 lerobot torch<2.7 的冲突。

关键洞察： 较小的 JAX 版本升级（0.5.0→0.5.3）可带来 20-30% 的性能提升，这得益于 XLA 编译器优化；多项目依赖漂移是一种隐蔽性能问题，需要定期进行对齐审计。uv 的 override-dependencies 可精准解决冲突，无需分裂上游代码。

4. MIHD 文件结构因命名不一致而混乱（benchmark_results、hd_results、rm_ideal 分散在多个目录中）#

解决方案： 执行了系统的 8 步迁移计划：创建新的层级结构（DLPFC、HD、rm_ideal/{cross_section,single_section}），迁移文件，更新 14 个代码文件和文档，清理旧目录。使用 bash mv + Edit 工具进行批量路径更新。**关键洞察：**大规模重构需要预先规划（先创建目录），然后迁移文件，接着更新代码，最后更新文档。对于历史文档，批量使用 sed 处理是可以接受的。

5. pi05 训练在启动时失败：‘RuntimeError: operator torchvision::nms does not exist’#

**解决方案：**诊断出 torch 2.7.1 + torchvision 0.21.0 版本不匹配（0.21.0 是为 torch 2.6.x 编译的）。在 pyproject.toml 中明确添加 torchvision==0.22.1 作为依赖项，使用 uv sync 进行升级。验证结果：torch 2.7.1+cu126，torchvision 0.22.1+cu126。

**关键洞察：**PyTorch 和 torchvision 有严格的版本匹配要求（2.7.x 需要 0.22.x）。通过 uv/pip 解决的间接依赖可能选择不兼容的版本——务必明确指定关键的二进制耦合依赖。

经验教训#

关键经验#

– K8s PID命名空间隔离防止了nvidia-smi进程的检测。解决方案：通过检查/proc//fd/中的/dev/nvidia*设备文件，结合CUDA_VISIBLE_DEVICES环境变量。未使用CUDA_VISIBLE_DEVICES打开所有GPU的监控工具属于误报。

  • JAX/XLA小版本升级（0.5.0→0.5.3）可通过编译器优化实现20-30%的训练速度提升；甚至框架层面的补丁级更新也值得在计算密集型机器学习项目中进行性能审计。多项目依赖漂移是一种隐蔽的性能漏洞，需要定期调整。
  • PyTorch/torchvision严格版本配对：torch 2.7.x需要torchvision 0.22.x，2.6.x需要0.21.x等。版本不匹配会导致C++运算符注册失败。使用torchvision时务必在依赖项中明确指定版本，因为间接解决可能失败。
  • 空间转录组学中条形码排序的陷阱：使用sc.read_10x_h5()创建的缓存中条形码顺序可能与运行时sc.read_visium()不同。基于索引的查找会隐式指向错误位置。始终使用明确的条形码到索引映射：{str(b): i for i, b in enumerate(cache_barcodes)}。
  • 当计划模式反复被拒绝时，用户可能存在未明言的障碍（环境不可用、优先级变化、技术限制）。经过2-3次拒绝后，从“让我调整计划”转变为“是什么阻碍了我们继续？”
  • RM-IDEAL中心点计算：对于特定查询领域，取该领域的所有点的嵌入向量，计算平均向量得到中心点。通过余弦相似度与所有参考区域的点进行比较。这可以将N对M的比较压缩为1对M，提高效率和鲁棒性。
  • uv的override-dependencies是一种精确的工具，可用于解决传递依赖冲突，无需拆分或修补上游包；在带有不兼容约束的git修订版本指定时特别有用。

实际经验#

  • 在假设修复方案之前，必须追踪所有来源的配置参数来源（代码默认设置、CLI参数、配置文件、环境变量），因为实际运行时值可能与代码检查结果不同。
  • 大规模代码库重构需要分阶段操作：1）创建新结构，2）迁移文件，3）更新代码引用，4）更新文档（批量sed适用于存档文档），5）验证最终结构，6）清理旧目录。在文件迁移前进行代码更新会导致故障。
