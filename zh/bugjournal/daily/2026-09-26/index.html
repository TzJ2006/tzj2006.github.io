Problems & Solutions#

Critical Issues#

1. 使用通用 visual prompting 时，Gemini 在精确的时序任务（计数、计时和事件检测）方面表现挣扎，导致性能进入平台期并出现 policy 失败。#

Solution: 实施了“任务特定重新设计”（Hybrid Logic）：仅使用 Gemini 回答简单的视觉问题，而将计数、轨迹追踪和计时任务卸载给确定性的 code 和机器人 proprioception。

Key Insight: 将时序和重逻辑任务从 LLMs 卸载到 code 中，可以显著提升机器人操控的可靠性。

2. 由于参数调优/校准，可能存在评估偏差以及测试集（episodes 10-49）的“污染”。#

Solution: 提出使用未使用的 RoboMME ‘val’ 分区进行正式的 validation workflow，以确保真正的泛化能力。

Key Insight: 科学的严谨性要求在真正未见的 validation set 上进行测试，而不是依赖 development episodes。

3. 审计发现启动脚本中存在 bug（case-sensitive env scrubbing、launch_i168_val.sh 中的 broken retry logic，以及 eval_batch_all16.sh 中的 silent exits），且 tianhe3 pod 存在资源超额订阅问题。#

Solution: 实施了 v2 版启动脚本，改进了数据清洗、可靠的 process-group retry 机制，并制定了分阶段 rollout plan 以优化 CPU 利用率。

Key Insight: 大规模 batch jobs 需要能够区分单个 client 退出与整个 process group 完成的 retry logic。

General Issues#

4. 评估循环中的机器人状态滞后导致 VideoRepick 失败。#

Solution: 修复了一个闭环 bug，即 state buffer 清除过于频繁，导致 writer 落后于实际情况。

5. 早期 Gemini 版本在前提条件（例如按钮按下）未满足前就绘制视觉线索，导致因序列错误引发 policy 失败。#

Solution: 实施了基于规则的 latch 机制，要求 Gemini 在绘制 prompt 之前必须确认前提事件已发生。

Key Insight: 对序列敏感的任务需要为视觉反馈设置时序门控（temporal gating）。

Learnings#

Key Learnings#

  • 通过从“要求 LLM 决定一切”转向“向 LLM 提问简单问题并使用 code 处理逻辑”，可以缩小 “Oracle Memory” 与 “Gemini Prompting” 之间的差距。
  • 对于机器人记忆而言，混合方法（Vision + Proprioception + Rules）比单纯依赖 Large Multimodal Model 的生成能力要健壮得多。
  • 大规模 batch jobs 的 retry logic 必须意识到单个 client 退出与整个 process group (arm) 完成之间的区别，否则它会尝试重启正在运行的任务。
