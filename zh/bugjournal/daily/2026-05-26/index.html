问题与解决方案#

关键问题#

1. ECL 验证仅依赖 ‘test -f’ 来检查 12 个功能，尽管已有 480+ 个测试，却无法确保代码功能正常。#

解决方案： 用具体的 pytest 命令替代 ECL YAML 中的文件存在检查，以对应实际功能实现。

关键洞察： 文件存在并不等同于功能正确；验证机制必须执行代码路径而非仅检查文件状态。

2. 用户对通过 Marketplace 的“AWS 上的 Claude 平台”是否符合标准 AWS Activate 信用存在困惑。#

解决方案： 深入研究了 AWS Activate 条款，发现只有 Bedrock 第三方模型有特定例外；明确说明 Marketplace SKU 通常不被计入信用。

关键洞察： 云计费细节往往取决于信用协议中的具体法律定义；在扩大使用规模前必须手动验证。

一般问题#

3. 测试套件执行因 structlog 和 fastmcp 出现 ‘ModuleNotFoundError’ 而立即失败。此外，会话测试在多次运行时存在磁盘状态泄露问题。#

解决方案： 通过 conda 安装缺失依赖项。重构测试，使用 tmp_path fixtures 来严格隔离临时数据库/文件系统状态。

关键洞察： 具有持久存储的集成测试需要严格的隔离策略（如临时目录）以防止测试案例之间的竞态和数据泄露。

AI 局限性#

一般限制#

  • AI 未能立即识别缺失依赖项 structlog 作为测试集合失败的根本原因，最初怀疑是代码层面的问题，而未检查环境要求。
  • AI 在通过 bash 循环遍历仓库时，最初在处理 Windows 路径格式（MSYS2 与原生 Windows 路径）时遇到困难，导致 ENOENT 错误，直到使用 Python 的 os 模块。

学习成果#

关键学习点#
