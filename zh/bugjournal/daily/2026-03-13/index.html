问题与解决方案#

关键问题#

1. 当 Haiku 修复失败时 JSON 解析会严重失败，导致原始 LLM 响应丢失且无法调试#

解决方案： 实现了递归修复链（haiku→sonnet→opus），通过 _try_parse_json 辅助函数避免递归，将失败响应保存到输出/日志/json_repair_failed/.txt 用于调试

关键见解： 当使用基于 LLM 的修复时，必须通过将纯解析逻辑 (_try_parse_json) 与修复触发逻辑（parse_json_response）分离来避免无限递归，并在完全失败时保留原始输出

2. ArXiv 仅返回最近 100 篇论文，Semantic Scholar 有 500 篇论文带有引用数据，但合并逻辑会丢弃没有 ArXiv 匹配的 S2 论文，导致大部分历史高影响力工作被丢失#

解决方案： 反转数据源优先级：S2 成为主要来源（包含年份/引用/会议/摘要），ArXiv 通过 arxiv_id/pdf_url/categories 进行丰富，然后添加孤立的 ArXiv 论文。结果：全面的时间线覆盖

关键见解： 当合并具有不同偏好的数据集时（ArXiv=最新，S2=全面），应以更完整的来源为基础，从专业来源中补充信息，而非相反

3. 仅按引用量排序的论文会丢失时间研究轨迹，使得无法看到研究者关注点在职业生涯不同阶段的变化情况解决方案： 实施了年份分层选择：按年份分组，再按奖项权重和引用数对同一年份内的论文进行排序，每年选取 ≤10篇，按时间顺序展示。在突出各时期优秀作品的同时保留轨迹叙述。#

关键洞察： 对于纵向分析，时间结构比全局排名更有价值；分层抽样能同时保留两种维度

4. manip_progress_distance_left/right 在收集的数据中包含负值和大于1的值#

解决方案： 添加 np.clip(progress_dist, 0.0, 1.0) 以将左右进度距离限制在有效的 [0,1] 范围内

关键洞察： 曲线机器人轨迹可能导致插值过程中当前 EE 位置暂时超过起始到目标距离，破坏 1 - |current-final|/|start-final| 公式的假设。对于进度指标，必须明确限制范围

5. ArXiv 和 Semantic Scholar API 不提供奖项数据（最佳论文、 spotlight 等），但这对识别突破性成果至关重要#

解决方案： 用户建议利用 LLM 训练数据：将论文标题+会议地点发送给 LLM，让其回忆已知的奖项。作为新的分析阶段实现，并采用独立缓存机制

关键洞察： LLM 可以作为通过 API 无法获取数据的辅助知识库，尤其适用于具有声望但非结构化的元数据，如会议奖项

6. 即使删除覆盖方法，HDF5 文件中仍出现 critical_region#

解决方案： 分析基类 _base_task.py:510，发现 get_obs() 无条件写入 pkl_dic[‘critical_region’]。添加后处理步骤，从修复后的 pickle 文件中移除该键

关键洞察： 删除覆盖方法仅改变返回值；必须追踪基类代码路径，确保输出中真正移除这些键。在 HDF5 转换前对 pkl 文件进行后处理可有效去除不需要的键

一般问题#

7. 日志消息 ‘[S2] 获取论文: 1736651’ 模糊——看起来是获取了170万篇论文，实际上是作者 ID。用户立即发现了这个问题#

解决方案： 改为 ‘[S2] 获取作者 1736651 的论文…’ 和 ‘[S2] 作者 1736651: 获取到 500 篇论文’。明确的主语-谓语-宾语结构消除了歧义

关键洞察： 即使从上下文中阅读，日志消息也必须清晰明确。数字应始终有明确的标签以表明其语义类型

8. 详细模式仅下载了排名前10的论文全文，但经过年份分层选择后每年已有 ≤10篇论文——应在详细模式下分析所有论文#

解决方案： 移除 ‘sorted(…, reverse=True)[:10]’ 过滤，改为 ‘papers_for_download = [p for p in papers if p.arxiv_id]’。现在下载所有筛选出的论文全文

关键洞察： 当选择逻辑已经在上游强制执行质量阈值时，下游不应使用不同的标准进行重新过滤——这会导致不同模式间的不一致

经验教训#

关键经验#

  • 对于研究人员轨迹分析，时间结构保留（年份分层采样）比全局引用排名更有价值。表明领域特定的采样策略比通用的“按指标排序”方法更重要
  • 针对“未来依赖”变量的后处理方法：当每帧变量需要了解move()完成状态（如目标姿态）时，正常记录帧数然后在move()完成后修补pickle文件比在帧捕获期间使用复杂的状态机更简洁
  • LLM可以作为非结构化元数据（会议奖项、论文声誉）的知识库，当API无法提供时。这种“LLM作为辅助数据库”模式未被充分利用——需要提示词设计技巧，但无需基础设施
  • 在递归解析逻辑中实施基于LLM的修复时，必须将非LLM阶段提取为独立助手以避免无限循环。模式：_try_parse（纯）与parse_response（带修复）
  • 多源数据合并：当来源具有不同偏见（近期性 vs 全面性）时，以最完整的数据为基础，并从专业数据中补充。ArXiv=近期，S2=历史 → S2基础 + ArXiv补充
  • 错误恢复应实现成本递增的升级机制（廉价模型→昂贵模型→通过日志人工干预），而非二元失败/成功。在保持调试信息的同时最大化自动恢复能力
  • 基类数据流需要深度追踪：在具有每帧数据收集的复杂OOP层次结构中，删除覆盖方法可能不会移除输出中的键。必须追踪基类执行路径（如get_obs() → _take_picture() → pkl文件），以确保变量真正被排除
  • 物理量需要语义边界约束：从几何公式推导出的进度指标应明确限制在其语义范围[0,1]内，即使公式理论上能产生有效值，因为现实世界的轨迹会引入边缘情况

实践经验#

  • 现在更倾向于使用ArXiv HTML渲染而非PDF进行全文提取：更快，无OCR错误，保留结构。对于HTML前的论文，备用PDF格式。表明基础设施演变需要定期重新审视“最佳实践”
  • 没有语义标签的日志数字会产生歧义：‘1736651’可能是数量/ID/大小。始终使用明确标签：‘作者 1736651’或‘1,736,651篇论文’。成本是多两个词，好处是消除整个解释错误类别
  • 对于学术分析工具，叙述部分 prefer中文输出，技术术语prefer英文。双语方法：结构用英语（突破、为何不之前、影响），解释用中文
  • 当选择逻辑在上游存在（年份分层→≤10/year）时，下游阶段不应使用不同标准进行重新过滤。导致模式不一致（快速模式看到与详细模式不同的论文）
  • 多智能体探索模式：使用Explore智能体理解代码库 → Plan智能体设计 → 顺序实现并经过用户验证，形成清晰的职责分离，允许在执行前审查计划
