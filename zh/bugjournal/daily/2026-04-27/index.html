问题与解决方案#

关键问题#

1. 当悬停图表条时，窗口高度快速波动（150-200ms 周期），导致细节面板在连续反馈循环中闪烁#

解决方案： 实现了三层防御：(1) onLeave 计时器检查 hoveredIdx >= 0 以跳过假离开事件；(2) ResizeOrchestrator 在图表悬停激活期间阻塞观察者驱动的调整大小；(3) 收缩保护防止悬停时窗口缩小

关键洞察： 波动是一个反馈循环，SetWindowPos 改变窗口位置导致浏览器触发假 mouseLeave 事件；打破循环需要在多个点进行干预，而不仅仅是阻止调整大小

2. SetFocus Win32 API 要求调用线程拥有前台窗口，但托盘点击处理程序没有前台权限#

解决方案： 使用 SetForegroundWindow，它在托盘图标上下文中具有隐式前台权限，并在 Svelte 中添加 200ms fallback 计时器以处理边缘情况

关键洞察： Win32 前台窗口规则依赖于上下文：托盘图标事件授予 SetForegroundWindow 前台权限，但不授予 SetFocus；理解上下文至关重要

3. 调整大小时窗口底部边缘从任务栏偏移，产生视觉差异；使用 current_rect.bottom 会导致底部边缘不可预测地跳动#

解决方案： 将 anchored_resize_origin 从 current_rect.bottom - height 改为 work.bottom - height；工作区域边界是稳定的常量，而 current_rect 反映中间异步 SetWindowPos 状态

关键洞察： 在异步窗口管理系统中，快速变化期间的“当前状态”查询返回中间值导致不稳定；应基于固定参考点（工作区域边界）而非当前状态进行锚定

4. 硬编码的底部右侧锚点导致任务栏在其他位置或用户/系统重新定位时出现闪烁#

解决方案： 构建了动态锚点检测：比较窗口中心与工作区域中心，将结果存储在 AtomicU8 中，在所有位置调整函数中使用检测到的锚点

关键洞察： 窗口锚点必须基于相对于工作区域的实际位置动态检测，而非假设为默认任务栏位置

5. 即使速率限制 API 正常工作，Cursor 使用警告仍会显示，导致用户对实际连接状态产生困惑#

解决方案： 将远程使用事件 API 失败从 set_cursor_warning 降级为日志；仅在认证真正不可用时警告（两个管道均失败）

关键洞察： 提供不同功能的多层数据管道应独立失败——当另一个管道正常时，不要因一个管道失败而警告用户

6. 使用 clientX/Y + getBoundingClientRect 的鼠标位置检测无法防止窗口移动时的假离开事件#

解决方案： 放弃基于坐标的检测；改为在计时器回调中检查 hoveredIdx 状态——如果 300ms 后 hoveredIdx >= 0，则重新进入，因此跳过离开事件

关键洞察： 当窗口移动时，pointermove 不会触发（鼠标实际上没有移动），因此跟踪坐标会变得过时；基于状态的检测（hoveredIdx）比基于坐标的检测更可靠

7. 用户必须手动重新打开 Cursor 并重启 TokenMonitor 才能解决认证令牌失效时的黄色“已连接”警告状态解决方案： 实现了跨平台应用启动命令（macOS open -a、Windows .exe 路径、Linux cursor 命令）和 retry_cursor_auth 轮询机制，该机制能自动检测令牌刷新并清除警告信息#

关键洞察： 带有计时器的自动重试模式可防止资源泄漏；每 4 秒轮询约 32 秒，能在响应速度与资源使用之间取得平衡

8. 当窗口底部锚定在任务栏时，由于 14px border-radius 导致窗口底部边缘出现透明间隙#

解决方案： 通过 get_window_anchor_edge IPC 在启动时查询窗口锚点方向，在 中设置 data-anchor 属性，当 data-anchor=‘bottom’ 时在 CSS 中条件性移除底部 border-radius

关键洞察： 带有 border-radius 的透明窗口在边缘与屏幕边界对齐时会产生视觉间隙；需要根据运行时锚点位置进行条件化样式设置

9. sqlite3 命令执行时缺少 CREATE_NO_WINDOW 标志，导致 Windows 上控制台窗口弹出#

解决方案： 在 cursor_parser.rs 中添加了 const CREATE_NO_WINDOW: u32 = 0x0800_0000 和 #[cfg(target_os = “windows”)] 保护下的 .creation_flags() 调用

关键洞察： 所有 Windows 进程启动都需要明确使用 CREATE_NO_WINDOW 标志；任何模块中缺失一次这样的启动都会破坏整体用户体验

经验教训#

关键经验- UI 系统中的反馈循环可能具有不明显的触发机制：窗口调整大小 → 位置变化 → 浏览器事件 → 状态变化 → 再次调整大小。打破这一循环需要识别多层的正确干预点#

  • Win32 前台窗口规则依赖于上下文：SetFocus 需要调用线程拥有前台焦点，但 SetForegroundWindow 从托盘图标事件上下文中具有默认权限——这对系统托盘应用程序至关重要
  • 异步窗口管理（SetWindowPos）意味着在快速变化期间查询“当前状态”（GetWindowRect）会返回中间值；稳定的锚点（工作区域边界）比查询当前状态更可靠
  • 窗口移动过程中的浏览器鼠标事件从用户视角看是“假的”，但从浏览器视角看是“真实的”；需要基于状态的检测而非坐标检测，以区分真正的用户操作与窗口移动产生的伪象
  • 多层数据管道设计：当管道处理不同功能（速率限制与使用事件）时，故障处理应反映功能的独立性——不要因一个功能的故障而阻塞另一个功能
  • Svelte 5 反应性机制：$state 更新通过微任务队列更新 DOM 变化，但 CustomEvent 分发是同步的——在 DOM 更新之前进行测量可能导致竞争条件
  • 自动重试模式设计：使用 onDestroy/cleanup 防止计时器泄漏；平衡轮询频率（4 秒）和最大尝试次数（8 次），适用于覆盖典型认证刷新时间的 32 秒窗口
  • 带有 border-radius 的透明窗口需要仔细考虑锚点位置，避免屏幕边缘出现视觉空白；基于运行时锚点检测的条件样式解决此问题
  • Tauri v2 IPC 命令模式：使用 #[tauri::command] 定义 Rust 命令，在 invoke_handler 中注册，通过 invoke() 从前端调用；需要针对外部应用启动进行平台特定的处理
