问题与解决方案#

关键问题#

1. TokenMonitor 的主界面显示陈旧成本，因为 SSH 同步后磁盘缓存从未被清除，只有内存缓存被失效。#

解决方案： 在 sync_ssh_host、clear_usage_view_cache 和后台 SSH 同步循环中添加 disk_cache.clear_prefix("usage-view:") 调用，确保始终重新计算最新数据。确认尽管之前担心“天和”设备记录，但并未发生原始数据丢失。

关键洞察： 在持久化桌面环境如 Tauri 中，一个层（内存缓存）的状态持续存在，而另一个层（磁盘缓存）却被清除，导致视图不一致；在无效化过程中必须同步两者。

2. Claude CLI 在处理复杂的日历请求时始终超时（120秒）且无输出，原因是 Windows shell=True 在生成子 MCP 进程时导致 stdio 死锁。#

解决方案： 发现继承的管道句柄导致隐式死锁。通过在子进程调用中设置 shell=False 并使用原生会话持久性（--resume）来管理上下文，从而解决死锁问题，确保可靠执行和内存保留。

关键洞察： Windows cmd.exe shell 行为中的 Popen 和子进程继承可能导致不可见的 silent stdio 死锁；需要经验性隔离测试来识别具体原因。

一般问题#

3. LifeCopilot 中启动服务器的多种方式导致配置漂移，而 TokenMonitor 中的新 SSH 设备因配置不匹配默认排除统计信息。#

解决方案： 将所有预检查逻辑集中到 launcher.py 中用于 LifeCopilot。在 TokenMonitor 的 Rust/TS 层标准化默认标志，确保“已连接”设备自动包含在成本报告中，除非明确选择排除。

关键洞察： 配置管理应编码为单一可执行脚本或统一存储，而非分散处理，从而减少认知负担并防止配置漂移。

经验教训#

关键经验#

  • 在 Windows 上，使用 subprocess.Popen 与 shell=True 启动生成自身子进程的过程（如 MCP 服务器）可能导致 handle 继承引起的 stdio 死锁。除非严格必要，否则避免使用 shell=True 进行命令解析。
  • 在 Tauri/桌面应用中，状态变更时务必同时清除磁盘缓存和内存缓存，以防止旧数据泄露；远程同步缓存是临时的，没有持久性归档。

实际经验#

  • 在调试 CLI 工具或 UI 差异时，始终通过可视化证据验证原始负载和缓存键，以区分缓存层与计算逻辑，而非仅依赖代码追踪。
