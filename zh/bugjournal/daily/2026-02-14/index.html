问题与解决方案#

关键问题#

1. MIHD 基准测试：冗余嵌入计算 - 相同的基因/视觉编码器针对不同融合策略运行数百次（例如，PCA 计算了 55 次，UNI2 计算了 77 次）#

解决方案： 设计了并实现了两阶段流水线：第一阶段提取并缓存所有编码器嵌入（去重，110 任务用于 286 次实验 = 减少了 62%），第二阶段加载缓存的嵌入并仅执行融合+聚类+评估。现在 UNI2 模型在所有 11 个部分中只加载一次，而非 77 次。**关键洞察：**当前的缓存使用 {gene}_{vision}_{fusion}/{section}_embeddings.npz作为键，包含融合名称，因此改变融合方式会导致重新提取。编码器级缓存（gene_cache/{encoder}/{section}.npz, vision_cache/{encoder}/{section}.npz）能够实现大量复用。不同部分之间的模型实例复用可进一步提升速度。

2. 错误恢复基准测试：对错误的身体施加力（bin2 而非夹持器 EEF），视频中无机器人异常现象#

**解决方案：**通过详细日志发现力被施加到 bin2 上。根本原因：_get_eef_body_name() 未在 possible_names 列表中包含 ‘gripper0_eef’，回退几何搜索匹配了 robot0_screen_collision（包含 ‘ee’）→ bin2。通过在 possible_names 中添加 ‘gripper0_eef’, ‘robot0_right_hand’, ‘gripper0_gripper_base’ 解决了问题。

**关键洞察：**机器人的 EEF 身体名称各不相同（Sawyer 使用 gripper0_eef，而非通用的 gripper_link），需在 possible 名称列表中明确包含。回退到几何搜索可能导致包含 ‘ee’ 的字符串与无关几何模型匹配。

3. 错误恢复基准测试：PreGrasp 检测器从未触发——get_task_phase() 始终返回 ‘unknown’#

**解决方案：**根本原因：get_task_phase() 调用了 _check_phase_condition()，该函数是一个空实现，始终返回 False。所有依赖 task_phase 的检测器（PreGrasp, GraspPrecond）均受影响。完整的阶段检测逻辑存在于 get_task_completion_stages() 中。通过重写 get_task_phase() 以使用基于传感器的检测解决了多个连锁错误：前视使用中性动作而非演示动作，接近门阻止预接触检测器，全局冷却时间导致无法同时检测，MuJoCo 身体名称不匹配。

**关键洞察：**代码库中存在功能实现良好的 get_task_completion_stages 和始终失败的空实现 (_check_phase_condition)，调用者使用了错误的方法。现象是检测器不触发，根本原因是基础设施层死代码。当观察到逻辑矛盾（无拒绝但无输出）时，应优先进行基础设施审计而非症状调试。

4. 错误恢复基准测试：duration_steps 配置参数无效——所有力仅持续1步（0.05秒）#

**解决方案：**MuJoCo 在每次 sim.step() 后自动清除 xfrc_applied。解决方案：修改 collect_rollout_stats() 在验证迭代的 first duration_steps 期间循环调用 injector.apply()，在持续时间结束后调用 injector.clear()。

**关键洞察：**MuJoCo 的 xfrc_applied 是一个持久字段但会被自动清除，需要应用层显式重新应用每一步以维持力作用。这是影响所有错误类型的系统级错误。

5. 错误恢复基准测试：30N 力在可视化视频中无机器人手臂运动#

**解决方案：**添加 –force_override 参数以测试更大的力而不进行再生；更新配置力范围至 15-45N。在 30N 下问题仍然存在——需要调查力机制（可能是 OSC 控制环过强，1步时的力持续时间过短，或 xfrc_applied 应用不正确）。

**关键洞察：**力注入机制工作正常（xfrc_applied 被设置/清除），但 30N 可能不足以对抗 OSC 控制器的 150 N/m 刚度，或 1步持续时间（约 20ms）对于可见效果来说太短。OSC 控制环可能在一个控制周期内就抑制了外部力。

6. CalendarPro：用户无法删除符合模式的多个日历事件（例如“3月1日之前取消所有 GB 教师会议”）——机器人仅能说“请指定要删除的事件”#

**解决方案：**扩展数据模型以支持日期范围和批量操作，更新 LLM 提示以提取这些字段，修改搜索以接受自定义时间窗口，添加带有 Discord 按钮的互动确认界面，显示预览并明确用户批准。

**关键洞察：**对于生产力工具而言，单项 CRUD 操作不足——带有安全确认的批量操作（预览+用户明确批准）对于涉及模式的用户工作流程至关重要。

7. Gadget/summarize：无头服务器无法安装云存储应用以实现自动同步#

**解决方案：**研究并集成 rclone CLI 工具，支持令牌复制认证方式（在机器上通过浏览器运行 rclone authorize，将令牌复制到无头服务器）。

**关键洞察：**rclone 支持 70 多种云提供商，通过令牌复制的无头认证是最佳跨平台云 CLI 选择。

8. 错误恢复基准测试：全局冷却时间阻止了预抓取检测器，当接近触发时先执行冷却#

**解决方案：**实现每个检测器冷却追踪（cooldown_counters 字典），使每个检测器具有独立的冷却周期。过滤检测结果以移除仍处于冷却中的检测器。

**关键洞察：**对于多个检测器系统而言，全局冷却时间不适合，因为不同检测器针对不同的阶段/条件。多检测器系统需要每个检测器的冷却追踪。

9. CalendarPro：Google Calendar API 在每个用户消息中返回 403 insufficientPermissions，导致控制台警告#

**解决方案：**从 calendarList().get() API 改为 settings().get(setting=‘timezone’) API，后者仅需要 calendar.events 范围而非更广泛的日历访问权限。

**关键洞察：**不同的 Google Calendar API 端点需要不同的 OAuth 范围——用于获取时区的 settings API 的权限要求低于 calendarList API。

10. CalendarPro：当 LLM 超时（嵌套 Claude Code 环境）时，批量删除失败因为 intent.data 为空——语义路由器正确分类意图，但未提取结构化数据#

**解决方案：**在处理程序中添加 _raw_input 直接传递，实现 _extract_delete_query() 并使用正则表达式模式从中文/英文短语中解析搜索关键词，添加日期提取模式以识别如“3月1号前”这样的范围。

**关键洞察：**双验证系统需要在两条路径中拥有独立的提取能力——仅依赖 SR 的回退无法完全依赖 LLM 生成的结构化数据。

11. Gadget/summarize：ccusage –offline 模式显示 Opus 4.6 费用为 $0#

**解决方案：**移除 –offline 参数，切换至在线模式以获取最新模型定价。

**关键洞察：**离线模式的定价表不包含最新模型（如 Opus 4.6），需要在线获取以获得准确计费。尽管在线模式稍慢，数据准确性更为重要。

12. 错误恢复基准测试：接近门（max_eef_object_distance=0.05m）阻止了在 0.05-0.1m 范围内操作的 Pregrasp#

**解决方案：**添加检测器名称以绕过列表进行门检查——具有自身距离验证的检测器（pregrasp, grasp_precond）跳过门检查。

**关键洞察：**接近门是为基于接触的检测器设计的，但被错误地应用于所有检测器，无论其操作距离如何。检测器特定的约束不应被全局门覆盖。

13. CalendarPro & gadget/summarize：嵌套的 Claude 代码会话块以及 Claude CLI 子进程调用，导致在开发过程中大语言模型分类总是超时解决方案： CalendarPro 在启动子进程时试图取消 CLAUDECODE 环境变量，但依然失败——最终解决方案是在外部环境中进行测试。Gadget/summarize 成功在子进程环境中取消 CLAUDECODE 和 CLAUDE_CODE_ENTRY。#

**关键洞察：**开发环境工具可能会以非直观方式干扰被测试系统——基于子进程的 AI 服务调用对环境污染特别敏感。子进程会继承父环境变量，需要明确删除。

**解决方案：**在 subprocess.run 调用中添加 shell=True 参数。

**关键洞察：**Windows npm 全局命令实际上是 .cmd 文件，Python 子进程默认不会解析，需要通过 shell 执行。

15. Gadget/summarize：LLM 返回的 JSON 可能包含代码块或在前后有解释文本#

**解决方案：**实现三步法 JSON 解析：直接解析 → 提取 ```json 代码块 → 查找 {to} 子字符串。

**关键洞察：**LLM 输出格式不稳定，需要多层 fallback 以确保稳健。

16. Gadget/summarize：同一天/设备下的多次导出会覆盖现有对话记录#

**解决方案：**当检测到现有文件时，根据 (source, project, timestamp) 元组进行去重后读取并合并。

经验教训#

关键经验- 实验矩阵的两阶段流水线模式：在运行 M 编码器 × N 融合 × K 段时，分为第一阶段（执行 M × K 编码任务并使用缓存）和第二阶段（从缓存加载 M × N × K 评估任务）。通过共享编码将 O(M × N × K) 的冗余计算简化为 O(M × K + M × N × K)。缓存键设计很重要：编码器级缓存使得不同融合之间可以共享。#

  • MuJoCo xfrc_applied 行为：虽然文档说明 xfrc_applied 会在调用间保留，但 mj_step() 会自动清除它。要实现持续力效果，需要在应用层显式重新执行每一步。在 duration_steps 结束后必须通过 injector.clear() 显式清除，才能实现真正的脉冲行为。
  • STUB 方法和完整实现并存属于代码异味：当某个函数中存在完整逻辑，但调用者使用总是失败的 stub 时，应该立即审查调用关系，而不是调试参数。当观察到逻辑矛盾（没有拒绝但也没有输出）时，应优先进行基础设施审计而非症状调试。
  • 力注入可视化平衡：OSC 控制器在 kp=150 N/m 时，需要力 ≥25N 才能看到位移，但 OSC 控制回路可能在一次控制周期内（约20ms）抑制外部力。需要在力大小和持续时间之间仔细平衡。
  • 生产力工具需要带有安全机制的批量操作：(1) 模式匹配以查找多个项目；(2) 预览将受影响的项；(3) 执行前明确用户确认。单项目 CRUD 操作不足以满足实际工作流程需求。
  • rclone 是最佳跨平台云 CLI 选择，支持70多种提供方，通过令牌复制实现无头认证（在浏览器上的机器上运行 rclone authorize，然后将令牌复制到无头服务器）。
  • 批次间模型重用：对于处理多个段的视觉编码器，只需加载一次模型即可在多个段中重用，无需每段重新加载。将模型初始化成本从 O(段数) 降至 O(1)。对像 UNI2这样的大型Transformer来说非常重要。
  • 备用机制不匹配风险：当主要方法失败时，使用较宽松的匹配方式（如几何名称搜索）可能会产生错误结果（“ee”匹配屏幕而非末端执行器）。备用路径需要额外的验证。EEF 身体名称在不同机器人之间有所不同（Sawyer 使用 gripper0_eef，而不是通用的 gripper_link），需要明确包含。
  • 步骤变化系统的检测逻辑简化：对于离散状态系统（如夹持器 0→1 步骤变化），基于连续性的检测（距离减小、接近）不可靠；应该直接检查状态变化（N步后是否不同）。
  • 多检测器系统需要每个检测器冷却时间跟踪——全局冷却会错误地阻止来自不同源的同时检测。检测器特定的约束（距离阈值、相位要求）不应被全局门覆盖——让检测器自行验证。
  • Google Calendar API 端点之间的 OAuth 权限要求差异很大——设置 API 所需的权限比 calendarList API 对相同信息（时区）的要求更低。
  • 双重验证系统（语义路由器 + LLM）需要在两条路径中具有独立的提取能力——不能假设 LLM 总是能生成结构化的输出。
  • ccusage 离线模式的定价表没有包含最新模型（如 Opus 4.6），需要在线获取以进行准确计费。虽然离线模式稍慢，但数据准确性更重要。
  • Windows 子进程调用 .cmd 文件需要 shell=True，否则无法找到全局安装的 npm 命令。
  • 视觉编码瓶颈：(1) 串行补丁提取循环受 CPU 限制（3000-4000次迭代）。(2) 每批后调用 torch.cuda.empty_cache()（约100次）会增加大量开销。(3) 硬编码的 batch_size=32 可能不够理想。优化前需进行性能分析。
  • 基于子进程的环境切换：当依赖项需要不同的 conda 环境时，使用子进程在目标环境中调用脚本，而不是尝试在 Python 内部切换。
  • 用户反馈应详细且具体——对于日历操作，应始终包含：采取了什么操作、哪些事件受到影响以及发生时间。
  • 开发环境可能干扰被测试系统——嵌套的 Claude Code 会话会阻塞基于子进程的 AI 服务调用。子进程继承父环境变量，需要明确移除特定变量（如 CLAUDECODE）以避免嵌套检测。
  • JSON 解析需要多层备用机制以处理 LLM 输出的多种格式：直接解析 → 提取代码块 → 查找 {to} 子字符串。LLM 输出格式不稳定，需要鲁棒性。
  • 配置文件优先级应为：CLI 参数 > 环境变量 > 配置文件 > 默认值，以确保灵活性和可覆盖性。
  • 去重键选择应基于唯一识别实体的最少字段组合。对于对话：(来源、项目、时间戳)。
