问题与解决方案#

关键问题#

1. MIHD 基准测试：冗余嵌入计算 — 相同的基因/视觉编码器针对不同的融合策略运行了数百次（例如，PCA 计算了 55 次，UNI2 计算了 77 次）#

解决方案： 设计了两阶段管道：第一阶段提取并缓存所有编码器嵌入（去重，110 任务对应 286 实验 = 减少 62%），第二阶段加载缓存的嵌入并仅执行融合+聚类+评估。现在 UNI2 模型在所有 11 个部分中只加载一次，而非 77 次。**关键洞察：**当前的缓存使用 {gene}_{vision}_{fusion}/{section}_embeddings.npz作为键，包含融合名称，因此更改融合方式会导致重新提取。编码器级缓存（gene_cache/{encoder}/{section}.npz, vision_cache/{encoder}/{section}.npz）能够实现大量复用。不同部分之间模型实例的复用还能带来额外的加速效果。

2. 错误恢复基准测试：对错误的身体部位施加力（使用bin2而非夹持器EEF），视频中未观察到机器人异常#

**解决方案：**通过详细日志发现力被施加到了bin2上。根本原因：_get_eef_body_name()在可能的名称列表中缺少“gripper0_eef”，回退几何搜索匹配到了robot0_screen_collision（包含“ee”）→ bin2。通过向可能的名称列表中添加“gripper0_eef”、“robot0_right_hand”、“gripper0_gripper_base”解决了问题。

**关键洞察：**不同机器人的EEF身体名称各不相同（Sawyer使用gripper0_eef，而非通用的gripper_link），必须在可能的名称列表中明确包含。回退到几何搜索可能导致包含“ee”的字符串与无关的几何模型不匹配。

3. 错误恢复基准测试：PreGrasp检测器从未触发——get_task_phase()始终返回“未知”#

**解决方案：**根本原因：get_task_phase()调用了_check_phase_condition()，该函数是一个空实现，始终返回False。所有依赖task_phase的检测器（PreGrasp、GraspPrecond）都受到影响。完整的阶段检测逻辑存在于get_task_completion_stages()中。通过重写get_task_phase()以使用基于传感器的检测解决了问题。同时修复了多个连锁错误：前视使用中性动作而非演示动作，接近门阻止了预接触检测器，全局冷却时间导致无法同时检测，MuJoCo身体名称不匹配。

**关键洞察：**代码库中存在可工作的实现（get_task_completion_stages）和始终失败的空实现_check_phase_condition，调用者使用了错误的方法。症状是检测器不触发，根本原因是基础设施层死代码。当观察到逻辑矛盾（没有拒绝但也没有输出）时，应优先进行基础设施审计而非症状调试。

4. 错误恢复基准测试：duration_steps配置参数无效——所有力仅持续1步（0.05秒）#

**解决方案：**MuJoCo在每次sim.step后自动清除xfrc_applied。解决方案：修改collect_rollout_stats()，在验证过程的第一个duration_steps期间循环调用injector.apply()，在持续时间结束后调用injector.clear()。

**关键洞察：**MuJoCo的xfrc_applied是一个持久字段但会被自动清除，需要应用层明确重新应用每一步以维持力作用。这是影响所有错误类型的系统级错误。

5. 错误恢复基准测试：30N力在可视化视频中未观察到机器人臂运动#

**解决方案：**添加 --force_override参数以测试更大的力而不进行再生；更新配置中的力范围至15-45N。在30N下问题仍然存在——需要调查力机制（可能是OSC控制环过强、1步时的力持续时间过短，或xfrc_applied应用不正确）。

**关键洞察：**力注入机制工作正常（xfrc_applied被设置/清除），但30N可能不足以对抗OSC控制器的150 N/m刚度，或者1步的持续时间（约20ms）对于可见效果来说太短。OSC控制环可能在一个控制周期内就抑制了外部力。

6. CalendarPro：用户无法删除符合模式的多个日历事件（例如“3月1日之前取消所有GB教师会议”）——机器人只会说“请指定要删除的事件”#

**解决方案：**扩展数据模型以支持日期范围和批量操作，更新LLM提示以提取这些字段，修改搜索功能以接受自定义时间窗口，并添加带有Discord按钮的交互式确认界面，显示预览和明确的批准选项。

**关键洞察：**对于生产力工具而言，单项CRUD操作不足——带有安全确认的批量操作（预览+用户明确批准）对于涉及模式的用户工作流程至关重要。

7. Gadget/summarize：无头服务器无法安装云存储应用以实现自动同步#

**解决方案：**研究并集成rclone CLI工具，支持通过令牌复制认证方法（在机器上使用浏览器运行rclone authorize，将令牌复制到无头服务器）。

**关键洞察：**rclone支持70多种云提供商，通过令牌复制的无头认证是最佳跨平台云CLI选择。

8. 错误恢复基准测试：全局冷却时间阻止了预抓取检测器，当接近检测首先触发时#

**解决方案：**实现每个检测器冷却时间的跟踪（cooldown_counters字典），使每个检测器拥有独立的冷却时间。过滤检测结果以排除仍处于冷却状态的检测器。

**关键洞察：**对于多个检测器系统而言，全局冷却时间不适合，因为不同检测器针对不同的阶段/条件。多检测器系统需要每个检测器的冷却时间跟踪。

9. CalendarPro：每次用户消息时Google日历API返回403 insufficientPermissions，导致控制台警告#

**解决方案：**从calendarList().get() API切换到settings().get(setting=‘timezone’) API，后者仅需要calendar.events范围而非更广泛的日历访问权限。

**关键洞察：**不同的Google日历API端点需要不同的OAuth范围——对于时区检索，settings API的权限要求低于calendarList API。

10. CalendarPro：当LLM超时（嵌套Claude Code环境）时，批量删除失败因为intent.data为空——语义路由器正确分类了意图，但没有提取结构化数据#

**解决方案：**在处理程序中添加_raw_input穿透机制，实现_extract_delete_query()并使用正则表达式模式从中文/英文短语中解析搜索关键词，并添加日期提取模式以识别如“3月1号前”这样的范围。

**关键洞察：**双重验证系统需要在两条路径中都有独立的提取能力——仅依赖SR fallback不能完全依赖LLM生成的结构化数据。

11. Gadget/summarize：ccusage –offline模式显示Opus 4.6的费用为$0#

**解决方案：**移除–offline参数，切换到在线模式以获取最新模型价格。

**关键洞察：**离线模式的定价表不包含最新模型（如Opus 4.6），需要在线获取以得到准确的计费信息。尽管在线模式稍慢，数据准确性更为重要。

12. 错误恢复基准测试：接近门（max_eef_object_distance=0.05m）阻止了在0.05-0.1m范围内操作的Pregrasp#

**解决方案：**添加检测器名称以绕过列表进行门检测——具有自身距离验证的检测器（pregrasp、grasp_precond）跳过门检测。

经验教训#

关键经验- 实验矩阵的双阶段流水线模式：在运行 M 编码器 × N 融合 × K 部分时，分为阶段 1（具有缓存的 M × K 编码任务）和阶段 2（从缓存加载的 M × N × K 评估任务）。通过共享编码将 O(M × N × K) 的冗余计算减少为 O(M × K + M × N × K)。缓存键设计很重要：编码器级缓存使得不同融合之间可以共享。#

  • MuJoCo xfrc_applied 行为：虽然文档说明 xfrc_applied 在调用间保留，但 mj_step() 会自动清除它。实现持续力需要应用层显式重新应用每个步骤。必须在 duration_steps 后通过 injector.clear() 显式清除，以实现真正的脉冲行为。
  • STUB 方法和完整实现共存存在代码异味：当某个函数中存在完整逻辑但调用者使用总是失败的 stub 时，应立即审核调用关系而非调试参数。当观察到逻辑矛盾（无拒绝但无输出）时，应优先进行基础设施审计而非症状调试。
  • 力注入可视化平衡：KP=150 N/m 的 OSC 控制器需要至少 ≥25N 的力才能看到位移，但 OSC 控制循环可能在一次控制周期内（约 20ms）抑制外部力。需要在力大小和持续时间之间仔细平衡。
  • 生产力工具需要具有安全机制的批量操作：(1) 模式匹配以查找多个项，(2) 预览将受影响的项，(3) 执行前显式用户确认。单一项的 CRUD 操作不足以满足实际工作流程。
  • rclone 是最佳跨平台云 CLI 选择，支持 70+ 提供方，通过令牌复制实现无头认证（在浏览器上的机器上运行 rclone authorize，然后将令牌复制到无头服务器）。
  • 批次间模型重用：对于处理多个部分的视觉编码器，只需加载一次模型即可在部分间重用，无需每部分重新加载。将模型初始化成本从 O(部分数) 降至 O(1)。对像 UNI2 这样的大型 Transformer 至关重要。
  • 回退机制不匹配风险：当主要方法失败时，回退到更宽松的匹配（如几何名称搜索）可能会产生错误结果（“ee”与屏幕匹配而非末端执行器）。回退路径需要额外的验证。EEF 主体名称在不同机器人之间有所不同（Sawyer 使用 gripper0_eef，而不是通用的 gripper_link），需要明确包含。
  • 步骤变化系统的检测逻辑简化：对于离散状态系统（如夹持器 0→1 步骤变化），基于连续性的检测（距离减小、接近）不可靠；应直接检查状态变化（N 步后是否不同）。
  • 多检测器系统需要每个检测器冷却时间跟踪——全局冷却会错误地阻止来自不同源的同时检测。检测器特定的约束（距离阈值、相位要求）不应被全局门覆盖——让检测器自行验证。
  • Google Calendar API 端点之间的 OAuth 权限要求差异很大——设置 API 对于相同信息（时区）需要的权限比 calendarList API 更低。
  • 双验证系统（语义路由器 + LLM）需要在两条路径中具有独立的提取能力——不能假设 LLM 总是能生成结构化的输出。
  • ccusage 离线模式的定价表未包含最新模型（如 Opus 4.6），需要在线获取以进行准确计费。虽然在线模式稍慢，但数据准确性更重要。
  • Windows 子进程调用 .cmd 文件需要 shell=True，否则无法找到全局安装的 npm 命令。
  • 视觉编码瓶颈：(1) 串行补丁提取循环受 CPU 限制（3000-4000 次迭代）。(2) 每批后（约 100 次）调用 torch.cuda.empty_cache() 带来显著开销。(3) 硬编码的 batch_size=32 可能不够理想。优化前需进行性能分析。
  • 基于子进程的环境切换：当依赖项需要不同的 conda 环境时，使用子进程在目标环境中调用脚本，而不是尝试在 Python 内部切换。
  • 用户反馈应详细具体——对于日历操作，应始终包括：采取了什么操作、哪些事件受到影响以及发生时间。
  • 开发环境可能干扰测试系统——嵌套的 Claude Code 会话会阻塞基于子进程的 AI 服务调用。子进程继承父环境变量，需要明确移除特定变量（如 CLAUDECODE）以避免嵌套检测。
  • JSON 解析需要多层回退以处理 LLM 输出多种格式：直接解析 → 提取代码块 → 查找 {to} 子字符串。LLM 输出格式不稳定，需要 robustness。
  • 配置文件优先级应为：CLI 参数 > 环境变量 > 配置文件 > 默认值，以确保灵活性和可覆盖性。
  • 去重键选择应基于唯一识别实体的最少字段组合。对于对话：(来源、项目、时间戳)。
