❌ VLA 基线评估设置（Pi0 + Pi0.5） — 尝试在 GPU 1-2 上启动 Pi0 服务器（端口 5555）和 Pi0.5 服务器（端口 5557）。Pi0 因端口冲突被阻塞，Pi0.5 成功启动。明确了检查点选择的歧义：pi0_libero（LIBERO 微调版）与 pi05_base（预训练版）均不适合 PickPlace 任务，导致数据集实用性的说法受到质疑**关键洞察：**基线评估需要仔细选择模型：领域不匹配的检查点可能因分布偏移而非数据集质量而表现不佳，从而使有效性声明不成立。需要符合任务需求的基线以进行公平评估

3. Vision Refinement scan_cluster 方法获得的 ARI 为 0.313，低于直接 concat 方法（0.387），表明 256d 压缩会丢失对多模态融合有用的信息，尽管能改善单模态聚类效果（0.303）#

**解决方案：**继续测试剩余的 6 种融合方法（attention、adaln_attention、llava_mlp、qformer 等），以判断某些策略是否能更好地利用优化后的 256d 嵌入；考虑调整隐藏维度或测试其他优化方法（stego_refine、byol_spatial）

**关键洞察：**自监督聚类方法注重簇的独立性，这可能不符合多模态融合的信息互补目标。降维可以过滤掉对基因视觉互补性有用的特征，即使这些特征对仅图像聚类的效果不那么明显

4. GPU 分配策略不明确：最初假设只有 GPU 0 可用，实际上 Slurm 节点上有 8 台 A800 GPU#

**解决方案：**人工确认通过 nvidia-smi 检查所有 GPU，使用内存占用超过 50% 的 GPU。更新计划动态检查内存使用情况，相应地分配 CUDA_VISIBLE_DEVICES，从而实现并行任务执行

**关键洞察：**在共享 HPC 环境中，可用性不等于空闲。需要基于内存的标准（50% 阈值）而非简单的空闲检查。如果内存允许，多个任务可以共享节点，最大化集群利用率

5. 到 GPU 节点的 SSH 连接不稳定且频繁断开，导致长时间运行的实验中断#

**解决方案：**改为使用 CLAUDE.md 中记录的基于 Slurm 的工作流：使用 squeue 查找活动作业，然后使用 srun –jobid= 连接到分配的节点。避免直接 SSH，利用 Slurm 的作业管理层

**关键洞察：**Slurm 作业连接（srun –jobid）比直接 SSH 更稳定，因为专为 HPC 工作负载设计，并遵循集群的资源管理层。作业 ID 在会话间保留，便于重新连接

**解决方案：**通过 srun 输出发现。选项包括：终止现有进程，使用不同端口，或检查现有服务器是否可复用。由用户决定冲突解决策略

9. QFormer 训练显示高内存使用量（19.4GB），但 GPU 利用率极低（4%，55W），导致训练进度缓慢#

**解决方案：**发现这是 QFormer 架构的特征：模型和数据存储在 VRAM 中，但交叉注意力计算相对轻量，大部分时间用于 CPU 密集的 k-NN 图构建和损失计算。这是预期行为，需要耐心

**关键洞察：**高内存占用不等于高 GPU 负载。可学习的查询机制导致训练受到 CPU 预处理的限制，而 GPU 核心大多处于空闲状态，VRAM 主要用于存储而非计算

10. 数据集库版本 4.4.1 与转换管道不兼容，导致导入失败#

**解决方案：**降级从 4.4.1 到 3.6.0，以恢复与 MimicGen-to-LeRobot 转换脚本的兼容性

**关键洞察：**前沿包版本可能破坏已建立的工作流程；在生产管道中固定到经过测试版本

人类与 AI 方法#

战略层面#

Vision Refinement 两阶段融合架构设计#

角色 方法
人类 用户明确提出“首先使用 scan_cluster 等自监督方法优化视觉嵌入，然后使用多模态融合策略与基因嵌入合并”——这是一种新的实验设计，AI 没有建议过
AI AI 之前将 scan_cluster 等作为独立融合策略实现（与基因嵌入并行），从未将其视为视觉嵌入预处理步骤

**差异分析：**人类的两阶段思维反映了对方法本质的深刻理解：仅图像自监督是特征优化，而非融合，应在不同的流程阶段使用。AI 的理解更机械（融合选择列表），缺乏对方法可组合性的洞察

VLA 检查点的选择用于基线评估#

角色 方法
人类 人类暂停执行以质疑检查点的相关性：“Pi0 和 Pi0.5 使用哪些检查点？”希望在继续之前了解领域匹配情况（LIBERO-tuned 与 PickPlace 任务）
AI AI 使用现有的符号链接检查点启动 VLA 服务器，未质疑领域匹配，优先保证运行而非验证适用性

**差异分析：**人类对实验有效性进行了批判性思考（基线是否符合目标领域？），避免在无效的基线上浪费计算资源。AI 则遵循文件系统惯例而不持怀疑态度

AI局限性#

关键局限性#

  • 开始VLA评估时使用了与领域不匹配的 checkpoint（在PickPlace任务上调整的LIBERO模型），未质疑其有效性，需要人类暂停并询问“你使用哪个 checkpoint？”
  • 在实施视觉优化时，AI没有预见到组合可能性，被动执行用户的两阶段思路，未主动建议其他组合方式（如stego_refine + attention、byol_spatial + qformer），缺乏对方法组合空间的创造性探索
  • 尽管基于SSH的Slurm-based GPU访问是HPC集群更稳健的方式，但AI未主动建议使用该方法，需要人类从经验中识别稳定性问题并明确请求工作流程调整
  • 尽管拥有8台A800 GPU，却假设采用保守的单GPU分配，需要人类纠正以有效利用集群资源。表明缺乏HPC资源优化意识
  • 在项目组织任务中，AI进入计划模式进行全面探索，但用户两次中断ExitPlanMode，说明计划呈现流程与用户预期节奏不符（用户更偏好“直接执行+即时调整”而非“完整计划+审批后执行”）

一般局限性#

  • 在启动VLA服务器前未检查端口可用性，导致端口5555冲突而启动失败。本应先使用lsof -i :5555或类似检查
  • 在MIHD文件组织过程中，最初误判了ENHANCEMENT_PLAN.md的位置（误以为在docs/目录下），需要验证文件路径。在大型项目中应更仔细地验证文件路径
  • 多次尝试中断ExitPlanMode，但用户持续打断，表明AI未预见到在最终确定前需要迭代优化计划
  • 在生成历史日报时，未质疑为何同一日期需要多次迭代/会话，也未建议将报告生成整合为更高效的单步流程
  • 初始srun命令因未先进入项目目录而超时，花了3次调试才修复。表明对bash环境的模拟不足
  • 在运行7种并行融合方法时，发现qformer运行时间较长且输出文件为空，AI采用重复轮询方式（睡眠30秒→查看输出），但conda run输出缓冲导致文件保持空状态。本应更早识别输出重定向失败，改为检查结果文件(.npz)的存在性而非依赖日志

经验教训#

关键经验- 两阶段融合（自监督优化 → 多模态整合）创造了一种新的实验维度，连接了仅基于图像的方法和多模态方法；但初步测试表明，在各种融合策略中，优化后的嵌入方式并不普遍优于原始嵌入——目标函数的对齐至关重要#

  • 基线模型选择对实验有效性有重大影响。使用不匹配领域的检查点（在 PickPlace 任务上调整的 LIBERO）会削弱其有效性声明。必须明确验证或微调基线以确保公平评估
  • 视觉优化流程的实现证明了在 run_benchmark.py 中插入中间处理步骤的可行性：在适当位置添加约 50 行代码（视觉编码之后、融合之前）可以创建全新的实验范式，同时与现有的缓存/命名/日志系统完全兼容
  • 通过 Slurm 作业附件（srun –jobid）访问 HPC 集群 GPU 比直接 SSH 更稳定，因为利用了集群的资源管理机制，适合长时间运行的科学任务。作业 ID 在会话间保持有效，即使断开连接后也可以重新附加
  • 第一阶段/第二阶段研究项目结构（基础设施构建 → 验证实验）从明确的里程碑跟踪中受益。错误恢复基准测试的 M1-M11 阶段完成（649 个场景），为 M14 基线评估提供了坚实基础，尽管目前受 Pi0.5 OOM 限制
  • 在 HPC 集群中，GPU 可用性应通过内存剩余量（超过 50% 空闲）来判断，而非空闲状态。如果内存允许，多个作业可以共存于同一节点，从而实现并行任务执行并最大化集群利用率
  • 依赖关系拓扑图应先于执行计划。清晰展示 M14 作为关键路径阻碍物的情况有助于调整资源分配决策和时间估计，从而进行更策略性的调度
  • 收集器恢复功能使得容错性强的长时间评估成为可能。M14 合理性检查验证表明，中断后的评估可以从最后检查点重新开始，这对于长达 6 小时的全流程运行至关重要
  • 项目维护“清理日”模式非常有效：使用 3 个并行 Explore 代理进行全面项目调查，然后进行系统清理（删除冗余文件、移动日志文件、重组文档、更新参考文献/内存），最终使根目录简化、文档层次结构清晰且可追踪
  • 通过 /init 技能进行的系统性文档审计在发现迭代开发过程中长期积累的缺陷方面非常有效，尤其适用于各工具独立记录的多工具项目
  • 错误检测流程（20 种分类器、PolicyErrorMonitor）在大规模情况下运行稳定。合理性检查中每集检测到 37-74 个错误，证明分类体系实现已具备生产级能力
  • MimicGen 到 LeRobot 转换流程需要仔细处理扁平与嵌套的 HDF5 布局。Phoenix 论文中用于训练的 84×84 图像被缩放到 224×224 尺寸，转换过程中必须保留此预处理步骤
  • JAX 在 batch_size 可被 GPU 数量整除时，会自动检测所有可见 GPU 用于多 GPU 训练。设置 CUDA_VISIBLE_DEVICES=0,1,3,4 且 batch_size=64 即可实现无需明确配置的高效 4-GPU 并行处理
  • Explore 代理在大型项目组织任务中表现卓越：可以递归遍历目录、读取文件头部快速识别内容、统计代码行数、比较文档以识别冗余——其效率比手动探索高数个数量级
  • 在大型项目清理工作中，如果用户有明确目标且愿意承担计划质量责任，用户控制的规划（跳过 ExitPlanMode 审批）可能更高效。AI 的角色变为执行而非设计

实用经验#

  • 当项目积累大量工作历史时，批量历史报告生成对于建立可搜索档案非常有用，即使主要是元工作而非主要开发。gadget 项目现在拥有涵盖 3 周多项目活动的整合报告
  • QFormer 和其他基于学习查询的融合方法在训练过程中表现出“高 VRAM + 低 GPU 使用率”：参数和中间结果占用内存，但实际计算（交叉注意力）较轻，大部分时间用于 CPU 密集的 k-NN 图构建和损失计算。这是架构特性，而非性能问题
