问题与解决方案#

关键问题#

1. 尽管进行了锚定修复， footer ‘Xs ago’ 文本在窗口调整时仍会上下移动#

解决方案： 将位置设置为 position:fixed; bottom:0，使其被视口锚定而非依赖布局

关键洞察： SetWindowPos 和 CSS 重新布局在 Win32+WebView2 架构中存在固有的1帧延迟；只有 position:fixed 可以绕过 CSS 布局时机

2. SWP_NOCOPYBITS 导致每次 SetWindowPos 帧中 WebView2 内容消失#

解决方案： 移除 SWP_NOCOPYBITS 标志；Windows 将保留旧像素内容，仅使新区域失效

关键洞察： SWP_NOCOPYBITS 对原生窗口的优化在 WebView2 中产生反效果——每帧显示空白窗口，直到重新渲染完成

3. 图表悬停细节面板在鼠标在条间移动时闪烁和跳动#

解决方案： 移除 {#key displayedIdx} DOM 销毁操作，将淡出持续时间从500ms减少到150ms，简化两阶段隐藏流程为单一流程

关键洞察： 过渡期间 DOM 销毁/重建会导致视觉双重显示；响应式内容更新比通过按键重新挂载更流畅

4. #app 底部 border-radius 边缘在调整时显示透明间隙#

解决方案： 在 invoke() IPC 调用前通过 JS 预先设置 appEl.style.minHeight，使浏览器在 SetWindowPos 同一帧内按照目标高度布局 #app

关键洞察： JS 与 Rust 之间的 IPC 延迟导致视觉问题；同步应用 CSS 更改可消除间隙

5. 窗口锚定检测在任意位置失败（不仅仅是距离边缘5px处）#

解决方案： 将 detect_vertical_anchor 从基于阈值的检测（5px）改为距离比较（top_gap vs bottom_gap）；底部锚定使用 current_rect.bottom 而非 work.bottom

关键洞察： 基于阈值的检测会在窗口行为不可预测的地方产生死区；距离比较适用于所有情况

学习收获#

关键收获#

  • Win32+WebView2 架构在 SetWindowPos（原生）和 CSS 重新布局（网页）之间存在固有的1帧延迟；只有 position:fixed 可以绕过这种时间依赖
  • 假设驱动的调试与并行调查比顺序试错更有效；三个子代理同时调查 H1/H2/H3 可节省时间并积累证据
  • 进化约束规划的对抗性评审（第5阶段）能发现关键问题：10个发现涉及子代理写冲突、缺失成功标准、上下文耗尽——均在实施前出现
  • SWP_NOCOPYBITS 优化了原生窗口重绘，但破坏 WebView2 渲染——每帧显示空白窗口，直到浏览器重新渲染所有内容
  • 可观察的成功标准（如‘Xs ago’文本位置）比抽象指标（窗口坐标）更适合调试 UI 问题
