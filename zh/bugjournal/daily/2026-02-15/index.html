问题与解决方案#

关键问题#

1. 可视化视频中未显示任何错误效应，尽管记录了力作用和身体位移#

解决方案： 根本原因：注入过程中的演示动作导致 OSC 控制器（kp=150）补偿外部力；修复方法：在注入和稳定阶段使用中性动作（零向量），使力能够累积而无需控制器干预。

关键洞察： OSC 位置控制器在跟踪轨迹时主动抵抗外部力；必须使用中性动作以观察干扰效应。验证阶段（drop.py）一直使用中性动作是正确的。

2. 可视化视频显示机械臂几乎不动，但日志显示施加了力且身体位置发生变化（15mm-117mm）#

解决方案： 第一个修复：在持续时间窗口内每次步骤都重新施加力（模仿 drop.py），解决 MuJoCo 的每步 xfrc_applied 清除问题。验证确认了力的重新施加（测试 1：11 次，测试 3：21 次）。发现更深层次的问题：可视化使用演示动作，OSC 控制器（kp=150）补偿了外部力效应。

关键洞察： 第一层问题：MuJoCo 物理引擎在每步物理操作后自动清除 xfrc_applied（防止累积），必须每次步骤都重新施加。第二层问题：验证使用中性动作（零向量），控制器仅维持位置；可视化使用演示动作，控制器在每个子步长跟踪演示轨迹（20 个子步长），产生远超外部力的修正扭矩。真正的修复需要在力窗口和稳定期间使用中性动作。

3. Q-Former 进程在完成 6/11 个部分后崩溃/停止，可能损失数小时的 GPU 计算工作#

解决方案： 管道的检查点恢复机制（检查是否存在 *_embeddings.npz 文件）自动检测到已完成的部分并从 151672 部分继续运行，跳过已完成的工作。

关键洞察： 断点续跑机制按设计工作；run_pipeline.py 的 is_completed() 检查防止重复运行昂贵的实验，验证了从原始实现计划到恢复架构的验证。

4. JSON 文件写入被 Ctrl+C、崩溃或电源中断打断，导致部分写入的无效 JSON，引发下次读取时的解析失败#

解决方案： 实现了 _atomic_write() 函数：写入临时文件（mkstemp），flush，使用 os.replace 进行原子重命名，失败时清理临时文件。确保要么完整旧文件要么完整新文件存在， never 处于部分写入状态。

关键洞察： 原子写入是防止文件损坏的标准模式：写入临时文件 → 原子重命名。适用于所有 JSON/配置文件持久化场景。

5. 多设备工作流需要手动将每台设备的日志文件复制到一台机器进行合并，操作繁琐#

解决方案： 将上传内容导出到 /logs/，将上传结果合并到 /reports/，添加 –sync 标志以自动从远程下载所有设备日志（使用 –include ‘{date}_*.json’ 过滤），去重路径后调用 API 生成报告。

关键洞察： rclone 子目录隔离 + –sync 标志将多设备协作从“手动复制”简化为“一条命令”，大幅减少了心理负担。

6. scgpt_uni2_qformer 实验因 CUDA 内存不足失败（11/12 次失败），尝试分配 2 MiB 但 GPU 仅有 2.31 MiB 空闲，进程已使用 21.46 GiB#

解决方案： 确定根本原因：pca_uni2_qformer 占用了 GPU（21.5 GB），没有足够内存用于并行 scgpt_uni2_qformer 运行；确定 scgpt Q-Former 实验必须等待 pca Q-Former 完成，以避免 GPU 竞争。

关键洞察： Q-Former 训练需要约 22GB GPU 内存；在 32GB GPU 上并行运行两个 Q-Former 实验会导致 OOM；尽管是技术上独立的任务，仍需顺序执行。

7. LLM 偶尔返回无效 JSON（Markdown 代码块、额外文本），导致 json.loads 失败#

**解决方案：**修复了 batch_visualize.py 的 GPU 分配问题：始终将 MUJOCO_EGL_DEVICE_ID 设为 0，并根据进程调整 CUDA_VISIBLE_DEVICES 以匹配（例如，CUDA_VISIBLE_DEVICES=3 时 MUJOCO_EGL_DEVICE_ID=3 是不正确的；两者都应使用相对 ID 0）

**关键洞察：**MuJoCo EGL 在 CUDA_VISIBLE_DEVICES 内使用相对 GPU 索引，而非系统 GPU 的绝对 ID

10. ProximityDetector 和 CollisionDetector 仅生成脉冲类型规格，导致场景库为单一类型（所有 30 个场景均为脉冲/尖端过界）#

**解决方案：**修改了两个检测器的 detect() 方法，将 _generate_impulse_specs() 替换为 _generate_mixed_specs()，同时生成脉冲+姿态扰动+摩擦候选项，并将最大场景数配置增加到 10

11. 一次 staig_fusion 失败（scgpt_uni_staig_fusion/151676）由“输入 X 包含 NaN”错误引起，同一部分也导致 pca_uni_staig_fusion 失败#

**关键洞察：**当同一部分在多种配置下因 NaN/零方差症状而失败时，很可能是数据问题（缺失空间坐标、表达式值损坏），而非代码 bug；STAIG 模型崩溃是问题输入的常见故障模式

**关键洞察：**延迟加载必须是事务性操作：所有初始化步骤必须在提交状态前成功；部分成功会导致对象损坏

**关键洞察：**轨迹数据需要完整状态保存（不仅是动作/奖励，还有 EEF 位置、夹持器状态、所有物体位置），NPZ 压缩存储（每款约 64KB），由配置标志控制

  • 对自然语言指令“不应合并默认设置”理解模糊，最初理解为 –sync 行为而非主开关，需要用户的再次说明
  • 首次尝试批量 GPU 分配使用了错误的 EGL 设备 ID 映射（不理解相对索引与绝对索引），出错后需要修正
  • 在第一次会话中，AI 直接调用 ExitPlanMode，没有预料到用户可能中断，导致第二次会话需要重新实现计划，显示跨会话连续性差
  • 作为每日报告分析工具时，AI 只能处理传入的对话记录，无法主动获取当天未包含在输入中的其他对话
  • 在研究 Pi0/Pi0.5 检查点可用性时发现 robosuite 没有微调检查点，但并未主动提出 LIBERO 环境整合方案或评估工作负载
  • 处理网站不是独立 git 仓库时，AI 只是被动解释当前状态，没有主动询问用户是否希望为网站源文件建立版本管理

学习成果#

关键学习成果- OSC位置控制器（kp=150）产生的关节扭矩远超常规外部力（15-20N），可在跟踪轨迹时主动补偿干扰。中性动作会停止跟踪，使力效应得以累积。#

  • 检查点/恢复机制在实际崩溃时验证其设计；MIHD的is_completed()文件存在性检查成功防止了6个部分（约9小时GPU工作）在进程崩溃后重新运行。
  • 原子写入是防止文件损坏的标准模式：tempfile + 写入 + 重命名。适用于所有JSON/配置文件持久化场景。
  • 多设备协作工具设计模式：本地生成 → 上传至云端子目录 → 单命令下载+合并，通过–sync标志将复杂工作流封装为单一命令。
  • MuJoCo在每次物理步骤后自动将xfrc_applied置零（默认0.002s）；为维持效果需在每个控制步骤中重新应用力。验证代码在10步循环中正确执行此操作。
  • 错误场景生成流程完全模块化：检测器→注入器→验证器均遵循插件模式，可通过更换动作源（policy.predict vs demo_actions[i]）无需修改即可用于基于策略的生成。
  • Robosuite的env.step()包含20个物理子步骤（默认control_freq=20，每个控制步骤0.04s = 20×0.002s物理步骤）。OSC控制器在每个子步骤中跟踪目标姿态（kp=150刚度），小于控制扭矩的外力将被补偿掉。
  • 错误注入流程在动作层面已与策略无关（EnvWrapper.step(action）不关心动作源）。从演示注入到策略注入的核心在于更换动作源（demo_actions[step] → policy.predict(obs)），检测-注入-验证流程保持不变。
  • 将写作计划写入.md文件并在新会话中粘贴是保留会话间上下文的有效方式，比依赖工具调用链更可靠。
  • Q-Former训练需要约22GB GPU内存；在32GB GPU上，尽管逻辑独立但并行Q-Former实验仍会导致OOM；内存密集型实验即使计算图独立也需顺序执行。
  • 云LLM API的结构化输出功能（Anthropic tool_use、OpenAI response_format）应被优先使用，可显著降低JSON解析失败率。
  • 幂等性设计：通过_merged_devices列表跟踪处理状态，重新运行时跳过已完成的操作，节省API成本。
  • MUJOCO_EGL_DEVICE_ID在CUDA_VISIBLE_DEVICES内使用相对索引，而非绝对系统GPU编号。对于单GPU进程，无论使用哪种物理GPU，始终将MUJOCO_EGL_DEVICE_ID设置为0。
  • 需要事务性初始化的延迟加载带回退机制：在本地作用域中创建对象，验证所有初始化步骤，仅在完全成功后分配给实例变量。部分成功会导致状态损坏。
  • 检测器设计应允许高频触发检测器提出多种类型规格，避免单一类型占用最大_scenes_per_demo配额。GraspPrecondDetector设计正确（脉冲+姿态扰动+夹持器偏置），需对ProximityDetector和CollisionDetector进行扩展。
  • 当相同数据部分（例如151676）在多种模型配置下持续出现NaN/零方差症状时，根本原因可能是数据质量问题（缺失坐标、损坏值），而非代码错误。
  • 代码重复阈值：当相同模式重复8次时，必须提取为共享工具；除了减少重复外，集中错误处理和超时逻辑可避免行为不一致。
  • 轨迹数据保存应包含完整状态（动作/奖励 + EEF位置 + 夹持器状态 + 所有物体位置），采用NPZ压缩存储（约64KB/集），由配置标志控制（evaluation.save_trajectories）。
  • 基础设施级功能（时间解析、提供者选择）应具有统一实现，而非模块级复制；单一真实来源原则适用于逻辑模式而非数据定义。
  • BC策略加载需从配置中读取检查点路径和设备信息，错误消息应提供可操作的修复指导（告知用户设置哪些字段）。Pi0/Pi0.5及其他基础模型目前没有Robosuite微调检查点，需自行微调或集成LIBERO环境。

实际经验总结#

  • rclone远程配置需要两步：安装rclone + 运行rclone config绑定云账户，脚本中的rclone_remote仅指定“上传位置”。
  • Hugo部署通常将公共/子目录作为Git仓库推送到GitHub Pages，按标准做法将源文件仓库和部署仓库分离。
  • 外部工具输出格式可能随版本/环境变化，防御性编程应检查类型并灵活处理（例如ccusage返回列表情况）。
  • Git子模块清理需执行：git rm –cached <路径>，删除.gitmodules，克隆新副本，移除.git目录，作为普通文件阶段化。还需更新所有文档引用，如果存在.git/modules/则删除。
  • Hugo前言摘要字段可直接从报告引文行提取用于内容复用。
