问题与解决方案#

关键问题#

1. 个人数据文件（对话日志、AI摘要、博客内容、研究缓存、基准测试结果）通过git跟踪并推送到GitHub，导致代码仓库与数据存储边界模糊，存在隐私风险#

解决方案： 设计三层清理机制：(1) 当前工作目录：使用git rm –cached删除跟踪记录；(2) 使用git filter-repo重写所有24次提交历史；(3) 强制推送后，使用rclone统一管理个人文件（远程路径gdrive:gadget）。将仓库大小从22MB缩小到516KB

关键洞察： Git和rclone的责任边界必须明确：git管理公共代码和可复现配置，rclone管理个人数据和运行输出。混合使用会导致仓库膨胀（94MB个人数据）、隐私泄露和协作困难。明确的分离能建立数据隐私边界

2. 当用户在其他设备上进行合并操作生成最终报告时，本地合并–sync-all仍将所有日期视为未最终完成，导致重复调用LLM#

解决方案： AI发现_rclone_download_logs仅下载日志而非报告，导致本地最终检查失败。实现_rclone_download_reports()在sync-all最终状态检查前从远程拉取现有报告

关键洞察： 在分布式协作场景中，状态同步必须同时同步输入（日志）和输出（报告），否则重复处理逻辑会失败。完整状态同步可避免资源浪费（重复LLM消耗）

3. test/CLAUDE.md中CPU BLAS matrix_size被记录为8192（单核）和4096（多核），GPU为2048——均错误#

解决方案： 验证实际代码：CpuSingleCoreBLASBenchmark.MATRIX_SIZE=2048，CpuAllCoresBenchmark.MATRIX_SIZE=4096，GpuBenchmark.MATRIX_SIZE=8192。更新文档以符合实际情况

关键洞察： 文档与代码的偏差会随时间悄悄累积；通过并行代理逐行验证可发现容易忽视的数字错误。系统性的全面验证对于正确性至关重要

一般问题#

4. git filter-repo删除了.gitkeep文件及过滤后的目录，导致目录结构无法保留#

解决方案： 使用touch和git add -f重新创建.gitkeep文件（research/cache/、research/projects/、research/reports/），在filter-repo+强制推送后提交为单独的“恢复目录结构”提交

关键洞察： git filter-repo的–invert-paths会删除整个目录树及结构文件；.gitkeep恢复必须作为filter-repo后的提交进行，而非过滤前的添加

5. research/CLAUDE.md第74行标注为“两阶段评估流程”，但第79行的标题为“三阶段评估流程”——存在内部矛盾#

解决方案： 验证代码实际实现3个阶段（筛选→深度分析→引用影响）；将第74行更新为“三阶段”，并批量替换research_scout.py注释中所有7次“两阶段”为“三阶段”

关键洞察： 文档与代码自相矛盾（同一文件不同部分）表明历史演变未完全协调；基于grep的批量修正可确保无残留不一致

AI 局限性#

关键局限性#

  • 在设计 rclone sync 逻辑时，AI 未能预见到 “sync-all” 场景下最终检查对报告的依赖关系，需要用户明确指出 “报告也需要下载”。对于分布式协作状态同步完整性缺乏前瞻性思考。
  • AI 最初没有建议进行逐行文档全面验证，直到用户明确要求 “检查每句话”；默认模式采用针对性/抽样式审查，可能会遗漏数值错误（matrix_size、博士毕业年份范围）。

一般局限性#

  • AI 启动了 3 个并行 Explore 代理进行代码库扫描（个人文件清单、rclone 逻辑、git 历史），尽管全面但效率可能不佳——这些信息可以通过几个 grep/ls/git 命令快速获取，代理开销可能过大。
  • AI 没有预测 .gitkeep 文件会被 git filter-repo –invert-paths 删除（目录结构保留问题）；需要用户在 filter-repo 后手动恢复这些文件。

经验教训#

关键经验#

  • Git 与 rclone 的责任边界必须明确：git 管理可复现的公开代码和配置（requirements.txt、scripts、CLAUDE.md），rclone 管理个人数据和运行输出（日志、报告、缓存、测试结果、网站内容）。混合使用会导致仓库膨胀（94MB 个人数据）、隐私风险及协作障碍。明确的分离能建立正确的数据隐私边界。
  • 文档与代码偏差是不可避免的，会随时间悄悄累积；定期进行逐行全面验证（使用并行 Explore 代理以提高效率）是必要的，以发现随意阅读无法发现的数值、路径引用和内部矛盾。系统化的验证可防止小错误累积。
  • 分布式协作状态同步设计原则：不仅需同步输入数据（日志），还需同步中间输出（报告），否则依赖输出状态的逻辑（如最终检查）会在不同设备间失败。完整的状态同步可避免资源浪费（重复调用 LLM）。
  • git filter-repo 是清除 git 历史中大文件/敏感数据的正确工具（仓库大小从 22MB 减少到 516KB），但需要完整工作流：备份 .git、运行 filter-repo、恢复结构文件 (.gitkeep)、强制推送、更新所有克隆副本。风险管理检查清单：（1）必须在所有设备上备份，（2）需要强制推送，（3）其他所有克隆副本将损坏需重新克隆。应使用明确的用户确认流程（AskUserQuestion）以确保理解破坏性后果。

实际经验#

  • 在构建集中式同步基础设施（sync.py）时，从一开始就支持 –dry-run 和 –category 标志，可以安全地进行增量测试和选择性同步，无需完整上传数据；rclone remote 路径迁移（gdrive:summarize/ → gdrive:gadget/）通过原子移动操作风险较低。修改远程路径时的配置迁移完整性检查清单：必须同时更新（1）summarize/daily_summary.py config.json、读取内容，（2）research/research_scout.py 配置，以及测试/同步逻辑、（4）网站/Hugo 集成、（5）sync.py 全局配置、（6）现有远程数据迁移脚本。
