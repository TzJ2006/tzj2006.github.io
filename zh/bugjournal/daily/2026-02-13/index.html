问题与解决方案#

关键问题#

1. 错误恢复机器人在演示重放时从未接近物体（最小距离0.22米，任务需要接触）#

解决方案： 通过追踪robosuite源代码、HDF5元数据、MuJoCo主体映射发现：使用PickPlace_D0+控制器配置记录的演示以纯PickPlace形式重放。相同操作会产生完全不同的轨迹。

关键洞察： 环境配置（包含kp、阻尼、斜率比的控制器配置）从根本上改变机器人动力学。始终使用来自HDF5数据集的精确环境元数据进行重放——参数调整无法掩盖根本原因

2. CalendarPro语义路由器和LLM意见不一致，系统始终使用SR导致错误路由（例如‘leetcode’关键词 → manage_recurring而非update）#

解决方案： 修改了dual_verify.py，在出现不匹配时优先使用LLM意图而非SR。LLM拥有完整的对话上下文，而SR仅匹配关键词。日志中显示‘→ using LLM intent’用于监控。

关键洞察： 基于关键词的分类器对模糊表达无效。当语义路由器和LLM意见不一致时，应信任具有更多上下文的模型（LLM），而非更快的SR。SR过滤明显情况，LLM作为仲裁者

3. MIHD 4部分数据缺失导致管道失败（空间文件、频率过滤空补丁、STAIG模型崩溃）#

解决方案： 从Dataset.zip中提取空间文件；添加边界检查（min_w/min_h >= 10）；添加mclust回退到KMeans，使用try/except包装器

关键洞察： 空间转录组数据需要强大的容错能力：多路径候选搜索、图像处理边界检查、统计模型回退策略以应对分布异常

4. gadget原始单步工作流无法支持多设备协作（需要手动复制日志到每个设备）解决方案： 重构为两阶段流程：(1) 导出子命令以创建本地 JSON 日志（无需 API 密钥），包含设备信息；(2) 合并子命令，聚合多份日志并调用 API 生成最终报告；保留旧模式以实现向后兼容#

关键洞察： 多设备工作流需要可移植的中间格式（版本化 JSON 日志）和清晰的阶段分离（本地解析与远程合并）。主要设计：设备信息收集、为未来扩展提供版本支持、可选的设备级摘要以防止合并时信息丢失

5. 添加邻近限制后所有错误检测器均失败——迭代阈值调整（0.05→0.15→0.25→0.30m）未产生任何触发信号#

解决方案： 编写诊断脚本测量实际 EEF-对象距离，发现是环境不匹配而非阈值问题。根本原因是重放配置，而非检测器的灵敏度问题

关键洞察： 当所有检测器都失败时，应通过诊断日志测量真实值，再调整阈值。无触发信号的症状往往掩盖了根本的不匹配（控制器动态错误）

6. CalendarPro 日历 API 错误（403 insufficientPermissions、HttpError）通过 print() 捕获并返回 None，导致用户对通用的“失败”消息感到困惑#

解决方案： 创建 CalendarServiceError 异常；重构所有 calendar_service 方法以抛出包含详细上下文的异常；更新所有调用方以捕获并显示包含技术细节的用户友好消息

关键洞察： 静默吞没错误（print + 返回 None）破坏了错误契约。用户无法修复看不见的问题。始终将带有上下文的错误传递给展示层，然后适当格式化

7. CalendarPro AI 提供方没有超时处理机制——网络卡顿可能使整个机器人无限期停滞#

解决方案： 用 asyncio.wait_for(timeout=30.0) 包裹所有 API 调用，并在客户端构造函数中添加 httpx.Timeout(30.0)，在超时时返回包含错误字段的 AIResponse

关键洞察： 超时保护需要双层防护：asyncio 协程级别（wait_for）和 HTTP 客户端级别（httpx.Timeout）以捕捉不同的失败模式

8. CalendarPro JSON 解析失败发生在 AI 在 JSON 之前返回文本、多个块或截断的 JSON 时——导致意图分类崩溃#

解决方案： 实现 _extract_json() 方法，通过平衡花括号计数提取第一个完整对象；添加三阶段回退机制（直接解析 → 修正尾逗号 → 通用意图）；移除 ValueError 异常用于日志记录和回退

关键洞察： 生产级 AI 系统需要优雅降级——绝不能在格式错误的输出上崩溃，始终提供安全的回退意图

9. 计划文档缺乏自包含性——用户多次拒绝 ExitPlanMode，要求“将计划的每个词都写入计划文件”#

解决方案： 重写计划文档使其完全自包含：添加用户决策记录、带有精确行号的代码快照、QueST 参考代码细节、包含“在行 X 后插入”位置的完整实现代码以及每个阶段的对应位置

关键洞察： 计划模式文档必须完全自包含，以便未来会话恢复。用户拒绝信号表明细节不足——所有探索结果（精确位置、行号、函数签名、现有代码）都必须写入计划中，而非依赖外部上下文

10. MuJoCo 速度交换导致虚假不稳定触发（角速度被误读为线性）#

解决方案： 交换数组切片：linvel = cvel[3:], angvel = cvel[:3]，以匹配 MuJoCo 的 [angular(3), linear(3)] 布局

关键洞察： 文档不匹配：代码注释声称 [linear, angular]，但 MuJoCo 存储的是 [angular, linear]。始终依据源文档验证，而非内联注释

11. Error recovery CLAUDE.md 有 615 行，各部分之间重复较多，还有内容属于 README 文件#

解决方案： 重写内容，重点包括：(1) 不易发现的信息（服务器限制、常见陷阱）；(2) 将命令整合到单一块中；(3) 移除易于发现的内容（文件树、方法签名）；(4) 仅保留需要多文件读取的架构

关键洞察： AI 代理文档应关注无法通过工具发现的内容，而非全面参考。简洁性提升可用性——101 行对比 615 行，且更清晰

12. CalendarPro 更新重复事件时修改的是整个系列而非单个实例，尽管搜索参数设置为 singleEvents=True#

解决方案： 修改 update_event() 以检测重复实例（有 recurringEventId），在调用 API 前移除重复/recurringEventId 字段。Google Calendar 仅针对该实例产生异常

关键洞察： Google Calendar API 隐式行为：搜索中的 singleEvents=True 提供实例 ID，但更新/删除需要明确移除字段以避免系列-wide 变化。始终在测试日历上测试重复操作

13. CalendarPro asyncio.create_task() 用于消息队列没有异常回调——任务可能在完整队列中静默死亡，用户消息 never 被处理#

解决方案： 所有 create_task 调用添加 done_callback=_on_queue_task_done；实现清理处理器记录异常并移除死亡任务；添加 close() 方法用于关闭

关键洞察： Asyncio 后台任务默认是“即使用完即忘”——始终为监控/清理添加 done 回调，尤其是长期运行的任务

一般问题#

14. 手动查询令牌使用情况很繁琐——用户希望自动生成每日统计#

解决方案： 通过子进程集成 ccusage，调用 npx ccusage@latest daily –json 并解析输出；在三个入口点实现自动收集；渲染包含总计表格和模型细节的令牌使用部分；跨设备合并聚合数据

关键洞察： 利用现有工具自动化数据收集，而非重新实现。设计考虑：子进程容错性（如果不可用则静默跳过）、多设备聚合策略（汇总令牌/成本、合并模型细节）、易于阅读的表现形式（表格优于列表）

15. MIHD GPU 峰值统计始终为零（ResourceMonitor 从未调用 update_peak_stats()）#

解决方案： 重构 ResourceMonitor：start_monitoring() 每秒启动守护线程采样，stop_monitoring() 终止线程并采样最终峰值，添加 threading.Event 生命周期控制

关键洞察： 监控峰值统计需要在运行期间持续采样，而不仅仅是 start/stop 快照。后台守护线程是标准解决方案，但需 proper 生命周期管理以避免资源泄漏

16. gadget test/ 目录是一个包含自身远程仓库的嵌套 Git 仓库，导致 git add 时出现嵌套仓库冲突#

解决方案： 使用 git submodule：将测试文件移动到备份中，运行 ‘git submodule add git@github.com:TzJ2006/test.git test’ 克隆到正确提交，删除备份，.gitmodules 自动记录配置

经验教训#

关键经验- 环境配置（controller_configs）从根本上改变了 robosuite 中的机器人动力学。在重放示例时，务必从 HDF5 数据集元数据中提取并使用准确的 env_name + env_kwargs。#

  • 错误注入可视化需要三阶段叙事： (1) 导致触发的重放示例动作，(2) 显示检测触发时刻，(3) 注入错误并展示后果。静态快照恢复会丢失“为何现在注入”的上下文。
  • 机器人仿真重放的准确性要求环境配置与控制器参数（OSC_POSE、kp、阻尼、ramp_ratio）完全一致，而不仅仅是任务名称。必须加载示例元数据（HDF5 中的 env_args）以重现相同的动力学行为。
  • 切勿对错误保持沉默（仅打印并返回 None）。务必将错误信息随上下文传递到展示层。用户无法修复他们看不见的问题。
  • 多设备工作流采用两阶段模式：本地导出（无需 API）+ 远程合并（需要 API）。关键要素包括：版本化的中间格式（JSON 日志）、设备信息收集、可选的每台设备摘要。
  • “计划模式”的目标是生成完全自包含的实现手册，需要所有探索结果（准确的代码位置、行号、函数签名、现有片段），而非简单的任务列表。
  • 系统性的根本原因分析比逐步调整参数更有效。当检测失败时，在调整阈值之前，需系统地比较录制环境与重放环境配置。参数扩展往往掩盖了根本的不匹配问题。
  • 当双分类器意见不一（语义路由器与 LLM）时，应信任具有更多上下文的那一方（LLM）。关键词匹配在模糊表达上会失效。
  • 超时保护需要双层防御：使用 asyncio.wait_for() 处理协程级超时，使用 httpx.Timeout() 处理连接级超时——不同的故障模式需要不同的保护机制。
  • 生产级 AI 系统绝不能因畸形 AI 输出而崩溃——需实现三阶段回退机制（直接解析 → 修复 → 安全默认），并在每个阶段进行详细日志记录。
  • 在现有代码库中添加新功能时，研究现有的类似模式（ThoughtOrganizer → PeriodicChecker）可确保架构一致性并减少集成阻力。
  • 空间转录组数据容错设计：多路径候选搜索（main_dir 和 Dataset/DLPFC），图像处理边界检查，统计模型回退策略（mclust → KMeans）。
  • MuJoCo cvel 存储的是 [angular(3), linear(3)]，而非 [linear(3), angular(3)]。务必对照主要文档验证二进制数据布局，而非依赖内联注释。
  • AI 智能体的文档应重点介绍不易察觉的信息和需要多文件理解的架构模式，而非全面的参考材料。AI 智能体可通过工具发现文件结构和方法签名，但它们需要关于陷阱和约束条件的上下文指导。
  • Google Calendar API 的定期事件：singleEvents=True 可获取实例 ID，但更新/删除操作需明确剥离字段（recurrence、recurringEventId），以避免整个序列的变化。
  • 全面的规划文档（如包含成熟度评级、路线图优先级、架构理由的 PLANNING.md）为逐步开发提供战略基础。
  • Asyncio 后台任务需要明确的生命周期管理：使用 create_task + done_callback 进行监控，close() 方法进行清理，正确记录异常以防止无声失败。
  • CalendarPro 架构模式：JSONL 仅追加写入以加快写入速度（thoughts.jsonl、intent_mismatches.jsonl），JSON 用于可变状态，复用现有数据源（DEFAULT_MEALS/DEFAULT_SLEEP）作为单一真实来源。
  • 在编写架构文档之前进行全面的前期探索（使用并行 Explore 代理）比逐步发现更有效——战略思考能带来成效。
  • 两阶段管道（导出 → 合并）是多设备工作流的自然模式，适用于手动数据传输。每台设备的导出支持增量处理和异步设备使用。
  • 惰性导入（方法内部的 import 语句）有助于打破循环依赖，但需特殊测试处理：模拟消费模块的命名空间，而非原始模块。

实用经验#

  • 通过利用现有工具（ccusage）自动化数据收集，而非重新实现。设计考虑因素：子进程容错性（失败时静默跳过），多设备聚合策略（求和/合并），易于阅读的展示方式（表格 > 列表）。
  • Git submodule 的使用场景和管理：适用于独立远程子项目，记录提交哈希而非分支，克隆需使用 –recursive，更新需使用 cd + git pull + 提交哈希变更。
  • 监控峰值统计数据需要在运行期间持续采样（后台线程），而不仅仅是启动/停止快照。需 Proper 的线程生命周期管理（Event 机制）以避免资源泄漏。
  • Windows conda 工作流需要 PowerShell，而非 cmd.exe。批处理文件缺乏 proper conda 集成。务必在全新 shell 中测试环境激活。
  • 在 pytest 中模拟时，始终在函数定义的源模块进行补丁，而非导入处——本地导入会创建新的引用，绕过模块级补丁。
  • 集群文件系统语义：共享存储意味着节点间路径相同，但 SSH 会话默认使用 home 目录——远程命令中务必明确执行 cd。
